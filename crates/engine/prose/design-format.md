# Design format

Hard-coded conventions of the rendered `design.md`. These are not configurable.

`design.md` carries the technical shape the non-behavioural claims evidence. The engine renders its front matter (`emery: <grammar>`, `revision: <id>`), `# Design`, your `preamble` paragraphs, then one `## ` section per drafted entry, in this fixed order whatever order you answer in:

1. `overview` → `## Overview` — what the system is and why, from `intent` and top-level `section` claims and the request's requirements. Always required.
2. `domain-model` → `## Domain model` — types and identifiers. Reference every `type` claim exactly once as a `type` block, each with its `role`; the engine renders a `Type: <key>` line — `Type: <key> (mechanism)` for a mechanism — and the claim's `signature` verbatim as a fenced code block beneath it.
3. `apis` → `## APIs and integrations` — external surfaces (`call` / `contract` / `decision` claims, surface-naming requirements): every inbound surface, and every outbound or reference-data call the `call` and `excerpt` claims carry, whether or not a requirement cites the module that makes it. Name each system the program reaches by its role — a message stream consumed or published, a store, a cache, an upstream service, an identity provider, a monitor — and beside it the technology the `call` claims spell as playing that role, with the topic, URL, entity, and keys as constructed, so a target can map the role onto its own platform and the operator can see what the source ran against. The technology a `decision` prescribes — a brief or a decision record saying the events go through one broker, the secrets live in one vault — lands here too, beside the role it plays and cited `(from <source>)`, since the specification states the behaviour by role alone and this section is where a target reads what was chosen. Spell each of these as the claims state it, and say `[unknown]` where they are silent:
   - a stream's topic as the code constructs it — the setting it reads, the default it falls back to, any suffix joined on — and the key each message is published under; an inbound stream's bullet also names the requirements its deliveries set off (`per REQ-019`), since the specification states what a delivery does and never the subscription, and a target reads the trigger from this bullet alone;
   - an upstream call's method, its path or URL template with its query parameters — its base URL as the code constructs it, the setting it reads by its key and the default it falls back to (`GTFS_CC_STATIC_URL`, default `https://..`), never the accessor that held it (`Config.staticCCUrl`), since a target reads the setting by its key and an accessor names nothing a deployment supplies — and the fields of its response the code reads, by path within the response body (`items[].sku`, `rates.fx.mid`), never prefixed with an HTTP client's own holder of the body (`response.data`, `res.body`), since a target reproduces the response's shape from this section alone and a holder written here becomes a wrapper the wire never carried;
   - the rule each such call runs under — its authentication, its timeout, its retry rule (`status < 500`, three attempts), its fallback, and the interval or TTL a reference table read through it is refreshed on (`10m`) — so a target building a cache-aside reference table has the endpoint, the fields, and the TTL from this section even when no requirement cites the module that prefetches it;
   - a produced message's wire shape — its field names as sent, nested as sent, with the constants the code fixes (`version: "1.0"`, `priority: 0`) — where no `type` claim declares it, since a shape the source builds in a function body reaches the design through the `requirement` or `excerpt` that states it, and this is where a target reads it.
4. `technical-logic` → `## Technical logic` — delegation, validation, errors; fold abstracting `excerpt` claims. Write out, in full, every literal value the `criterion` and `excerpt` claims carry that a behaviour reads: a lookup mapping entry by entry, the active entries of a filtered one each with its mapped value, a numeric threshold, a format string, a timezone or locale identifier, a default. A stem built in several slices reads these from this one section, so a value summarised here into the name of the constant that held it is a value each slice invents for itself. This section also carries the program's readiness and lifecycle from the `excerpt` claims, since the specification states none of it: what it loads or obtains before it serves (a credential, a token, a reference table), how it rotates a credential and what rotation does to the process, what it schedules and on what interval, how it acknowledges or advances a delivery, how it drains and shuts down, and what a signal or an uncaught error does — each as the claims state it, so a build that reads the specification for the behaviour reads this for the machinery that readies it.
5. `ui-layout` → `## UI / layout` — only with spatial claims (`region` / `container` / `leaf`), rendered as one tree.
6. `observability` → `## Observability` — only when claims evidence metrics, traces, or logs.

## Section plan

The request lists every section with its presence — `required`, `permitted`, or `omitted` — computed by the engine from the claim kinds present. Draft every `required` section, never an `omitted` section, and a `permitted` section only when claims inform it. Each drafted section carries at least one block.

## Blocks

- **`{"text": "…"}`** — one Markdown paragraph. Cite decisions inline as `(from <source>)`, where `<source>` is exactly one bound source name; a citation naming an unbound source is refused. Refer to requirements by their `REQ-NNN` id inline — no `### Requirement:` or `#### Scenario:` heading and no provenance line belongs here.
- **`{"type": {"key": "<key>", "role": "data" | "mechanism"}}`** — a `type` claim by its declared name — its `name`, else its id, else its path with any line anchor stripped — under `domain-model` only. Interleave with text blocks to place each signature; every listed type claim is referenced exactly once, or the draft is refused. The `role` is what the type stands for, and it decides what a build does with it:
  - `data` — a shape the program reads, stores, or produces: a message consumed or published, a record, an upstream response, an enumeration. A build declares it, and the plan gives it to the one slice whose requirements read or produce it.
  - `mechanism` — a class that is part of the source's own machinery rather than its data: a client for an upstream service, a secret retriever, a settings carrier, a bootstrap or main, a converter whose state is its dependencies, or a custom error or exception class (`extends Error`, `ValidationError`). A build declares nothing for it — the behaviour its requirements state is built through the target's own platform and its error contract — and no slice owns it. Decide by what the type holds, not by its name: a class holding a URL and a method that fetches, or extending `Error` to signal a failure, is a mechanism; a class holding the fields a message carries is data, whatever the source called it.

Fold `decision` and `section` claims into the section they inform — a `decision` naming a technology into `apis`, which its presence requires. Where the claims are silent, say nothing — never pad a section with invented architecture. No timestamps or run identifiers; re-runs must be byte-identical.

## Amending

A request that opens `Amend design.md` redrafts part of a design that already stands. The claims it lists are a change's alone, and the engine has decided from their kinds which sections they inform, by the table above: a `decision`, `call`, or `contract` informs `apis`, a `type` informs `domain-model`, an `excerpt` informs `technical-logic`. A section is listed too when one of its paragraphs describes a requirement the change retires, since the design must stop describing what the specification no longer states. The request lists exactly those sections under `## Current design`, and `## Overview` with them, since it describes the whole. Answer those sections and no other: every other section and the preamble are the current design's and are kept by the engine, and a section you answer that is not listed is refused.

Each listed section shows its current blocks numbered `[1]`, `[2]`, … A listed section the current design lacks says so, and you draft it whole. For a section that stands, the redraft is the current text with the change folded in:

- Keep every paragraph verbatim unless the change touches what it describes, and name every paragraph you reword in that section's `revised` list, by its number. Naming a paragraph `revised` rewords it, never drops it: every requirement it describes that the change keeps is still described by a paragraph of the section you answer, in `## Overview` as in any other, or the redraft is refused naming the requirement — so a paragraph you drop under `revised` describes retired requirements alone, or no requirement at all. A paragraph describing requirements the change leaves unchanged, and nothing else, is kept as it is — except in a change that adds or revises no requirement, whose whole content is technology: that lands in the paragraphs that already describe the behaviour it serves, each one named `revised`.
- A paragraph describing requirements the change retires, and no other, describes nothing the specification states any longer: drop it, or reword it around what stands, named or not. A section other than `## Overview` whose every paragraph describes retired requirements alone may be answered with no block; it then leaves the design.
- A paragraph that is neither kept verbatim nor named is refused, since a redraft that quietly loses a paragraph loses what the design said; so is a number named whose paragraph is kept verbatim, is a type block, or is no paragraph the section holds.
- Add the paragraphs the change calls for where they read best; a new paragraph is named nowhere.
- A type block is shown as its `Type:` line and is never named in `revised`. Where `domain-model` is listed, `## Type blocks` lists every key to reference exactly once: a kept type, whose role stands unless the signature the change redeclares changes what it stands for, and a new one the change's `type` claims declare. A type the change retired with the requirements that owned it is shown nowhere, and is left out.

The request ends with the requirements the change adds or revises, which `## Overview` and the informed sections describe as a draft would, and the requirements it retires, which nothing of the design describes any longer.

Worked example: a change carrying one `decision` claim, `Secrets live in the team vault (from brief)`, and a requirement `secrets.read` under a new stem informs `apis`. The request lists `## Overview`, two paragraphs, and `## APIs and integrations`, which the current design lacks. The answer keeps the two overview paragraphs verbatim and adds a third naming what `REQ-005` reads at use, with `"revised": []`; and drafts `apis` whole, one paragraph naming the vault as the secret store `(from brief)` beside the role it plays. `## Domain model` is not listed, so it is not answered, and the engine keeps it.

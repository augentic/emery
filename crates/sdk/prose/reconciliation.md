# From sources to a spec

How one `emery specify` run turns bound sources into a reviewable specification, and where an extract prompt's output lands in that pipeline.

## The pipeline

1. **Extract** — the engine dispatches one `extract` per authored source. Each call receives the whole bound source (a read-only workspace view, or an inline value) and returns one Evidence document: a flat list of typed claims, and nothing else. The kind of source (`intent`, `documentation`, `behaviour`) is not in the document — it is the adapter's, read from its `metadata` before any extract, so no answer can state or change it. There is no lead catalog; extraction mines the entire source in one pass, however the adapter's survey splits the calls.
2. **Gate** — the engine validates every claim against the closed required-extras table before anything else runs: a `requirement` claim must carry a `statement` extra, a `criterion` claim a `criterion` extra, an `example` claim a `replay-digest` extra. A claim missing its required extra fails the whole run closed (typed `bad_request`) naming the source, claim, and missing key. There is no partial acceptance and no fallback to `synopsis`.
3. **Group** — the engine decides which `requirement` claims across sources describe one requirement, and which of them agree. Byte-equal dotted-kebab `id`s are the baseline: they always merge into one requirement. Beyond the baseline, a run over two or more sources asks the model for one partition — claims into requirements, each requirement's claims into agreeing classes — with the sources' authority withheld, and refuses an answer that splits a baseline pair or leaves a claim unplaced. A run over one source takes the baseline alone (whitespace-equal statements agree). Then deterministic code ranks each requirement's classes by authority precedence: one class is `agreed`; a unique highest-authority class wins as `divergence` over the losers; a tie at the top authority is a `conflict`. The requirement's subject is the winning contributor's id; the other contributors' ids surface in the losers' notes. A requirement no `criterion` claim covers (an id equal to, or dot-extending, any contributor's id) is uncovered: `[unknown]` when otherwise agreed, and a rendered acceptance-gap note in every case.
4. **Synthesise** — each requirement's body is engine-rendered: the winning class's `statement`, verbatim, or nothing when the requirement is a `conflict` and no statement wins. The model answers two schema-gated drafts around it: the acceptance scenarios for every requirement, keyed by subject, and the paragraphs and `type` references for each section of the claim-derived design plan. Every run starts from its sources alone — nothing of a stored revision reaches the synthesis, and requirements number from `REQ-001` in source order. The engine checks each draft against its requirements and section plan, feeds findings back for bounded repair, and assembles the typed specification and design itself — every requirement id, heading, provenance pair, status, note, and signature is engine output; `emery show` projects them as `spec.md` and `design.md`.
5. **Commit** — the engine writes the revision atomically and swaps the current revision id; a re-run reports the diff against the revision it displaced, and reads nothing from it. Adapters never write artifacts; the returned Evidence is the entire contribution.

## What this means for extract prompts

- **Claim ids name the domain concept, and byte-equal ids guarantee a merge.** Derive ids from the behaviour the claim describes (`session.timeout`, `password-reset.expiry`), never from file layout, position, or invented counters. Two independent sources that mint the same id are merged without judgement; a source that names the same behaviour differently (`session-expiry`) leaves the merge to the engine's grouping judgement, which may or may not make it, and the id then reads as an alias in the rendered notes. A precise domain id is still the strongest signal you can give.
- **`requirement` claims are the grouping currency.** Only `kind: requirement` claims form spec requirement blocks and can agree, diverge, or conflict. Detail kinds (`section`, `excerpt`, `type`, `call`, …) reach synthesis as supporting context but never form requirements.
- **`criterion` ids must extend their requirement's id.** The acceptance-coverage rule keys on the prefix: a criterion for `session.timeout` must carry id `session.timeout` or `session.timeout.<suffix>`. A criterion with an unrelated id leaves its requirement uncovered.
- **Statements are what agreement is judged on, so quote precisely.** The `statement` extra is what the grouping judges same-or-different (byte-equal ids over one source compare it whitespace-normalised). Paraphrase drift between sources invites false disagreement; verbatim quoting where the source is prose, and precise present-tense observation where it is code, keeps agreement honest. The winning statement *is* the requirement's rendered body, and a losing statement is rendered verbatim in its `Note:` line — the model never rewrites either.
- **Gaps are preserved, never guessed.** When the source does not answer something, emit nothing for it. The engine renders missing coverage as `[unknown]`; a fabricated claim corrupts the spec silently, an absent one is surfaced to the reviewer.
- **Do not pre-resolve disagreement.** The kind of source is the adapter's compiled-in constant, declared in its metadata and never written in an answer; emit the claim the source supports. Precedence, winners, and `Status:` are engine-side; dropping a value another source will contradict destroys the audit trail.

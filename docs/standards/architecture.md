# Architecture

Workspace shape, crate dependency direction, the WASI carve-out, and the `.omnia/storage` layout boundary. Read this before adding a new crate or shifting where state lives.

## Workspace layout

Deployment crate (`name = "emery"`) at the repo root. The shipped binary ([`src/main.rs`](../../src/main.rs)) is one `omnia::runtime!` command-mode invocation over the cursor-bound backends, its plugin `locations:` list the path root and the `omnia.host` registry; the journey host ([`examples/runtime.rs`](../../examples/runtime.rs)) is a second block mirroring it path-only. [`src/lib.rs`](../../src/lib.rs) is wasm32-only — the engine guest, nothing native. The engine guest is embedded as static component bytes (`include_bytes!` over `$OUT_DIR/emery.cwasm`, produced by the root `build.rs` — a child wasm32 build into `target/wasm32-engine`, one directory shared by every outer feature set, profile, and lock revision rather than nested under the per-hash `OUT_DIR`, then in release builds an ahead-of-time wasmtime serialize so startup deserializes instead of JIT-compiling the engine; debug builds embed the raw component and JIT at startup; there is no placeholder fallback). Deployment policy is static and CWD-rooted: the invocation directory mounts read-only as the guest's `.` — nothing writes the working tree, the C3 least-authority posture (no ancestor walk — a verb run below the project root fails typed), the storage hosts bind the revision store to the durable omnia-filesystem store (compiled-in root `.omnia/storage`), and the `plugins:` block declares the source seam (`emery:adapter/source@0.1.0`) plus the caller's acquisition policy as a declarative `locations:` list (the `.` path root — preopen-aligned reads, fresh on every load, never cached — then, in the shipped binary, the `omnia.host` registry endpoint, likewise read fresh: the runtime declares no project cache). The shipped runtime embeds the engine only: a local `.wasm` adapter loads at run time through the `omnia:plugins/loader` capability, an exact package reference fetches from its registry, and bare names still dispatch only statically declared guests. Every invocation — help, version, and grammar rejections included — runs in the emery guest (the wasm32 arm of [`src/lib.rs`](../../src/lib.rs)) through the shared command grammar (`emery_cli`).

The authoritative leaf → root crate graph (with per-crate roles) lives in [AGENTS.md](../../AGENTS.md). Headline shape: `prose` (the embedded-corpus registry) and `source` (the `emery:adapter/source` contract, both sides) are the leaves; `adapter` is the guest-only SDK over them; `engine` owns the transport-neutral domain operations (`specify`, `show`, adapter resolution) and returns `omnia_guest::Error` from them; `cli` (`emery-cli`) is the command grammar over the engine — clap grammar, source carriers, per-output text render fns, hint table — driving omnia's command façade (`omnia_guest::api::command`) for dispatch, projection, and the exit map; the root package's `src/main.rs` owns native deployment policy (the one `omnia::runtime!` block) and `src/lib.rs` is the one provider on wasm32 (the component contract is the only production boundary). The journey's mock adapter is the root-package `adapter` example (`examples/adapter/lib.rs` plus its embedded `prose/`), the same `SourceAdapter` + `source!` anatomy as a first-party adapter. The `runtime` example stays on the root package because it embeds `$OUT_DIR/emery.cwasm`.

There is no lint engine or `Check` substrate. Repo consistency is the mdBook links gate (`make links`).

Evidence claim types live in `source` (the WIT-shaped DTOs, re-exported by the adapter SDK); the typed revision and its Markdown renderer live in `engine`. Neither depends on anything named lint.

### Engineering standards live in the adapters

There is no standards crate: engineering-standards rules (`UNI-*` and per-adapter overlays) are authored in `augentic/emery-adapters` and ship embedded in each target adapter's component, applied by its build review prompts. The "no lifecycle authority in review" rule is structural — no engine crate parses or resolves rules, so standards prose cannot reach slice or plan transitions.

Every crate uses the shared `[workspace.package]` (`edition = "2024"`, `rust-version = "1.98"`, MIT/Apache-2.0) and the shared `[workspace.lints]` block in the root `Cargo.toml` (clippy `all`/`cargo`/`nursery`/`pedantic` warned, plus a hand-picked `restriction` subset and a tightened rust lint set — `missing_debug_implementations`, `single_use_lifetimes`, `redundant_lifetimes`).

**Hard dependency rule:** `prose` and `source` are the leaves and depend on no other workspace crate; `adapter` depends on both and nothing else; no production crate depends on `adapter` (the root package links it as a dev-dependency for `examples/adapter` only). The engine reaches the contract and the corpus registry through the leaves, never through the SDK — before this split the engine guest linked the whole judgment SDK to reach the wire types. Adding a workspace dep to a leaf, or an `adapter` dep to `engine` or the root's production arms, re-introduces that coupling; do not. The command boundary is one-directional too: `cli → engine`, never the reverse, and `engine` carries no `clap`, `clap_complete`, or `toml` dependency and no terminal vocabulary (flag names, verbs, stdout, exit codes) in its types, docs, or error descriptions — omnia's `api::http` overlay must type-check over `emery_engine::specify::SpecifyInput` / `emery_engine::show::ShowInput` with no engine edits, and `cargo tree -p emery-engine -e normal --depth 1` stays free of the façade crates. Only the root's wasm32 arm and the root suites depend on `cli`.

**New workspace crates** are an exception, not the default. Capability doubles are not a local crate: the native suites take them from omnia's `omnia-test` (`guest::{Scripted, ScriptedLoader, Memory, Namespaced}`). No test-only package builds a component here; the wasm boundary is instantiated by `emery-adapters`' conformance rung and guarded in this repository by `make wasm`.

The `adapter` example (`examples/adapter/`) is the one mock source adapter: a `emery_adapter::SourceAdapter` implementor whose extract calls the host `Model` over its fixture tree (`examples/docs/`). The `runtime` example hosts it with the Cursor backend and a path-only plugin `locations:` list. It carries no production lifecycle authority and never enters the shipped guest. Do not add another mock adapter — extend this example.

## Deployment: the Wasm guest

The guest's provider is a bare unit at the composition root (`src/lib.rs`) carrying the engine's capabilities: the model (`omnia_guest::Model`, WASI-backed defaults), the `Source` capability (`emery_source::Source`), the storage pair (`omnia_guest::StateStore` / `BlobStore`, since design/portable-storage.md steps 1–2), whose wasm32 default bodies ride the `wasi:keyvalue` / `wasi:blobstore` imports, and the plugin loader (`omnia_guest::Plugins`, whose wasm32 default rides the `omnia:plugins/loader` import); the runtime binds those hosts to the durable `omnia-filesystem` store (compiled-in root `.omnia/storage`; the `hosts:` block of the `omnia::runtime!` invocation in `src/main.rs`), so the backing is deployment policy, never engine code — alternative bindings, project-id-keyed multi-project hosts included, are documented in [deployment profiles](../reference/deployment-profiles.md). Everything else is structural: paths are fixed constants relative to named preopens (the `.` project mount; `emery_engine::preopen_path` normalizes operator paths inside it), and adapter dispatch — `extract` and `metadata` — rides the `emery:adapter/source` WIT imports directly from the engine's cfg-gated dispatch functions (typed refusals on native, where no WIT import exists). The native provider was deleted at the Phase 3 spine cut; the product arc's native coverage is the root scenario rung (`tests/specify.rs`), while pure kernels test over scripted capabilities.

The root `emery` package carries the Omnia deployment unit under `src/`: the guest cdylib (the wasm32 arm of `src/lib.rs`, the `wasi:cli/run` exporter plus the bare model provider — there is no HTTP export; C3 is satisfied by binding no listener at all) and the shipped runtime (`src/main.rs` — one `omnia::runtime!` invocation embedding the engine bytes). Operations live in `engine` as `Handler<P, I>` fns (`specify`, `show`) over transport-neutral serde inputs (`SpecifyInput`, `ShowInput`; path plumbing in `emery_engine::preopen_path`). `emery_cli` owns the clap grammar, the source carriers, and the per-output render fns; `emery_cli::run` binds the caller's provider into a `Client` for one argv and drives omnia's `Command` projector over it. The WASI shim (`omnia_guest::command!(dispatch)`) constructs the provider, runs that grammar, and hands the `Response` to `omnia_guest::api::command::execute_wasi`. The routing design is documented in [handler-shape.md](handler-shape.md).

## Domain modules of note

- **`crates/engine/src/adapter.rs`** — source-adapter loading over the typed `AdapterRef`: reference parsing, the per-run `Loader` memo issuing the `omnia:plugins/loader` load request for local components and registry packages (over the provider's `Plugins` capability, threading the source's digest pin and registry override and returning the adapter id the `Source` capability addresses it by), and the adapter `emery-version` gate, dispatched directly over the provider's `Source` capability (the WIT `metadata` import on wasm32, a scripted mock natively).
- **Asking the model** — the engine owns no completion loop. Each of the three judgments is an `omnia_guest::model::Question<T>` (`grouping`, `spec-draft`, `design-draft`) put as a `Brief` (the private trait in `specify/brief.rs`): one struct per judgment (`GroupingBrief`, `SpecBrief`, `DesignBrief`) built from the run's facts, whose `NAME` names the question, whose `PROSE` is joined into the system prompt, whose `Display` is the user turn, whose `tighten` tightens `T`'s derived draft-2020-12 schema to the run (requirement subjects and exact counts for `SpecAnswer`, the plan's section kinds and the run's `type` keys for `DesignAnswer`, index bounds for `Grouping`), and whose `verify` is the acceptance gate, run over every candidate the backend proposes; the trait's provided `judge(model)` is the one place a `Question` is built and put: it consumes the brief and hands the accepted answer to the brief's `into_output`, which derives the judgment's `Output` (the requirement bases, a document) from the two together. A miss goes back as the correction (`## Previous answer (rejected)` / `## Findings`), written by omnia, and the backend asks again within its own round budget; the engine never sees the reply text. `From<model::Error>` does the exit map: a serde mismatch or spent rounds is `bad_request` carrying the last correction, a model failure `bad_gateway`. `tighten` steers only; every rule stays in `verify`.
- **`crates/engine/src/specify.rs`** — the `specify` handler: checks the source list, extracts, synthesises, and commits. Nothing of the stored revision is read into the run; the store observes the outgoing revision only for the re-mine diff and the id swap.
- **`crates/engine/src/specify/basis.rs`** — requirement identity and status. Every `requirement` claim is indexed in source order; a run over two or more sources asks the model for one `Grouping` — a partition into requirements, each partitioned into agreeing classes — with authority withheld, validated as a partition over the byte-equal-id baseline (a baseline pair split is a finding); a run over one source takes the baseline alone with no model turn. `derive` then sorts every class by authority and source order, sorts classes by their top contributor, and reads off each `Basis` — what `spec.md` renders a requirement from: the subject (the top contributor's id), `Status` (one class agreed; a unique top authority divergence; tied top authorities conflict; agreed-but-uncovered unknown), whether any `criterion` id equals or dot-extends a contributor id, and the classes themselves for the body (the winning statement) and the loser notes. The bases are numbered `REQ-001` onward in the order of each group's earliest claim, so the same sources in the same order number alike.
- **`crates/engine/src/specify/brief.rs`** — the `Brief` trait above, and the `Review` every `verify` records on — carrying the prose checks the document briefs share (no blank or reserved-opener paragraph, one-line scenario fields); `judge` alone turns its findings into the accept-or-reject verdict.
- **`crates/engine/src/specify/synthesis.rs`** — the synthesis entry (`synthesise`, over the extracts: `basis::derive(model, extracts)` for the requirement bases, then `SpecBrief::new(..).judge(model)`, then `DesignBrief::new(..).judge(model)`, returning the `Revision` the store commits) and the prompt's `ClaimsSection` the two document briefs share. One child per document, each carrying its typed answer and its brief, whose `into_output` places the accepted answer beside the engine's facts in the typed revision:
  - **`synthesis/spec.rs`** — `SpecBrief` (the extracts, the bases) renders its turn — every requirement with its facts — names the subjects and exact counts in the schema, and checks that the drafted subject set equals the listed set exactly once, a scenario per entry, and no reserved opener in the preamble. `SpecBrief::into_output` builds the `Spec` from the accepted `SpecAnswer` (preamble, one `{ subject, scenarios }` `Draft` per requirement, its scenarios already the specification's `Scenario` shape): every id, status, coverage flag, cited `(source, claim)` pair, body (the winning statement), and losing class is the engine's (`Basis::requirement`).
  - **`synthesis/design.rs`** — `DesignBrief` (the extracts, the `Spec`, and the private `Plan`: the section verdicts from the extracted claim kinds, the bound sources, the `type` keys) renders its turn (the specification rendered through `Display`), names the permitted section kinds and the run's `type` keys in the schema, and checks that the section set equals the plan's required set plus informed permitted ones, every `type` claim is referenced exactly once and only under `domain-model`, and every `(from <key>)` is bound. `DesignBrief::into_output` builds the `Design` from the accepted `DesignAnswer` (preamble, one `Section<Block>` per section over the draft's `Block::Text(text) | Type(key)`): the sections in vocabulary order, each `type` reference replaced by the design's `Type { key, signature }` carrying the claim's signature — the one place the draft's block shape and the design's differ.
- **`crates/engine/src/revision.rs`** — the typed revision and its projections: the `Document` trait each file of a revision meets — `FILE` (the store's name for it), the provided `from_json(bytes)` (the grammar stamp `EMERY` checked before the shape: `spec-outdated`, then `server_error` for bytes that are not JSON or a shape this engine did not write), `to_json()` (the JSON bytes the store hashes and writes) and `to_markdown(id)` (the Markdown projection: the `emery:` / `revision:` front matter, then the document's `Display`) — implemented by `Spec` (`spec.json`) and `Design` (`design.json`); `Revision { spec: Spec, design: Design }` with `read(id, spec, design)` (bytes that no longer hash to the id are refused as `server_error` before either document is read — the store is content-addressed, so a mismatch is corruption), `FILES` (every name a revision holds, in digest order), `files()` (each document's canonical bytes under its name) and `id()` (the digest of those files: the content id the store commits under); `RESERVED` lists the line openers no drafted paragraph may use. Nothing parses Markdown back: the store writes one serialisation of those files and reads them back through `Revision::read`. Which document `show` prints is the verb's own `Artifact` selector in `show.rs`, not the revision's concern.
  - **`revision/spec.rs`** — `Spec` (`emery`, preamble, requirements), `Requirement` (`ReqId`, subject, `Status`, coverage, cited `Cited { source, claim }` pairs, body paragraphs, `Loser` classes, `Scenario`s with `and` lines) and the `Display` that renders `### Requirement:` blocks in id order with their `ID:` / `Sources:` / `Status:` lines, `Note:` lines, and scenario bullets.
  - **`revision/design.rs`** — `Design` (preamble, sections), `Section<B = Block> { kind, blocks }` (the one section shape, over the design's blocks or a draft's), `Block::Text(text) | Type { key, signature }`, the closed `SectionKind` vocabulary (`Overview`, `Domain model`, `APIs and integrations`, `Technical logic`, `UI / layout`, `Observability`) in fixed order, and the `Display` that renders `## ` sections with fenced signatures; also home to the `(from <key>)` citation scanner the draft check reuses.
  - **`revision/diff.rs`** — the re-mine `Diff` between two revisions (`Diff::between(from, outgoing, incoming)`): `SpecDiff` matches requirements by `ReqId` — the position each run numbers in source order, so a requirement whose place moved reads as a change — naming each as an `Entry { id, subject }` and each change's differing `fields`; `DesignDiff` matches sections by `SectionKind`. Typed equality throughout, never a comparison of projections; reported once by `specify` and stored nowhere.
- **`crates/engine/src/store.rs`** — where revisions live, IO alone: `commit` observes the current id and outgoing revision once, writes the incoming documents under their content id, swaps the current id by compare-and-swap against the observed token, and prunes the outgoing blobs; `current` reads the current revision back through `Revision::read`. A bad outgoing revision suppresses only the advisory diff, never the swap.

  The revision's JSON and the projections' layout are frozen byte-for-byte by the root scenario fixtures (`tests/specify/*.json`, `tests/specify/*.md`).

The lenient v1 module trees (provenance, the task/decision/leads validators) were deleted at the Phase 3 spine cut and are documented at tag `v1`.

## Adapter component resolution

Resolution addresses adapters by adapter id (the WIT `metadata` export). A local component reference or an exact package reference loads through the deployment's `omnia:plugins/loader` capability once per adapter identity on every `specify` that names it: the host's acquirer reads a component file fresh (nothing is mirrored, so a deleted file refuses typed on the next run) or fetches a package from the source's `registry` override or the compiled-in default endpoint, verifies the source's optional sha256 pin before validation, validates the component against the declared source seam, and registers it — a component under its `source:<name>` adapter id, a package under the package reference itself. Bare names still dispatch only guests declared in the runtime invocation; anything else fails at dispatch. There is no sibling-checkout or build-tree probe. Storage locations are fixed key and container-name formulas — the same names resolve against whatever backing the deployment binds. A binding names the axis; a component bound on the wrong axis fails at dispatch — no deployed guest exports the requested `<axis>:<name>` id.

## WASI carve-outs

The two adapter validators — `contract` and `vectis` — are in-guest adapter library code compiled into each adapter's published component in `augentic/emery-adapters`. The carve-out discipline (leaner lint posture and minimal `[workspace.dependencies]`) lives in that repo's workspace. Crux shell presence and launcher-icon heuristics live in the vectis adapter's in-guest core: the host performs no plan-time shell detection, so this repo carries no shell-detect crate.

**Host runner invariant.** The host CLI dispatches no adapter-owned tool: adapter validation, scaffold, and rendering logic lives entirely in the adapters repo as in-guest library code. There is no declared-tool surface. No `emery-*` workspace crate may import adapter-specific validation, scaffold, or rendering logic.

## Layout boundary

`.omnia/storage` — the storage root compiled into `src/main.rs` — is framework-managed state every CLI verb writes through, and the engine's private `store` module is its one owner: the revision store (the revision's `spec.json` / `design.json` plus the current revision id) over the deployment's storage capabilities. Do not hard-code storage paths elsewhere; a new storage location lands on that owner. `spec.md` / `design.md` beside the code are not storage: they are `emery show` output the skill writes for review, and nothing reads them back.

## Toolchain

Rust stable per `rust-toolchain.toml` (channel `stable`, components `clippy`, `rust-src`, `rustfmt`). WASM targets pre-installed via `targets = ["aarch64-apple-darwin", "wasm32-wasip2", "x86_64-apple-darwin"]`.

`rustfmt.toml` uses unstable nightly features (`unstable_features = true`, `imports_granularity = "Module"`, `group_imports = "StdExternalCrate"`). Format with nightly:

```bash
cargo +nightly fmt --all
```

`make fmt` does this for you.

## Supply chain

`cargo-vet` and `cargo-deny` gate `make ci`; `cargo-audit`, `cargo-outdated`, and `cargo-udeps` are advisory tasks run on demand (`make audit` / `outdated` / `deps`). The vet task is check-only (`cargo vet --locked`) — regeneration is deliberately not part of the gate, since regenerating exemptions before checking would auto-exempt anything unaudited. When a new dependency lands:

1. Add it to `[workspace.dependencies]` in the root `Cargo.toml` with a major-version pin (e.g. `serde = { version = "1", features = ["derive"] }`). Per-crate `Cargo.toml` references it as `serde.workspace = true`.
2. Run `cargo vet regenerate imports`, `cargo vet regenerate exemptions`, and `cargo vet regenerate unpublished`; review the `supply-chain/` diff, then commit it.
3. Check `deny.toml` allows the dependency's licence. The current allowlist is in `deny.toml`; add a new SPDX id only after confirming compatibility with MIT-OR-Apache-2.0.

`clippy::multiple_crate_versions` is silenced workspace-wide (`Cargo.toml`'s `[workspace.lints.clippy]`); duplicate transitive versions are audited by hand via `cargo tree --duplicates` on each `cargo update`, not gated through a ratchet.

## Skill / CLI responsibility split

Every deterministic operation lives in this CLI: kebab-case validation, adapter resolution and loading, and schema validation. The surviving `/emery:specify` skill shells out for all of those.

The corollary: when a skill currently does something deterministic in prose (parsing YAML, validating shape, transitioning state), the right fix is to add a CLI verb here and have the skill call it. The wrong fix is to make the skill smarter.

[`AGENTS.md`](../../AGENTS.md) is the source of truth for vocabulary and the crate map.

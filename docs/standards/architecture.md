# Architecture

Workspace shape, crate dependency direction, the WASI carve-out, and the `.omnia/storage` layout boundary. Read this before adding a new crate or shifting where state lives.

## Workspace layout

Deployment crate (`name = "emery"`) at the repo root. The shipped binary ([`src/main.rs`](../../src/main.rs)) is one domain-free `omnia::runtime!` command-mode invocation over the cursor-bound backends — no hand-written `main`, no per-run deployment planning — whose `guests:` list is the one embedded engine (`guests: [{ path: env!("EMERY_GUEST") }]`, the guest named `emery` by the file's stem) and which declares no `registries`: which registry serves a package adapter is the project's `emery.toml` to say, and the engine names it on the load. [`src/lib.rs`](../../src/lib.rs) is wasm32-only — the engine guest, nothing native. The engine guest is embedded as static component bytes (the macro's `include_bytes!` over the path the root `build.rs` emits as `EMERY_GUEST` — a child wasm32 build into `target/engine`, one directory shared by every outer feature set, profile, and lock revision rather than nested under the per-hash `OUT_DIR`; the raw `emery.wasm` in a debug build, JIT-compiled at startup, and the precompiled `emery.cwasm` in a release build, compiled for the binary's own `TARGET` under `omnia::CompileOptions::default()` so the build shell's environment steers nothing — omnia loads either format; there is no placeholder fallback). Deployment policy is static and CWD-rooted: the invocation directory mounts read-only as the guest's `.` — nothing writes the working tree, the C3 least-authority posture (no ancestor walk — a verb run below the project root fails typed), the storage hosts bind the revision store to the durable omnia-filesystem store (compiled-in root `.omnia/storage`), and nothing declares the source interface (`emery:adapter/source@0.1.0`): omnia relays every import outside its own `wasi:` / `omnia:` namespaces to the guest exporting it, so the engine's import of the interface reaches whichever adapter the loader admitted. The read-only `.` mount is both the guest's data view and the one root a local component loads through: the loader reads the component through the mount at the project-relative path the reference names (the engine checks the path against its `.` preopen before the load), fresh on every run and never cached — a mount a guest could write is never a code root, so the loader refuses a path beneath a writable mount — and a package is likewise fetched fresh from the registry the load names, so the runtime keeps no project cache. Tracing is one level for the host console and every guest's `RUST_LOG` — command mode's `info` on a bare run, moved a step per `-v` / `-q` omnia's direct entry counts from argv, a process `RUST_LOG` kept when no flag is passed — so the engine's progress and an adapter's SDK progress reach stderr together, and the invocation declares no environment. The shipped runtime embeds the engine only, and every adapter reference goes through the `omnia:plugins/loader` capability at the location it names (`omnia_sdk::plugins::Location` — a path through the mount, a package at its registry, a declared name), under the guest name that location registers (`Location::name`): the deployment's grant bounds every load, so a local `.wasm` adapter loads through the read-only mount, an exact package reference from the registry the project's `[registries]` table routes it to, and a bare name is attested as a guest declared at boot — or refused typed, since the shipped runtime declares none. Every invocation — help, version, and grammar rejections included — runs in the emery guest (the wasm32 arm of [`src/lib.rs`](../../src/lib.rs)) through the shared command grammar (`emery_cli`).

The leaf → root crate graph, with per-crate roles: `prose` (the embedded prose corpus: the `prose!` list-and-embed macro over the documents beneath a `prose/` directory, the `Doc` lookups, and the `check` that holds a list to its tree and to the imports it may link) and `adapter` (the `emery:adapter` contract, both sides, one module per axis — today `emery_adapter::source`) are the leaves; `sdk` is the guest-only SDK over them and owns the one corpus every adapter shares — `crates/sdk/prose/` (`claims.md`, `reconciliation.md`), embedded as `emery_sdk::RUNTIME`, answered to `read_doc` beside an adapter's own table and passed to `emery_sdk::check` as the imports a link may name, so the guidance that describes the claim gate ships with the SDK that enforces it; `engine` owns the transport-neutral domain operations (`specify`, `show`, adapter resolution) and returns `omnia_sdk::Error` from them; `cli` (`emery-cli`) is the command grammar over the engine — clap grammar, source carriers, per-output text render fns, hint table — driving omnia's command façade (`omnia_sdk::api::command`) for dispatch, projection, and the exit map; the root package's `src/main.rs` owns native deployment policy (the one `omnia::runtime!` block) and `src/lib.rs` is the one provider on wasm32 (the component contract is the only production boundary). The journey's mock adapter is the root-package `adapter` example (`examples/adapter/lib.rs` plus its embedded `prose/`), the same anatomy as a first-party adapter: a kind, embedded docs, a survey, and a `wasm32`-only `Guest` impl over `emery_sdk::extract`. The shipped binary hosts it through `examples/emery.toml`; there is no separate journey host.

There is no lint engine or `Check` substrate. Developer Guide link integrity is the mdBook build (`mdbook build docs`, which runs `mdbook-linkcheck2`).

Evidence claim types live in the contract crate's `source` axis module (the WIT-shaped DTOs, re-exported by the SDK); the typed revision and its Markdown renderer live in `engine`. Neither depends on anything named lint.

Every crate uses the shared `[workspace.package]` (`edition = "2024"`, `rust-version = "1.98"`, MIT/Apache-2.0) and the shared `[workspace.lints]` block in the root `Cargo.toml` (clippy `all`/`cargo`/`nursery`/`pedantic` warned, plus a hand-picked `restriction` subset and a tightened rust lint set).

**Hard dependency rule:** `prose` and `adapter` are the leaves and depend on no other workspace crate; `sdk` depends on both and nothing else; no production crate depends on `sdk` (the root package links it as a dev-dependency for `examples/adapter` only). The engine reaches the contract and the embedded corpus through the leaves, never through the SDK — before this split the engine guest linked the whole judgment SDK to reach the WIT bindings types. Adding a workspace dep to a leaf, or an `sdk` dep to `engine` or the root's production arms, re-introduces that coupling; do not. A second adapter axis is a second module in `adapter` and a second role in `sdk`, never a crate of its own. The command boundary is one-directional too: `cli → engine`, never the reverse, and `engine` carries no `clap`, `clap_complete`, or `toml` dependency and no terminal vocabulary (flag names, verbs, stdout, exit codes) in its types, docs, or error descriptions — omnia's `api::http` overlay must type-check over `emery_engine::specify::SpecifyInput` / `emery_engine::show::ShowInput` with no engine edits, and `cargo tree -p emery-engine -e normal --depth 1` stays free of the façade crates. Only the root's wasm32 arm and the root suites depend on `cli`.

**New workspace crates** are an exception, not the default. Capability doubles are not a local crate: the native suites take them from omnia's `omnia-test` (`guest::{Scripted, ScriptedLoader, Memory, Namespaced}`). No test-only package builds a component here; the wasm boundary is instantiated by `emery-adapters`' conformance rung, and the root build script compiles the engine guest for `wasm32-wasip2` on every native build.

The `adapter` example (`examples/adapter/`) is the one mock source adapter: a guest of the `source-adapter` world whose `extract` hands its survey's seam to `emery_sdk::extract` over the host `Model` and its fixture tree (`examples/docs/`). The shipped binary hosts it: [`examples/emery.toml`](../../examples/emery.toml) names the built component by path, and the binary's `.` mount is the root it loads from. It carries no production lifecycle authority and never enters the shipped guest. Do not add another mock adapter — extend this example.

## Deployment: the Wasm guest

The guest's provider is a bare unit at the composition root (`src/lib.rs`) carrying the engine's capabilities: the model (`omnia_sdk::Model`, WASI-backed defaults), the `Source` capability (`emery_adapter::source::Source`), the storage pair (`omnia_sdk::StateStore` / `BlobStore`), whose wasm32 default bodies ride the `wasi:keyvalue` / `wasi:blobstore` imports, and the plugin loader (`omnia_sdk::Plugins`, whose wasm32 default rides the `omnia:plugins/loader` import); the runtime binds those hosts to the durable `omnia-filesystem` store (compiled-in root `.omnia/storage`; the `hosts:` block of the `omnia::runtime!` invocation in `src/main.rs`), so the backing is deployment policy, never engine code — alternative bindings, project-id-keyed multi-project hosts included, are documented in [deployment profiles](../reference/deployment-profiles.md). Everything else is structural: paths are fixed constants relative to named preopens (the `.` project mount; `emery_engine::preopen_path` normalizes operator paths inside it), and adapter dispatch — `extract` and `metadata` — rides the `emery:adapter/source` WIT imports directly from the engine's cfg-gated dispatch functions (typed refusals on native, where no WIT import exists). The product arc's native coverage is the root scenario rung (`tests/specify.rs`), while pure kernels test over scripted capabilities.

The root `emery` package carries the Omnia deployment unit under `src/`: the guest cdylib (the wasm32 arm of `src/lib.rs`, the `wasi:cli/run` exporter plus the bare model provider — there is no HTTP export; C3 is satisfied by binding no listener at all) and the shipped runtime (`src/main.rs` — one `omnia::runtime!` invocation embedding the engine bytes). Operations live in `engine` as `Handler<P, I>` fns (`specify`, `show`) over transport-neutral serde inputs (`SpecifyInput`, `ShowInput`; path plumbing in `emery_engine::preopen_path`). `emery_cli` owns the clap grammar, the source carriers, and the per-output render fns; `emery_cli::run` binds the caller's provider into a `Client` for one argv and drives omnia's `Command` projector over it. The WASI shim in `src/lib.rs` constructs the provider, runs that grammar, writes the `Response` channels, and exits through `wasi:cli/exit`. The routing design is documented in [handler-shape.md](handler-shape.md).

## Domain modules of note

- **`crates/engine/src/adapter.rs`** — source-adapter loading over the typed `AdapterRef`: reference parsing (the reference's Display keys the run's view of the adapter; `AdapterRef::name` is the kebab name a binding takes from it when a carrier gives none — a component's stem, refused typed when it is not kebab-case), `Registries` (the project's `[registries]` table over the engine's one first-party route, `emery` → `augentic.io`; a namespace nothing routes refuses the package before any load), and `adapter::load`, which brings every adapter a run's sources name into the run once each — one `omnia:plugins/loader` load request per distinct reference over the provider's `Plugins` capability, carrying the source's `digest` as its pin: a local component by path, a package by reference with the registry its namespace routes to named on the load, a bare name as a declared guest the loader attests or refuses; two references that would register under one name (two components sharing a file stem, two versions of one package), and a reference that would register under the engine's own (`emery_engine::ENGINE`, the bare name `emery` or a component of that stem, which the loader would attest in the adapter's place), are refused before any loads — and reads each adapter's `metadata` once under the identity the loader's handle returns (the path's file stem, the package reference without its version, the declared name), dispatched directly over the provider's `Source` capability (the WIT `metadata` import on wasm32, a scripted mock natively): the `emery-version` gate is put to it, and what each adapter `Loaded` as — that identity and the kind of source it declares — is returned keyed by reference, so every source's rank and dispatch identity are fixed before any extract and never read from a document.
- **Asking the model** — the engine owns no completion loop. Each of the four judgments is an `omnia_sdk::model::Question<T>` (`grouping`, `spec-draft`, `design-draft`, `slicing`) put as a `Brief` (the private trait in `specify/brief.rs`): one struct per judgment (`GroupingBrief`, `SpecBrief`, `DesignBrief`, `SliceBrief`) built from the run's facts, whose `NAME` names the question, whose `PROSE` is joined into the system prompt, whose `Display` is the user turn, whose `tighten` tightens `T`'s derived draft-2020-12 schema to the run (requirement subjects and exact counts for `SpecAnswer`, the outline's section kinds and the run's `type` keys for `DesignAnswer`, index bounds for `Grouping`, the run's requirement ids and type keys with the stem count as the slice ceiling for `SliceAnswer`), and whose `verify` is the acceptance gate, run over every candidate the backend proposes; the trait's provided `judge(model)` is the one place a `Question` is built and put: it consumes the brief and hands the accepted answer to the brief's `into_output`, which derives the judgment's `Output` (the requirement bases, a document) from the two together. A miss goes back as the correction (`## Previous answer (rejected)` / `## Findings`), written by omnia, and the backend asks again within its own round budget; the engine never sees the reply text. `From<model::Error>` does the exit map: a serde mismatch or spent rounds is `bad_request` carrying the last correction, a model failure `bad_gateway`. `tighten` steers only; every rule stays in `verify`.
- **`crates/engine/src/specify.rs`** — the `specify` handler: checks the source list, extracts, puts the grouping brief (`GroupingBrief::new(&extracts).derive(model)` for the requirement bases), then the three document briefs together from those bases — `SpecBrief::new(&extracts, &bases).judge(model)`, `DesignBrief::new(&extracts, &bases).judge(model)`, and `SliceBrief::new(&bases, design.types()).derive(model)` for the plan, joined by `future::try_join3`, so the design and the slicing wait on no drafted document — and commits the `Revision { spec, design, plan }`. Nothing of the stored revision is read into the run; the store observes the outgoing revision only for the re-mine diff and the id swap. The four briefs are one file each under `specify/`, named for what each produces — mirroring `revision/`, where `spec.rs`, `design.rs`, and `plan.rs` are the documents these briefs draft:
  - **`specify/brief.rs`** — the `Brief` trait above; the `Review` every `verify` records on — carrying the prose checks the document briefs share (no blank or reserved-opener paragraph, one-line scenario fields), whose findings `judge` alone turns into the accept-or-reject verdict; and the prompt sections the document briefs share — `ClaimsSection`, which the specification and design briefs open their turn with, and `BasesSection`, the requirement outline every base carries (id, subject, status, sources, coverage, each contributor's statement and role) that all three close on.
  - **`specify/basis.rs`** — requirement identity and status. `GroupingBrief` indexes every `requirement` claim in source order; a run in which no source contributes one is refused `bad_request` before any turn; when the claims come from two or more sources its `derive` asks the model for one `Grouping` — a partition into requirements, each partitioned into agreeing classes — with authority withheld, validated as a partition over the byte-equal-id baseline (a baseline pair split is a finding); a run over one contributing source takes the baseline alone with no model turn. Either way it then sorts every class by authority and source order, sorts classes by their top contributor, and reads off each `Basis` — what `spec.md` renders a requirement from: the subject (the top contributor's id), `Status` (one class agreed; a unique top authority divergence; tied top authorities conflict; agreed-but-uncovered unknown), whether any `criterion` id equals or dot-extends a contributor id, and the classes themselves for the body (the winning statement) and the loser notes. The bases are numbered `REQ-001` onward in the order of each group's earliest claim, so the same sources in the same order number alike.
  - **`specify/spec.rs`** — `SpecBrief` (the extracts, the bases) renders its turn — every requirement with its facts — names the subjects and exact counts in the schema, and checks that the drafted subject set equals the listed set exactly once, a scenario per entry, and no reserved opener in the preamble. `SpecBrief::into_output` builds the `Spec` from the accepted `SpecAnswer` (preamble, one `{ subject, scenarios }` `Draft` per requirement, its scenarios already the specification's `Scenario` shape): every id, status, coverage flag, cited `(source, claim)` pair, body (the winning statement), and losing class is the engine's (`Basis::requirement`).
  - **`specify/design.rs`** — `DesignBrief` (the extracts, the bases, and the private `Outline`: the section verdicts from the extracted claim kinds, the bound sources, the `type` keys) renders its turn (the requirement outline from the bases, drafted beside it rather than read from a drafted `Spec`), names the permitted section kinds and the run's `type` keys in the schema, and checks that the section set equals the outline's required set plus informed permitted ones, every `type` claim is referenced exactly once and only under `domain-model`, and every `(from <key>)` is bound. `DesignBrief::into_output` builds the `Design` from the accepted `DesignAnswer` (preamble, one `Section<Block>` per section over the draft's `Block::Text(text) | Type(key)`): the sections in vocabulary order, each `type` reference replaced by the design's `Type { key, signature }` carrying the claim's signature — the one place the draft's block shape and the design's differ.
  - **`specify/plan.rs`** — `SliceBrief` (the bases, the type keys the design brief offers — `DesignBrief::types()`, in key order, every one of which an accepted design references exactly once — and the stems: the first segment of each requirement subject's dotted id, with the `ReqId`s under it in first-appearance order) renders its turn (the stems as the baseline, the type keys, then the requirement outline from the bases), names the run's requirement ids and type keys in the schema with the stem count as the slice ceiling, and checks that every requirement is in exactly one slice, no stem is split across slices, every slice has a kebab-case name unique in the plan and at least one requirement, every type key is owned by exactly one slice and every owned key is a type, and every `depends-on` names another slice without a cycle (Kahn's elimination, naming what it cannot order); the preamble and every brief pass the shared paragraph checks. A specification under one stem is one slice named for it, owning every type, with no turn spent (`SliceBrief::derive`). `SliceBrief::into_output` builds the `Plan` from the accepted `SliceAnswer` (preamble, one `{ name, requirements, types, depends-on, brief }` `Draft` per slice): the drafts numbered `SLICE-001` onward by each one's lowest requirement, every `requirements` list in id order, `types` in key order, and `depends-on` resolved from names to `SliceId`s in id order.
- **`crates/engine/src/revision.rs`** — the typed revision and its projections: the `Document` trait each file of a revision meets — `NAME` (`spec` / `design` / `plan`), the provided `from_json(bytes)` (the grammar stamp `EMERY` checked before the shape: `spec-outdated`, then `server_error` for bytes that are not JSON or a shape this engine did not write), `to_json()` (the JSON bytes the store hashes and writes) and `to_markdown(id)` (the Markdown projection: the `emery:` / `revision:` front matter, then the document's `Display`) — implemented by `Spec` (`spec`), `Design` (`design`), and `Plan` (`plan`); `Revision { spec: Spec, design: Design, plan: Plan }` with `read(id, spec, design, plan)` (bytes that no longer hash to the id are refused as `server_error` before any document is read — the store is content-addressed, so a mismatch is corruption) and `id()` (the digest of those three documents' canonical bytes, spec, design, then plan: the content id the store commits under); `RESERVED` lists the line openers no drafted paragraph may use. Nothing parses Markdown back: the store writes one serialisation of those files and reads them back through `Revision::read`. Which document `show` prints is the verb's own `Artifact` selector in `show.rs`, not the revision's concern.
  - **`revision/id.rs`** — the numbered identifiers, `ReqId` (`REQ-NNN`) and `SliceId` (`SLICE-NNN`), one private `numbered!` macro over a `u32` behind a prefix: rendered padded to three digits, parsed only from that rendering, stored as the string.
  - **`revision/spec.rs`** — `Spec` (`emery`, preamble, requirements), `Requirement` (`ReqId`, subject, `Status`, coverage, cited `Cited { source, claim }` pairs, body paragraphs, `Loser` classes, `Scenario`s with `and` lines) and the `Display` that renders `### Requirement:` blocks in id order with their `ID:` / `Sources:` / `Status:` lines, `Note:` lines, and scenario bullets.
  - **`revision/design.rs`** — `Design` (preamble, sections), `Section<B = Block> { kind, blocks }` (the one section shape, over the design's blocks or a draft's), `Block::Text(text) | Type { key, signature }`, the closed `SectionKind` vocabulary (`Overview`, `Domain model`, `APIs and integrations`, `Technical logic`, `UI / layout`, `Observability`) in fixed order, and the `Display` that renders `## ` sections with fenced signatures; also home to the `(from <key>)` citation scanner the draft check reuses.
  - **`revision/plan.rs`** — `Plan` (`emery`, preamble, slices), `Slice` (`SliceId`, name, `ReqId`s, owned type keys, `depends_on` `SliceId`s, brief paragraphs) and the `Display` that renders `## Slice:` blocks in id order with their `ID:` / `Requirements:` lines, a `Types:` line and a `Depends on:` line where the lists are not empty, and the brief's paragraphs.
  - **`revision/diff.rs`** — the re-mine `Diff` between two revisions (`Diff::between(from, outgoing, incoming)`): `SpecDiff` matches requirements by `ReqId` — the position each run numbers in source order, so a requirement whose place moved reads as a change — naming each as an `Entry { id, subject }` and each change's differing `fields`; `DesignDiff` matches sections by `SectionKind`; `PlanDiff` matches slices by `SliceId` — numbered by lowest requirement, so a merge that swallows a stem renumbers the slices after it as changes — naming each as a `SliceEntry { id, name }`; `Changed<E>` is the one changed-record shape over either entry; each diff flags whether its document's `preamble` changed. Typed equality throughout, never a comparison of projections; reported once by `specify` and stored nowhere.
- **`crates/engine/src/store.rs`** — where revisions live, IO alone: `commit` observes the current id and outgoing revision once, writes the incoming documents under their content id, swaps the current id by compare-and-swap against the observed token, and prunes the outgoing blobs; `current` reads the current revision back through `Revision::read`. A bad outgoing revision suppresses only the advisory diff, never the swap.

  The revision's JSON and the projections' layout are frozen byte-for-byte by the root scenario fixtures (`tests/specify/*.json`, `tests/specify/*.md`).

## Adapter component resolution

Resolution addresses adapters by the guest name a reference's location registers (`omnia_sdk::plugins::Location::name` — a bare name itself, a package its reference without the version, a component its file's stem), which is the identity the loader's handle returns; the engine derives no guest name of its own. Every reference loads through the deployment's `omnia:plugins/loader` capability at the location it names (`omnia_sdk::plugins::Location`), once per distinct reference on every `specify` that names it, and the deployment's grant bounds every load: a local component loads by its project-relative path (`Location::Path`), which the loader reads through the deployment's read-only `.` mount fresh on every run (nothing is mirrored, so a deleted file refuses typed on the next run; the engine checks the path against its preopen before asking, and a path at no file is `not_found`) and registers under the file's stem; a package loads by its exact reference (`Location::Registry`), fetched from the registry the project's `[registries]` table routes its namespace to — `augentic.io` for `emery` unless a line re-routes it — which the engine names on the load, since the shipped runtime routes nothing itself (a namespace no line routes is `bad_request` before any load), and registers under the reference without its version (`emery:intent@1.0.0` is the guest `emery:intent`), so a run holds one version of a package; a bare name loads as a guest declared at boot (`Location::Declared`): the loader attests one the deployment declares and refuses any other, typed, before a dispatch is attempted. The source's `digest` rides the load as its pin, and the loader holds the resolved bytes to it — a mismatch, or bytes that are not a raw wasm component, refuse typed before wasmtime sees them; the handle's digest is what the bytes hashed to. Two references that name one guest — two files with one stem, two versions of one package — are refused by the engine before either loads, as is a reference that names the engine's own guest (`emery_engine::ENGINE`): the engine is declared at boot as `emery`, so the engine refuses the bare name and a component of that stem alike, where the loader would otherwise attest the engine itself in the adapter's place. There is no sibling-checkout or build-tree probe. Storage locations are fixed key and container-name formulas — the same names resolve against whatever backing the deployment binds. A component that does not export the source interface fails at dispatch — no deployed guest under that id exports it.

## Adapter logic stays in the adapters

The engine dispatches no adapter-owned tool: extraction behaviour and prose live in each adapter's published component in `augentic/emery-adapters`, as in-guest library code. No `emery-*` workspace crate may import adapter-specific logic.

## Layout boundary

`.omnia/storage` — the storage root compiled into `src/main.rs` — is framework-managed state every CLI verb writes through, and the engine's private `store` module is its one owner: the revision store (the revision's `spec.json` / `design.json` / `plan.json` plus the current revision id) over the deployment's storage capabilities. Do not hard-code storage paths elsewhere; a new storage location lands on that owner. `spec.md` / `design.md` / `plan.md` beside the code are not storage: they are `emery show` output the skill writes for review, and nothing reads them back.

## Toolchain

Rust stable per `rust-toolchain.toml` (channel `stable`, components `clippy`, `rust-src`, `rustfmt`, target `wasm32-wasip2`).

`rustfmt.toml` uses unstable nightly features (`unstable_features = true`, `imports_granularity = "Module"`, `group_imports = "StdExternalCrate"`). Format with nightly:

```bash
cargo +nightly fmt --all
```

`make fmt` does this for you.

## Supply chain

`cargo-vet` and `cargo-deny` gate `make ci`; `cargo-audit`, `cargo-outdated`, and `cargo-udeps` are advisory tasks run on demand (`make audit` / `outdated` / `deps`). The vet task is check-only (`cargo vet --locked`) — regeneration is deliberately not part of the gate, since regenerating exemptions before checking would auto-exempt anything unaudited. When a new dependency lands:

1. Add it to `[workspace.dependencies]` in the root `Cargo.toml` with a major-version pin (e.g. `serde = { version = "1", features = ["derive"] }`). Per-crate `Cargo.toml` references it as `serde.workspace = true`.
2. Run `cargo vet regenerate imports`, `cargo vet regenerate exemptions`, and `cargo vet regenerate unpublished`; review the `supply-chain/` diff, then commit it.
3. Check `deny.toml` allows the dependency's licence. The current allowlist is in `deny.toml`; add a new SPDX id only after confirming compatibility with MIT-OR-Apache-2.0.

`clippy::multiple_crate_versions` is silenced workspace-wide (`Cargo.toml`'s `[workspace.lints.clippy]`); duplicate transitive versions are audited by hand via `cargo tree --duplicates` on each `cargo update`, not gated through a ratchet.

## Skill / CLI responsibility split

Every deterministic operation lives in this CLI: kebab-case validation, adapter resolution and loading, and schema validation. The surviving `/emery:specify` skill shells out for all of those.

The corollary: when a skill currently does something deterministic in prose (parsing YAML, validating shape, transitioning state), the right fix is to add a CLI verb here and have the skill call it. The wrong fix is to make the skill smarter.

[`AGENTS.md`](../../AGENTS.md) carries the vocabulary and the short repository map; this document is the authoritative crate graph.

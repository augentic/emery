# Emery — Agent Instructions

A Rust workspace producing the `emery` binary. `emery specify <adapter>... [--description <adapter>=<text>] [--config [<path>]]` extracts typed claims from source adapters, derives requirements under authority rank (each source's configured `rank` or its kind's default), synthesises a specification and a design, slices the specification into a build plan, and commits the three as one content-addressed revision; `emery build [<adapter>] [--config [<path>]] [--jobs <N>]` builds the current plan in waves through one target adapter — every slice whose dependencies are merged at once, each in a working copy cut from the wave's head, sealed as one commit and merged in id order under the adapter's merge rules, a path the rules leave conflicted resolved with the model and merged in its place, the wave verified by the adapter and labelled `emery/<revision>` — resuming a label the repository already holds; `emery show <spec|design|plan>` prints a Markdown projection of the current revision; `emery completions <shell>` is derived from the clap surface. `plugins/emery/` is the Cursor plugin carrying the `/emery:specify` and `/emery:build` skill wrappers, the latter relaying the label a build set. First-party adapters live in [`augentic/emery-adapters`](https://github.com/augentic/emery-adapters). The v1 implementation is archived at git tag `v1`.

## Git

Never `git commit`, `git push`, open or close a pull request, or delete a branch — in this repository or in any sibling checkout — unless the maintainer lifts this for the session, explicitly and for named work. Leave every change uncommitted in the working tree; the maintainer reviews and commits. No plan or to-do list carries a commit, push, or PR step, and an instruction to complete every step does not override this.

## Vocabulary

- **source adapter** — a WebAssembly component exporting the WIT `source-adapter` world (`metadata` + `extract`): given a `SourceInput` (a name and a workspace or inline value) it returns an `Evidence` document of typed claims. See [wit/emery.wit](wit/emery.wit).
- **target adapter** — a WebAssembly component exporting the WIT `target-adapter` world (`metadata` + `run`): given the writable project tree and a `task` — `init`, `build(slice)`, or `verify` — it answers the `outcome` of that kind: `initialised` once it has scaffolded the files of its layout the tree lacks; `built(report)`, the requirement ids it covered and the files it wrote, for a `slice` (its plan entry, the specification cut to its requirements, the whole design) built into the tree; `verified(verdict)` for the integrated tree checked and repaired. Same WIT package, second world.
- **engine** — this product: the engine guest and the crates behind it.
- **capability** — an engine-side trait a provider carries: `Model`, `Source`, `Target`, `Plugins`, `StateStore`, `BlobStore`, `Vcs`, and `Files`, the one the engine answers itself in the guest through the `.` preopen: `read` is what a commit would carry at a path beneath a working copy — a file's bytes, or the target a symbolic link names, never followed — for the secret gate, refusing a path that holds neither rather than reading it as empty; `list` is the entries of a directory beneath one, each its name and whether it is a file, a directory, or a link, for what stands at a conflicted path; `write` puts a file's bytes at a path beneath one, making the directories on the way and following no symbolic link, for the `.gitignore` of a repository the engine creates when the adapter's layout scaffolded none and the resolutions of a slice's merge conflicts.
- **contract** — a typed agreement: WIT, CLI grammar, JSON envelope.
- **plugin** — the adapter noun in omnia's loader vocabulary. Not to be confused with the Cursor plugin under `plugins/emery/`, which the `emery` CLI never sees.

When authoritative inputs are incomplete, preserve the gap as `[unknown]` rather than guessing.

## Invariants

- Failures are `omnia_sdk::Error`, built with `bad_request!` and siblings. Explicit variants only for the recovery codes `specify-source-required`, `build-target-required`, `adapter-reference`, `unsupported-version`, `spec-not-generated`, `spec-outdated`, `repository-required`, `base-not-sealed`, `revision-not-found`, `merge-unresolved`, `verify-failed`, `secret-detected`. `anyhow::Context` carries the unclassified tail to `server_error`. Production code never panics — a guest panic is a trap with no envelope. Exit codes are omnia's 1:1 map (`Error::exit_code`: `bad_request` 1, `not_found` 2, `server_error` 3, `bad_gateway` 4; clap usage errors exit 64 with no envelope).
- The model never authors a document. Synthesis is typed `Question`s put as briefs (`crates/engine/src/specify/{basis,spec,design,plan}.rs`, and `build/merge.rs` for a merge's resolution, all over `brief.rs`) and verified against engine facts; the stored revision is the truth and Markdown is a `Display` projection. The specification is drafted per stem group: `SpecBrief::chunked` cuts the bases into chunks of at most `SPEC_CHUNK` (25) requirements — a stem past the cap split, smaller stems merged up to it — one `spec-draft` turn each beside the design turn, the first chunk alone carrying the preamble, and `SpecBrief::assemble` orders the one `Spec` by `ReqId`. A requirement's trigger is code's, never the model's: the SDK's survey derives it — a route, or a message — from the registration the recogniser read and carries it in a `contract` claim, the engine binds it at the grouping by id prefix, else by anchor, and no drafting turn is asked for one. The trigger variant is closed and spells only what a recogniser derives and a target reads: a case is added for a surface kind code can read at a registration, never for one the model would name. The specification is behaviour by role and the design holds the technology: one `Lexicon` — the fixed names and the packages the run's `call` claims spell — gates every turn that authors specification text, the survey's stems and the extraction's ids and statements in the SDK, the spec-draft's preamble and scenario lines in the engine, each hit a correction finding rather than a refusal; a `call` or `excerpt` carries the technology to the design from a behaviour source, a `decision` from a prose source, and a `decision` informs `## APIs and integrations` as `call` and `contract` do, so the section is required wherever a prose source prescribes a technology. The design turn labels every `type` block with its `Role` — `data`, a shape the program reads, stores, or produces, or `mechanism`, a class of the source's own machinery (a client, a retriever, a bootstrap, a settings carrier) — stored in `Block::Type { key, signature, role }` and rendered `Type: <key>` or `Type: <key> (mechanism)`; the slicing turn follows the design, since `SliceBrief::new` takes `Design::data_types()`, so the model is offered the data keys alone and a mechanism type is owned by no slice. The plan's floor is the stem — the first segment of a requirement subject's dotted id: requirements sharing one are one slice at the least, the model may merge stems and never splits one, each data type key is owned by exactly one slice (the one whose requirements read or produce it, `slicing.md` says, whatever module declared it), the requirements reached through one trigger are one slice whatever their stems, since one trigger is one handler, and a specification under one stem is one slice with no turn spent. `slicing.md` also states the pipeline rule: where a stem's sub-stems are an entry and the stages it runs, the entry's slice depends on every stage slice and is built last, its brief naming the stage functions it composes. Nothing parses Markdown back, and nothing of a stored revision reaches a run. A revision-shape change re-ids every revision and changes the JSON fixtures under `tests/specify/`; a projection change touches only the `.md` fixtures; a prompt change (`crates/engine/prose/`) touches none.
- The mount and the store follow W^X: what a run can write it never loads code from. The invocation directory is the one mount, `.`, writable — the tree `specify` lends its source adapters, the repository `build` starts from, `.emery/storage` and `.emery/vcs` beneath it — and the package store `~/.emery/adapters` is no mount at all: the host's loader reads it, no guest reaches it, and it lies apart from any project, so a component is never loaded from a tree a run can write; omnia refuses a store beneath a writable mount at assembly, so running `emery` from `$HOME` is refused at startup. The model's worker is bounded the same way: every `cursor-sdk-bridge` the shipped runtime spawns for a lent tree runs inside the kernel boundary omnia-cursor sets up — it reads the system, the lent tree, its own scratch `HOME` and `TMPDIR`, and the `~/` roots the turn's worker grant names, writes the tree and the scratch alone, and reaches the network through a loopback `CONNECT` proxy bound for it alone and the grant's hosts (Cursor's own go through the backend's relay), nothing of the operator's environment carried in but the grant's variables — and the grant is the target adapter's `metadata().grants` (one `target::Grant { egress, read, env }` per program the prompts run and the grant their union; none by default and for every source adapter), which the SDK puts with every build and verify turn, the host holds to its shape, and the backend applies as this machine allows (a root the home lacks granted nothing, a grant over a lend under no shell root or an entry the backend refuses `invalid-request`), so the adapter trusted by its digest spells its toolchain's reach and no environment variable widens every adapter's; and the shell runs on the two roots compiled into `deployment.rs`, `.emery/vcs/worktrees` and `.emery/vcs/integration`, so a build's turn can run the tree's own install and tests while a source adapter's lend stays read-only. Every repository and working copy a run names is a deployment-local path beneath that mount (`.`, `./.emery/vcs/repos/<key>` for a source's clone, `./.emery/vcs/repos/<name>` for the target's, `./.emery/vcs/sources/<name>`, `./.emery/vcs/integration`), which the `omnia:vcs` host resolves before git sees it: no guest holds a host path, a credential, or a git process. A build lends its integration working copy, never the checkout, and the mount beneath it is writable `.emery/` included: the revision store fails closed on a document rewritten beneath it rather than preventing the write. `SKIP_DIRS` names `.emery` and `.git`, so `beneath` refuses a claim or a write under either, and `workspace::list` skips a `.git` file as it does the directory, since a linked working copy's root holds one.
- An adapter is an exact package reference, `namespace:name@version` (`AdapterRef`), and nothing else: no default namespace, no latest, no path, no bare name — anything else is `bad_request` with code `adapter-reference` before any load. Every reference goes through the `omnia:plugins/loader` capability at its registry location (`Location::Registry { endpoint: None }`), under the guest name that location registers (`Location::name`: the reference without its version, so `emery:intent@1.0.0` is `emery:intent`), and the deployment's grant bounds every load: the loader reads the release from the package store first — the file `namespace_name@version.wasm` under `~/.emery/adapters`, read fresh on every run, whoever wrote it (the fetcher, an operator's `cp`, `wkg get -o`), final until removed — and, when the store lacks it, fetches it from the registry the deployment routes its namespace to (`emery` to `augentic.io`, compiled in; nothing else routed, and `~/.emery/wasm-pkg.toml` unread), hashes it to the registry's digest, writes it to the store, and loads it; a release the store lacks under a namespace nothing routes is the loader's `refused` before any fetch, naming the namespace and the file the store holds no copy of, hinted `wkg get <reference> -o ~/.emery/adapters/`; a registry that cannot supply it is `unavailable`. The engine names no registry on a load, so a project file, which a build can rewrite, chooses which package and, through `digest`, which bytes, and never where from. A `[[source]] digest` or `[target] digest` rides the load as its pin and the loader holds the bytes that answered — stored or fetched — to it. One reference pinned to two digests, and two versions of one package in one run (one guest), are refused before any load. The only pre-compiled artifact is the engine compiled into the binary; adapters are always raw wasm — the loader admits a package as raw wasm alone, so a `.cwasm` in the store or at the registry is refused typed however it hashes. A loaded handle is held to its axis before any dispatch (`Axis::require` over its exports): a source adapter under `build`, or a target under `specify`, is `bad_request` naming the interface it lacks.
- `build` lands as commits in one repository, never in the checkout. The revision is read, and `spec-not-generated` / `spec-outdated` raised, before the target loads; the `[target] name` — kebab-case, the adapter's package name when the config gives none, as on the command line — is held before anything is read; the repository and its base are settled after the load, by the `[target] repository` alone, since the adapter declares no base: with a `repository` URL, the build lands in the clone under `.emery/vcs/repos/<name>`, cloned on the first run and fetched on every one after, from the default branch as the origin holds it, `origin/HEAD` (`revision-not-found` for a URL naming no repository or one with no default branch; `bad_gateway` for a remote that refuses); with `repository = "."` (`vcs::PROJECT`), in the project checkout from its head, which must be a repository (`repository-required`) whose `pending(".")` minus paths under `SKIP_DIRS` is empty and which has a commit (`base-not-sealed`, the paths listed); with none, as a run naming its adapter on the command line has, in a repository the engine creates at `.emery/vcs/repos/<name>` and keeps — `init`, the adapter's `Task::Init` run over it to scaffold its layout (`initialise`, the scaffolded paths held to the secret gate), a `.gitignore` holding `.emery/` written through `Files` when the layout scaffolded none, sealed as the root commit `Initialise`, which is the base; a later run finds it and starts from its head, and one left initialised and unsealed is initialised and sealed now — so the project directory is never read as a repository. The engine never initialises the project directory: a root commit sealed there would carry `.emery/storage`. A directory under `repos/<name>` belongs to whatever first cloned or created it: the engine never re-points it, so a run naming a URL over a created one, which has no `origin` to fetch, is `revision-not-found`, and one naming another URL over a clone fetches the first origin; the hint says to remove the directory or rename the target. A build resumes: the label `emery/<full revision id>` the repository already holds is read back as a local branch alone (`labelled`) — a tag, a remote's branch, or a commit of that spelling is never it, and a fetch writes no local branch, so whoever can write local branches in the repository a build reads is the operator, the party that already writes `.emery/storage` and the store — and only where it descends from the base (`descends`): a label the branches lack, or one off the base, is a fresh build from the base, and one over the base is resumed from wherever it stands. Its chain is read through `log` from the label to the base, first-parent, and every entry whose `Message` parses under this revision's `Revision:` trailer names a slice that is not built again (`resumed`); an entry without a `Slice:` trailer, or under another revision, is passed over, and a chain naming no slice is still resumed from, every slice built over the labelled head. From the labelled head, or the base, the engine cuts `./.emery/vcs/integration` on no branch. A copy an earlier run left is read before it goes: when its head descends from the head the run starts at and every commit between them along the first parent is a `Message` of this revision — a run that ended after a wave's slices merged and before the wave was verified leaves exactly that — the slices they name are staged: listed as `resumed` beside the label's, not built again, counted merged in the wave they are ready in, and verified there, the copy cut again at its own head so the merges stay and what the failed verification left uncommitted goes; a copy on the head, off it, holding another revision's slice, or sealing none is removed and the copy cut again at the head. The staged slices reach the model only as the tree their merges left, never as a brief, so a repeated resume seals nothing twice. A fresh build over a base the engine did not create then has the adapter initialise the tree: `Task::Init` over the integration copy, the adapter scaffolding the files of its layout the tree lacks and leaving a held one as it stands, with no model turn, so a resumed build or a later run scaffolds nothing twice, and an adapter that scaffolds a whole tree — a layout, a manifest, the tooling beside them — scaffolds it into an empty clone and leaves a held project's files standing, which is why no base is refused for what it holds; what it left pending is held to the secret gate (`secret-detected`, nothing sealed) and sealed as `Initialise` on the integration copy, the commit every slice builds over, reported as `BuildOutput.initialised: Option<Initialised { commit, paths }>` — `None` when the layout added nothing, so nothing is sealed — and a build resumed from a label, or from staged slices, reads and initialises nothing, since the run that set them admitted the base and scaffolded the layout. The engine then runs the plan in waves: `Plan::ready(merged)` is every unmerged slice whose `depends_on` are merged, in id order (so a slice waiting on nothing is in the first wave whatever its id; none ready with slices left is a stored cycle, `server_error` naming them); every slice of a wave is built at once, up to `jobs` concurrently, each in `./.emery/vcs/worktrees/<id>` cut at the wave's head and handed the slice's plan entry, `Spec::cut` to its requirements, the whole design, the head as its `base`, that copy, and the requirements, owned types, and brief typed beside the renderings, so an adapter reads a scenario or a type's signature without parsing the Markdown back; the model never sees the plan whole, and the cap bounds concurrency alone, so a cap of one yields the same history as a wide run. A build that fails upstream (`bad_gateway`), or one the model backend's time budget ended before it answered (a `bad_request` whose description says `budget exhausted` and `timed out`, the one refusal read for its words), is put once more in a fresh copy cut at the same head, the first removed; the second failure is the run's. An adapter's own code may scaffold files into the copy before the turn, from the typed slice, and name them to the turn through `BuildContext::scaffold`, so the model fills what code scaffolded rather than writing it; the engine sees only the change set. The model writes the copy through the SDK's `write_files` tool, in a list or a map of files, with a `delete` list beside it, and the SDK's turn holds the report to the tree before it answers: a `written` path the tree does not hold is a correction, so a build that wrote nothing cannot report files, and a file written and left out is added to the report. A `Report` the gate refuses is the adapter's defect, `server_error` naming every finding; a requirement left out of `covered` is reported `uncovered`, never invented. Once the wave is built, each slice that built is integrated in id order, whatever order the builds finished in, and before a slice whose build failed ends the run, so the slices built beside it stay merged in the integration copy for the next run to stage: its copy is first held to the head it was cut at (`head`), since the model's shell reaches the repository and a commit it sealed or moved there would leave `pending` empty and the slice merged as nothing, so a copy that moved is `server_error` naming both commits, nothing of it sealed; then what it changed — the copy's `pending`, which is the slice's `written`, whatever the report listed, and which holds what the shell wrote as it holds what `write_files` wrote — is held to the secret gate: every non-deleted path read through `Files` as a commit would carry it — a file's bytes, or a symbolic link's target, so a link the shell planted whose target spells a token is caught as a file holding it would be, and a path that is neither, or cannot be read, ends the run `server_error` rather than passing — a credential carrier by name or by content `bad_request` with code `secret-detected` listing each `<path>: <what>`, nothing of the change set sealed and the copy left as it was written; what passes is one commit in its copy — `<id> <name>` over `Slice:`, `Revision:`, `Requirements:`, `Covered:`, `Adapter:`, `Base:`, `Wave:` trailers — or none when it changed nothing, merged into the integration copy as a merge commit under the same message and the adapter's `merge_rules` (`union`, `ours`, `theirs` by path glob; a path only one side changed since the base takes that side), and the copy removed. A merge that conflicts at a path no rule resolves is not made yet: both sides of each such path are read from the two working copies through `Files` before any turn — a path the engine never writes, one the slice removed or the integrated tree does not hold as a regular file, a symbolic link or a directory at it, or a file that is not text is `bad_request` with code `merge-unresolved`, the paths and the reason named, since the model is handed text and a commit stores a link's target — and put to the model in one `merge-<slice>` turn with the slice's plan entry and the entries of the wave's slices merged before it that wrote the path, steered to those paths alone and held to one whole file apiece, free of conflict markers and not empty, a resolution refused within the available rounds `merge-unresolved` naming the findings; the resolutions are written into the slice's working copy through `Files::write`, which follows no symbolic link, held to the secret gate as the build's change set was (`secret-detected`, the copy left as written), sealed there over the slice's commit as `<id> <name> resolved at <paths>` — nothing sealed where the resolution kept the slice's own side — and the slice is merged again with each resolved path taken from the slice whole ahead of the rules, so the slice lands as one merge commit in its wave and the paths are reported as `resolved`; a merge still conflicted after that is `server_error`. A wave that integrated any slice, a commit merged or nothing to merge, is verified: one `Target::verify` over the integration copy, lent writable with `write_files` and `edit_files`, runs the checks, repairs what they find, runs them again, and answers a `Verdict` — a dispatch that fails upstream, or that the backend's time budget ended, is put once more over the same copy, since nothing is sealed until the verdict and a repair the first left stands, the second failure the run's — gated by `Verdict::findings` (`server_error` as a bad report is), `passed: false` `bad_request` with code `verify-failed` listing the failures; `passed` holds what the repairs and checks left pending to the same secret gate (`secret-detected` at the wave, the slices merged in it staying committed and the wave's commit never made) and seals it as `Wave <k> verified`, reports the seal with its paths under `sealed`, lists the wave in `repaired` when a sealed path is one no `ours` rule covers (a lockfile a check regenerated under one is no repair), and labels the head `emery/<full revision id>` in the repository the base came from, so the label always stands at a verified tree and the next wave is cut from it. Once every slice is merged, the copy is removed; nothing is pushed, so the label stands in the project checkout, the clone, or the repository the engine created for the operator to read or push. The first failure ends the run as the adapter put it — class and code kept; a slice's failure names the slice, its wave, and the slices merged before it, those built beside it in its wave included, as staying committed in the integration copy; a wave's names the wave, the slices merged in it, and where the label stands — the integration copy, and a failed wave's slice copies, staying for inspection, the slice copies until the next build removes them and the integration copy until the next build has read the merges it holds; the engine writes no state of its own for a build: the labelled history and the merges the integration copy holds over it are the output and what a run resumes from, and `BuildOutput` is the run's report alone. A repository source under `specify` is the same clone, keyed by its URL normalised (scheme and host case, a trailing `/` or `.git`, the `git@host:path` form), read in `./.emery/vcs/sources/<name>` at its `revision` and removed once the source answered, success or failure.
- Deleted verbs and flags are deleted from the grammar, not aliased. Pre-1.0, a major bump means regenerating with a fresh `emery specify`.
- Engine state is written only through the storage capabilities. Never hand-edit `.emery/storage`. `spec.md` / `design.md` / `plan.md` beside code are `emery show` output, never sources.

## Code style

clippy (`make lint`) and nightly rustfmt (`make fmt`) are the style gate; beyond them and the rules below, match the surrounding code.

- Suppress a lint with `#[expect(lint, reason = "…")]` at the smallest scope, never `#[allow]`.
- `<module>.rs` plus `<module>/<child>.rs`; `mod.rs` only under `tests/support/`.
- A fn over a type is that type's method, not a free fn taking it as its first argument, where the type's module declares the fn or the fn is a plain lookup or predicate on the type. A constructor is an associated fn. A policy `const` sits beside the type whose method reads it. Values several fns thread through every call become one struct whose methods they are. A fn stays free when it is pure over primitives and iterators, or when it is one module's rule applied to another module's type.

Comments follow the conventions `std`, `serde`, and `tokio` converge on: docs state the observable contract for the crate's user, never the body's mechanics.

- `///` goes on the public API only — the `pub` types, fns, fields, variants, and re-exports a user of the crate can reach — never on a private or `pub(crate)` item, an `impl` block, or a trait-impl method. A clap field's `///` is its `--help` text. A doc opens with one summary sentence (about fifteen words, full stop), then a blank line, then short sentences and bullet lists. `# Examples` holds compiled doctests, for non-obvious usage only; `# Errors` names each class the caller matches on, linked; `# Panics` the rest. Every item mentioned is an intra-doc link. No mechanics, history, or migration notes. A `//!` says what a module is for, in the same shape.
- A private item takes a `//` only for what a senior developer would not see from its name and signature: a constraint, a why, an invariant. Most carry nothing. No restatements, match-arm labels, or body paraphrases.
- Inside a body, a `//` is a section header: lowercase, no full stop, above a blank-line-separated block, naming what the block achieves, so the headers read together outline the fn. A fn readable at a glance carries none, and a header never narrates the line beneath it. The one in-body explanation is `// HACK: …`, for a trick a senior would not see through.
- A test fn takes `//`, never `///`, and only for rationale its scenario name and assertions do not expose.
- No commented-out code.
- Every sentence earns its place and reads once: short plain sentences, one idea each; three or more things are a bullet list, not a colon-and-dash clause; no chained em-dashes, nested parentheticals, or semicolon runs; each fact has one home across `//!`, `///`, and `//`. A comment is as long as its why takes and no longer — concise is not dense, and readable is not verbose.

## Testing

Tests drive the public boundary: a behaviour is asserted through what a user of the product or crate can reach, over scripted doubles rather than the operator's filesystem, a network, or a live model, never through private internals. A suite below the root survives only for an independent library contract; a unit test only for a branch no public boundary reaches. A test fn names the scenario (`gen_spec`, `no_sources`), never the outcome. Scripted doubles are strict: script exactly the exchanges a run consumes.

Root-led, on two rungs. Every CLI-reachable behaviour of the engine lives in `tests/` and drives `emery_cli::run` in-process over scripted capabilities (`tests/support/`), asserting the exit code, the envelope, scripted storage, and the version-control calls the scripted `Vcs` recorded — the locations, the order, the commit messages — never the operator's filesystem; the `Provider`'s `Plugins` is a constant, so nothing of a load is asserted there. The adapter boundary — the store, the fetch, the pin, the loader's refusals, and a real component extracting and building — and the repository boundary — what a build commits and labels, the repository it clones or creates to hold them, what a dirty checkout refuses, what a repository source is lent — are asserted in `tests/runtime.rs` under the real runtime, in a deployment the suite owns (`omnia_test::host::Deployment` over the engine guest `build.rs` names, linking the hosts the engine imports, `WasiVcs` over `omnia_git::Client`), over scratch roots, a scratch wasm-pkg `local` registry, in-memory backends, repositories created with a hermetic git that is also the oracle, and the mocks `build.rs` names, with a strict scripted model; no scripted double stands for a plugin or a version-control capability there, and the binary's `main.rs` is reached by no test. Crate suites survive only for independent library contracts (`sdk`, `prose`); unit tests only for CLI-unreachable branches.

## Commands

All from the repository root through `make` ([`Makefile`](Makefile) → mise). The tasks are the shared `mise/rust.toml` of [`augentic/toolkit`](https://github.com/augentic/toolkit), pinned in [`mise.toml`](mise.toml) to the tag every `uses:` under `.github/workflows/` names; bump both in one pull request when the pin moves.

```bash
make ci # exactly the CI jobs: fmt-check + lint + test + test-docs + docs + vet + deny — run before handing over
make check # local advisories: audit + fmt (rewrites) + lint + outdated + deps
make test # cargo nextest run --locked --workspace --all-features, under -Dwarnings
make lint # lint-host (cargo clippy --workspace --all-targets --all-features, then cargo hack --each-feature), then lint-wasm (the same over every lib, bin and example for wasm32-wasip2 — never tests)
make fmt # cargo +nightly fmt --all
make vet-regen # regenerate cargo-vet imports/exemptions/unpublished, then vet
make cov # cargo llvm-cov nextest --workspace --all-features --summary-only
make sweep # drop target/ artifacts untouched for a week
```

If `make ci` cannot run, say exactly why and which checks ran instead.

`mdbook build docs` builds the CLI reference and checks its links. The live journey (`cargo run -- specify --config examples/emery.toml`, then `cargo run -- build --config examples/emery.toml`, over the two mock components copied into the store `~/.emery/adapters` under references of their own) is in [examples/README.md](examples/README.md). The skill preview is `cursor-agent --plugin-dir plugins/emery` over a `cargo install --path . --locked` binary; reinstall when the CLI changes.

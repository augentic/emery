# Emery — Agent Instructions

A Rust workspace producing the `emery` binary. Verbs:

- `emery specify <adapter>... [--description <adapter>=<text>] [--config [<path>]] [--apply] [--fresh]` — extracts typed claims from source adapters, derives requirements under authority rank (a source's configured `rank` or its kind's default), synthesises a specification and a design, slices the specification into a build plan, and stages the three as one content-addressed candidate; `--apply` seals in the same run.
- `emery apply [--config [<path>]] [--repository <url|.>]` — seals the staged item (a revision candidate or an amendment) as the current revision in the target's repository, under `spec/` at one commit labelled `emery/<id>`, clearing the slot.
- `emery build [<adapter>] [--config [<path>]] [--jobs <N>]` — builds the current plan in waves through one target adapter, resuming a label the repository already holds.
- `emery show <spec|design|plan|amendment> [--staged] [--config [<path>]]` — a Markdown projection of the current revision, the staged candidate, or the staged amendment.
- `emery amend <adapter>... [--description <adapter>=<text>] [--config [<path>]] [--apply]` — extracts the change sources, matches their claims against the current revision, and stages an `Amendment` for `show amendment` and `apply`.
- `emery completions <shell>` — derived from the clap surface.

`plugins/emery/` is the Cursor plugin: `/emery:specify` re-projects the candidate through `show --staged` and offers the seal, `/emery:amend` relays the amendment's counts and offers `show amendment` and the seal, `/emery:apply` relays the commit, label, and parent, `/emery:build` relays the label. First-party adapters live in [`augentic/emery-adapters`](https://github.com/augentic/emery-adapters). The v1 implementation is archived at git tag `v1`.

## Git

Never `git commit`, `git push`, open or close a pull request, or delete a branch — in this repository or in any sibling checkout — unless the maintainer lifts this for the session, explicitly and for named work. Leave every change uncommitted in the working tree; the maintainer reviews and commits. No plan or to-do list carries a commit, push, or PR step, and an instruction to complete every step does not override this.

## Vocabulary

- **source adapter** — a WebAssembly component exporting the WIT `source-adapter` world (`metadata` + `extract`): a `SourceInput` (a name and a workspace or inline value) in, an `Evidence` document of typed claims out. See [wit/emery.wit](wit/emery.wit).
- **target adapter** — a component exporting the `target-adapter` world (`metadata` + `run`): given the writable project tree and a `task` — `init`, `build(slice)`, or `verify` — it answers the `outcome` of that kind: `initialised` (the files of its layout the tree lacked scaffolded), `built(report)` (the requirement ids covered and the files written), `verified(verdict)` (the integrated tree checked and repaired).
- **engine** — this product: the engine guest and the crates behind it.
- **capability** — an engine-side trait a provider carries: `Model`, `Source`, `Target`, `Plugins`, `StateStore`, `BlobStore`, `Vcs`, and `Files`. The engine answers `Files` itself in the guest through the `.` preopen: `read` is what a commit would carry at a path beneath a working copy (a file's bytes, or a symbolic link's target, never followed; a path holding neither refused), `list` a directory's entries with each one's kind, `write` puts bytes beneath a working copy, making directories and following no link. Used for the secret gate, conflicted merge paths, the three documents under `spec/`, the engine's `.gitignore`, and merge resolutions.
- **contract** — a typed agreement: WIT, CLI grammar, JSON envelope.
- **plugin** — the adapter noun in omnia's loader vocabulary, not the Cursor plugin under `plugins/emery/`, which the CLI never sees.

When authoritative inputs are incomplete, preserve the gap as `[unknown]` rather than guessing.

The current revision lives in the target's repository under `spec/{spec,design,plan}.json` at the commit labelled `emery/<id>` (`store::label`); `REVISION_KEY` (`current-revision`) is a pointer to the label, a cache the repository bears out or not. `current(provider, &BuildRepo) -> Standing { head, current: Option<Current { id, revision: Result<Revision, Error>, commit, parent }>, behind }` reads the `head`, then the label the pointer names where `labelled` finds it and `descends(head, label)` holds (cutting `vcs::REVISION` there, reading the three documents through `Files`, `Revision::identify` held to the label's id — `spec-mismatch` on a miss or a `spec/` that is not exactly the three files), else the head's tree, else none; a label behind the head is `behind`; `revision` is a `Result` so an outdated grammar is still a parent to seal over while `show` and `build` raise it, and `parent` is read off the spec's own top-level key. At a head no label names, three documents that read as no revision were `edited or merged by hand` (the phrase the CLI's hint reads) → `spec-mismatch`; three that each read but fail `Revision::findings` (one side's `spec.json` beside the other's `design.json` and `plan.json`) the same, the description naming the breaks; documents reading as one revision are that revision whatever label stands (a clone reads no remote's label, an operator may delete a merged one), which is the two-branch reading: two checkouts whose pointers name labels a merge left behind both read the kept side from the head's tree, and an amendment prepared there seals over the merge commit under the kept revision as parent. `Standing::no_lineage` is the `lineage-exists` refusal where `current.parent` is `Some`. `Sealing` is one seal — the `Revision`, its `parent`, the commit `over`, an `Option<Summary>` for the message: `Sealing::candidate` (parent the current id, over its commit; `lineage-exists` where the current has a parent), `Sealing::fresh` (no parent, over `standing.head`, every earlier label standing), `Sealing::amendment` (its three documents, parent `base.revision`, over `base.commit`; `amendment-stale`, `bad_request`, where `standing.current` is not that revision at that commit). `commit(provider, &repo, Sealing, Standing) -> Sealed` cuts `REVISION` at `over`, else the head, else creates the created kind (`BuildRepo::init`, the seal its root commit; a project with no commit `base-not-sealed`), refuses a `spec/` holding anything but the three documents (`spec-mismatch`), writes them, puts `pending` to the secret gate, seals under a `RevisionMessage`, labels `emery/<id>`, swaps the pointer, and clears the staged item; a revision the repository already holds seals nothing; the base's label stands. `Standing::diff` is the advisory diff against a readable current. Refusal helpers: `not_generated` (`spec-not-generated`, naming a repository with no commit, a label behind its head, and a staged candidate or amendment where each stands), `target_required(verb)`, `nothing_staged` / `no_amendment_staged`, `amendment_pending(id)`. **Verbs.** `apply(ApplyInput { target }, ctx)` settles the `BuildRepo`, reads `current`, and seals through `seal(provider, &repo, standing)` (`nothing_staged` on none; `fresh` for a candidate marked fresh, `candidate` otherwise, `amendment` for a staged amendment) → `ApplyOutput { revision, parent, commit, label, repository, kind, amendment, diff }`. `specify` holds the sources to `Bound::all`, refuses `amendment-pending` and `lineage-exists` (unless `SpecifyInput.fresh`, which stages the candidate marked fresh) before any load, settles `target: Option<TargetRef>` and reads `current` where one is named (a run naming none reads no repository and answers no `diff`; `build-target-required` for `apply` with none), extracts through `Bound::extract_all(provider, &bound) -> Extracted { extracts, repositories }` (shared with `amend`), stages, and under `apply` seals through `apply::seal` after the stage lands, so a refused seal leaves the candidate staged. `show` reads the candidate under `ShowInput.staged` (`amendment-pending` over a staged amendment), else the current revision from `target`'s repository, and for `Artifact::Amendment` the staged amendment alone, `staged` and `target` unread. **Amend** (`amend.rs`; `amend/{standing,change,plan}.rs`; `specify/design/amend.rs`; `specify/plan/amend.rs`). `amend(AmendInput { sources, target, apply })` refuses a source named `BASELINE` (`specify::BASELINE`, `baseline`, the reserved name the current requirements enter the grouping under), settles the target, reads `current` (`spec-not-generated` with none), refuses a staged candidate (`no_candidate`, `amendment-pending`), each before any load, and extracts. Where the change states a behaviour (`ChangeSet::states`: any `requirement` or `retire` claim) it groups; a change of `decision` / `type` / `call` / `excerpt` alone spends no grouping or draft, every standing requirement `Unchanged`, the design turn alone deciding the stage. Either way `ChangeSet::retire_by_scope` reads each `Extract` with `Scope::Whole`: a behaviour source read whole covers the stems of its `requirement` ids, and every standing requirement under one left `Unchanged` with no change claim joined is `Retired` with `scope` naming the source; a prose source read whole retires nothing. ## Invariants

- Failures are `omnia_sdk::Error`, built with `bad_request!` and siblings. Explicit variants only for the recovery codes `specify-source-required`, `build-target-required`, `adapter-reference`, `unsupported-version`, `spec-not-generated`, `nothing-staged`, `amendment-pending`, `amendment-stale`, `lineage-exists`, `retire-unmatched`, `spec-outdated`, `spec-mismatch`, `repository-required`, `base-not-sealed`, `revision-not-found`, `merge-unresolved`, `verify-failed`, `secret-detected`, `spec-rewritten`. `anyhow::Context` carries the unclassified tail to `server_error`. Production code never panics — a guest panic is a trap with no envelope. Exit codes are omnia's 1:1 map (`Error::exit_code`: `bad_request` 1, `not_found` 2, `server_error` 3, `bad_gateway` 4; clap usage errors exit 64 with no envelope).
- The model never authors a document. Synthesis is typed `Question`s put as briefs (`crates/engine/src/specify/{basis,spec,design,plan}.rs`, `build/merge.rs`, all over `brief.rs`) and verified against engine facts; the stored revision is the truth and Markdown is a `Display` projection; nothing parses Markdown back, and nothing of a stored revision reaches a run. The specification is drafted per stem group: `SpecBrief::chunked` cuts the bases into chunks of at most `SPEC_CHUNK` requirements (a stem past the cap split, smaller stems merged up to it), one `spec-draft` turn each beside the design turn, the first chunk alone carrying the preamble, `SpecBrief::assemble` ordering the one `Spec` by `ReqId`; an amend drafts the added, changed, and conflicting bases alone under the ids the change set assigned and keeps the base's preamble and unchanged requirements byte for byte. A requirement the base holds in conflict is one standing requirement listing the competing statements; a claim matched to it resolves the conflict as `Changed` under the status the change sources alone settle; a conflict among change sources seals marked `[conflict]` as a specify's does, `apply` refusing nothing for it, since the next change is where the operator reconciles it. The amended design is drafted the same way (`DesignAmend`, one turn only where the change informs a section or a paragraph cites a retired requirement, over `## Overview` and the informed sections alone), so what the change does not touch is byte for byte the base's and a reworded paragraph is the model's declared choice, never a silent loss.
- A requirement's trigger is code's, never the model's: the SDK's survey derives it from the registration the recogniser read and carries it in a `contract` claim, the engine binds it at the grouping by id prefix, else by anchor, and no drafting turn is asked for one. The trigger variant is closed and spells only what a recogniser derives and a target reads.
- The specification is behaviour by role and the design holds the technology: one `Lexicon` — the fixed names and the packages the run's `call` claims spell — gates every turn that authors specification text (the survey's stems and the extraction's ids and statements in the SDK, the spec-draft's preamble and scenario lines in the engine), each hit a correction finding rather than a refusal; a `call` or `excerpt` carries the technology to the design from a behaviour source, a `decision` from a prose source, and a `decision` informs `## APIs and integrations` as `call` and `contract` do, so the section is required wherever a prose source prescribes a technology. The design turn labels every `type` block with its `Role` — `data` (a shape the program reads, stores, or produces) or `mechanism` (a class of the source's own machinery: a client, a retriever, a bootstrap, a settings carrier) — stored in `Block::Type { key, signature, role }` and rendered `Type: <key>` or `Type: <key> (mechanism)`; `SliceBrief::new` takes `Design::data_types()`, so a mechanism type is owned by no slice.
- The plan's floor is the stem, the first segment of a requirement subject's dotted id: requirements sharing one are one slice at the least, the model may merge stems and never splits one, each data type key is owned by exactly one slice (the one whose requirements read or produce it, whatever module declared it), the requirements reached through one trigger are one slice whatever their stems, and a specification under one stem is one slice with no turn spent. `slicing.md` also states the pipeline rule: where a stem's sub-stems are an entry and the stages it runs, the entry's slice depends on every stage slice and is built last, its brief naming the stage functions it composes. A stem of more than `SLICE_CAP` requirements is floored at its sub-stems instead (the first two segments, decided by code): the gate refuses a sub-stem split across slices, admits the stem split along them, and refuses the stem cut finer than the cap asks (two of its slices that would together fit within `SLICE_CAP`, the smallest pair named, a pair a third slice stands between in `depends-on` set aside since merging it would close a cycle), so a stem is cut at as few sub-stem boundaries as the cap allows; no slice-size ceiling is enforced. An amended plan is the base's by code where a rule decides (ids, names, and briefs kept; a retired requirement leaves its slice; one restated under another stem moves to its new stem's slice; an added one joins the slice its trigger reaches or its stem's; an emptied slice goes and its dependants take its dependencies; an unowned data type goes to the one touched slice where nothing else is open), and one slicing turn over the current slices as fixed context decides the rest, held to the open set and the same gate; a change adding only under stems the plan holds spends no slicing turn.
- Each document carries `emery`, the grammar stamp (`revision::EMERY`, 8), and `parent: Option<String>`, the revision it amends by id, always serialised so the id covers it and `None` from `specify`; the projection renders neither. A revision-shape change re-ids every revision and changes the JSON fixtures under `tests/specify/` and `tests/build/`; a projection change touches only the `.md` fixtures; a prompt change (`crates/engine/prose/`) touches none.
- The mount and the store follow W^X: what a run can write it never loads code from. The invocation directory is the one mount, `.`, writable (`.emery/storage` and `.emery/vcs` beneath it), and the package store `~/.emery/adapters` is no mount: the host's loader reads it, no guest reaches it, and omnia refuses a store beneath a writable mount at assembly, so running `emery` from `$HOME` is refused at startup. The model's worker is bounded the same way: every `cursor-sdk-bridge` the shipped runtime spawns for a lent tree runs inside the kernel boundary omnia-cursor sets up — it reads the system, the lent tree, its own scratch `HOME` and `TMPDIR`, and the `~/` roots the turn's worker grant names, writes the tree and the scratch alone, and reaches the network through a loopback `CONNECT` proxy bound for it alone and the grant's hosts (Cursor's own go through the backend's relay), nothing of the operator's environment carried in but the grant's variables — and the grant is the target adapter's `metadata().grants` (none by default and for every source adapter), which the SDK puts with every build and verify turn, the host holds to its shape, and the backend applies as this machine allows (a root the home lacks granted nothing; a grant over a lend under no shell root or an entry the backend refuses `invalid-request`), so the adapter trusted by its digest spells its toolchain's reach and no environment variable widens every adapter's; the shell runs on the two roots compiled into `deployment.rs`, so a build's turn can run the tree's own install and tests while a source adapter's lend stays read-only. Every repository and working copy a run names is a deployment-local path beneath the mount (`.`, `./.emery/vcs/repos/<key>` for a source's clone, `./.emery/vcs/repos/<name>` for the target's, `./.emery/vcs/sources/<name>`, `./.emery/vcs/integration`), which the `omnia:vcs` host resolves before git sees it: no guest holds a host path, a credential, or a git process. A build lends its integration working copy, never the checkout, and the mount beneath it is writable `.emery/` included: the revision store fails closed on a document rewritten beneath it rather than preventing the write, and `spec/` in the target repository is held to its label's id the same way (`spec-mismatch`). `SKIP_DIRS` names `.emery` and `.git`, so `beneath` refuses a claim or a write under either, and `workspace::list` skips a `.git` file as it does the directory, since a linked working copy's root holds one. `SPECIFICATION` names `spec` (`vcs::SPECIFICATION` re-exports it): `beneath` refuses a path led by it, so no claim anchors there and no build turn writes there, and `workspace::list` prunes the root-level entry alone; `vcs::project_base`'s cleanliness exception reads `SKIP_DIRS` alone, so a pending `spec/` in the project checkout is the operator's to seal.
- An adapter is an exact package reference, `namespace:name@version` (`AdapterRef`), and nothing else — no default namespace, no latest, no path, no bare name (`adapter-reference` before any load). Every reference goes through the `omnia:plugins/loader` capability at its registry location (`Location::Registry { endpoint: None }`), under the guest name that location registers (`Location::name`, the reference without its version), and the deployment's grant bounds every load: the loader reads the release from the package store first (the file `namespace_name@version.wasm` under `~/.emery/adapters`, read fresh on every run, whoever wrote it, final until removed) and, when the store lacks it, fetches it from the registry the deployment routes its namespace to (`emery` to `augentic.io`, compiled in; nothing else routed, `~/.emery/wasm-pkg.toml` unread), hashes it to the registry's digest, writes it to the store, and loads it; a release the store lacks under a namespace nothing routes is the loader's `refused` before any fetch, hinted `wkg get <reference> -o ~/.emery/adapters/`; a registry that cannot supply it is `unavailable`. The engine names no registry on a load, so a project file, which a build can rewrite, chooses which package and, through `digest`, which bytes, and never where from. A `[[source]] digest` or `[target] digest` rides the load as its pin and the loader holds the bytes that answered, stored or fetched, to it. One reference pinned to two digests, and two versions of one package in one run, are refused before any load. The only pre-compiled artifact is the engine compiled into the binary; the loader admits a package as raw wasm alone, so a `.cwasm` in the store or at the registry is refused however it hashes. A loaded handle is held to its axis before any dispatch (`Axis::require`): a source adapter under `build`, or a target under `specify`, is `bad_request` naming the interface it lacks.
- `build` lands as commits in one repository, never in the checkout, and the specification lives in the same repository: `apply` seals the staged item's three documents under `spec/` as one commit `Revision <id>` over the repository's head (or the current revision's commit), labelled `emery/<id>`, the checkout never touched, and `.emery/storage` keeps only the staged item and the `current-revision` pointer, a cache the repository bears out — a verb reads the revision at the label the pointer names where that label stands over the head, else from the head's own tree (a label merged into the branch), and a label the head moved on without is `spec-not-generated` naming it, the way out a merge or rebase, or `specify --apply` sealing a fresh revision over the head. The `[target] name` and `repository` settle the repository before anything is read; `build` reads the current revision from it, never the staged candidate, and raises `spec-not-generated` / `spec-outdated` / `spec-mismatch` before the target loads; its base is settled after the load, since the adapter declares no base. With a `repository` URL the build lands in the clone under `.emery/vcs/repos/<name>`, cloned on the first run and fetched on every one after, from `origin/HEAD` (`revision-not-found` for a URL naming no repository or one with no default branch; `bad_gateway` for a remote that refuses); with `repository = "."` in the project checkout from its head, which must be a repository (`repository-required`) whose `pending(".")` minus `SKIP_DIRS` paths is empty and which has a commit (`base-not-sealed`, the paths listed); with none, as a run naming its adapter on the command line has, in a repository `apply` created at `.emery/vcs/repos/<name>` and the engine keeps — `init` at the first seal, the `Revision <id>` commit its root and the base, the build never creating one (`spec-not-generated` for a repository no `apply` created) — so the project directory is never read as a repository, and the engine never initialises it (a root commit sealed there would carry `.emery/storage`). A directory under `repos/<name>` belongs to whatever first cloned or created it: the engine never re-points it, so a run naming a URL over a created one is `revision-not-found` and one naming another URL over a clone fetches the first origin; the hint says to remove the directory or rename the target. A build resumes from the label `emery/<full revision id>` read back as a local branch alone (a tag, a remote's branch, or a commit of that spelling is never it, and a fetch writes no local branch, so whoever writes local branches there is the operator, who already writes `.emery/storage` and the store) and only where it descends from the base; a chain naming no slice is still resumed from; the staged slices of an earlier run's integration copy reach the model only as the tree their merges left, never as a brief, so a repeated resume seals nothing twice. An adapter that scaffolds a whole tree at `Task::Init` scaffolds it into an empty clone and leaves a held project's files standing, which is why no base is refused for what it holds. A slice is handed the requirements, owned types, and brief typed beside the renderings, so an adapter reads a scenario or a signature without parsing Markdown back; the model never sees the plan whole, and `jobs` bounds concurrency alone, so a cap of one yields the same history as a wide run. An adapter's own code may scaffold files into the copy before the turn and name them through `BuildContext::scaffold`; the engine sees only the change set. The merge turn is handed text alone, since a commit stores a link's target; the label always stands at a verified tree; nothing is pushed, so the label stands in the project checkout, the clone, or the created repository for the operator to read or push. The first failure ends the run as the adapter put it, class and code kept; the integration copy and a failed wave's slice copies stay for inspection (the slice copies until the next build removes them, the integration copy until the next build has read its merges); the engine writes no state of its own for a build: the labelled history and the integration copy's merges are the output and what a run resumes from, and `BuildOutput` is the run's report alone. A repository source under `specify` is the same clone, keyed by its URL normalised (scheme and host case, a trailing `/` or `.git`, the `git@host:path` form), read at its `revision` and removed once the source answered, success or failure.
- Deleted verbs and flags are deleted from the grammar, not aliased. Pre-1.0, a major bump means regenerating with a fresh `emery specify` — `emery specify --fresh` where the repository holds a lineage, since a specify never starts an amended history over unasked (`lineage-exists`).
- Engine state is written only through the storage and version-control capabilities. Never hand-edit `.emery/storage`, and never edit `spec/` in the target repository: its three documents are the sealed revision, held to the id their label names, and `spec.md` / `design.md` / `plan.md` beside code are `emery show` output, never sources. `specify` stages and never seals; `apply` seals; `build` and a bare `show` read the current revision alone from the target's repository, so each needs the `[target]`. "Staged" has three homes and is never one item: a **staged candidate** is the revision-store item awaiting `emery apply`; a **staged amendment** stands in the same slot (one item of either `StagedKind`), `show amendment`'s to render, `amend`'s to replace, `apply`'s to seal as a revision over the base it names (refused `amendment-stale` once the repository's current revision or commit is no longer that base), `specify` refusing `amendment-pending` over it and `amend` refusing `amendment-pending` over a staged candidate, neither displacing the other; the **slices staged in the integration copy** are a build's merges an earlier run left in `.emery/vcs/integration`, which the next build resumes.
- When you remove a symbol: `rg <Symbol> -- AGENTS.md README.md docs/` and fix every hit in the same PR.

## Code style

clippy (`make lint`) and nightly rustfmt (`make fmt`) are the style gate; beyond them and the rules below, match the surrounding code.

- Suppress a lint with `#[expect(lint, reason = "…")]` at the smallest scope, never `#[allow]`. The one standing exception is a `#![allow]` with its `reason` around generated bindings alone, whose lints are not the workspace's to expect.
- `<module>.rs` plus `<module>/<child>.rs`; `mod.rs` only under `tests/support/`.
- Visibility is an item's reach and nothing wider. An item is private unless another module reads it; a module's private items are visible to its children, so what only children read stays private whatever the module's own visibility. An item another module reads is `pub`, which a private module bounds to wherever that module is visible. `pub(crate)` only where `pub` would export the item from the crate — an item of a public module chain, or a method or field of a type the crate exports — and `clippy::redundant_pub_crate` refuses it anywhere else. Never `pub(super)` or `pub(in …)`.
- A fn over a type is that type's method, not a free fn taking it as its first argument, where the type's module declares the fn or the fn is a plain lookup or predicate on the type. A constructor is an associated fn. A policy `const` sits beside the type whose method reads it. Values several fns thread through every call become one struct whose methods they are. A fn stays free when it is pure over primitives and iterators, or when it is one module's rule applied to another module's type.

Comments follow the conventions `std`, `serde`, and `tokio` converge on: docs state the observable contract for the crate's user, never the body's mechanics.

- `///` goes on the public API only — the `pub` types, fns, fields, variants, and re-exports a user of the crate can reach — never on an `impl` block or a trait-impl method. An item the crate does not export takes none, whatever its `pub`: a private one, a `pub(crate)` one, a `pub` one in a private module. A clap field's `///` is its `--help` text. A doc opens with one summary sentence (about fifteen words, full stop), then a blank line, then short sentences and bullet lists. `# Examples` holds compiled doctests, for non-obvious usage only; `# Errors` names each class the caller matches on, linked; `# Panics` the rest. Every item mentioned is an intra-doc link. No mechanics, history, or migration notes. A `//!` says what a module is for, in the same shape.
- A private item takes a `//` only for what a senior developer would not see from its name and signature: a constraint, a why, an invariant. Most carry nothing. No restatements, match-arm labels, or body paraphrases.
- Inside a body, a `//` is a section header: lowercase, no full stop, above a blank-line-separated block, naming what the block achieves, so the headers read together outline the fn. A fn readable at a glance carries none, and a header never narrates the line beneath it. The one in-body explanation is `// HACK: …`, for a trick a senior would not see through.
- A test fn takes `//`, never `///`, and only for rationale its scenario name and assertions do not expose.
- No commented-out code.
- Every sentence earns its place and reads once: short plain sentences, one idea each; three or more things are a bullet list, not a colon-and-dash clause; no chained em-dashes, nested parentheticals, or semicolon runs; each fact has one home across `//!`, `///`, and `//`. A comment is as long as its why takes and no longer — concise is not dense, and readable is not verbose.

## Testing

Tests drive the public boundary: a behaviour is asserted through what a user of the product or crate can reach, over scripted doubles rather than the operator's filesystem, a network, or a live model, never through private internals. A suite below the root survives only for an independent library contract (`sdk`, `prose`); a unit test only for a branch no public boundary reaches. A test fn names the scenario (`gen_spec`, `no_sources`), never the outcome. Scripted doubles are strict: script exactly the exchanges a run consumes.

Root-led, on two rungs. Every CLI-reachable behaviour of the engine lives in `tests/` and drives `emery_cli::run` in-process over scripted capabilities (`tests/support/`), asserting the exit code, the envelope, scripted storage, and the version-control calls the scripted `Vcs` recorded — the locations, the order, the commit messages — never the operator's filesystem; the `Provider`'s `Plugins` is a constant, so nothing of a load is asserted there. The adapter boundary (the store, the fetch, the pin, the loader's refusals, a real component extracting and building) and the repository boundary (what a build commits and labels, the repository it clones or creates, what a dirty checkout refuses, what a repository source is lent) are asserted in `tests/runtime.rs` under the real runtime, in a deployment the suite owns, with a strict scripted model; no scripted double stands for a plugin or a version-control capability there, and the binary's `main.rs` is reached by no test.

## Commands

All from the repository root through `make` ([`Makefile`](Makefile) → mise). The tasks are the shared `mise/rust.toml` of [`augentic/toolkit`](https://github.com/augentic/toolkit), pinned in [`mise.toml`](mise.toml) to the tag every `uses:` under `.github/workflows/` names; bump both in one pull request when the pin moves.

```bash
make check # local advisories: audit + fmt (rewrites) + lint + outdated + deps

make lint # lint-host (cargo clippy --workspace --all-targets --all-features, then cargo hack --each-feature), then lint-wasm (the same over every lib, bin and example for wasm32-wasip2 — never tests)
make fmt # cargo +nightly fmt --all
make vet-regen # regenerate cargo-vet imports/exemptions/unpublished, then vet
make cov # cargo llvm-cov nextest --workspace --all-features --summary-only
make sweep # drop target/ artifacts untouched for a week
```

If `make ci` cannot run, say exactly why and which checks ran instead.

# Emery — Agent Instructions

A Rust workspace producing the `emery` binary. `emery specify <adapter>... [--description <adapter>=<text>] [--config [<path>]]` extracts typed claims from source adapters, derives requirements under authority rank (each source's configured `rank` or its kind's default), synthesises a specification and a design, slices the specification into a build plan, and commits the three as one content-addressed revision; `emery build [<adapter>] [--config [<path>]] [--jobs <N>]` builds the current plan in waves through one target adapter — every slice whose dependencies are merged at once, each in a working copy cut from the wave's head, sealed as one commit and merged in id order under the adapter's merge rules, the wave verified by the adapter and labelled `emery/<revision>` — resuming a label the repository already holds; `emery show <spec|design|plan>` prints a Markdown projection of the current revision; `emery completions <shell>` is derived from the clap surface. `plugins/emery/` is the Cursor plugin carrying the `/emery:specify` and `/emery:build` skill wrappers, the latter relaying the label a build set. First-party adapters live in [`augentic/emery-adapters`](https://github.com/augentic/emery-adapters). The v1 implementation is archived at git tag `v1`.

## Git

Never `git commit`, `git push`, open or close a pull request, or delete a branch — in this repository or in any sibling checkout — unless the maintainer lifts this for the session, explicitly and for named work. Leave every change uncommitted in the working tree; the maintainer reviews and commits. No plan or to-do list carries a commit, push, or PR step, and an instruction to complete every step does not override this.

## Vocabulary

- **source adapter** — a WebAssembly component exporting the WIT `source-adapter` world (`metadata` + `extract`): given a `SourceInput` (a name and a workspace or inline value) it returns an `Evidence` document of typed claims. See [wit/emery.wit](wit/emery.wit).
- **target adapter** — a WebAssembly component exporting the WIT `target-adapter` world (`metadata` + `build`): given a `Slice` (its plan entry, the specification cut to its requirements, the whole design) and the writable project tree, it builds the slice into the tree and returns a `Report` of the requirement ids it covered and the files it wrote. Same WIT package, second world.
- **engine** — this product: the engine guest and the crates behind it.
- **capability** — an engine-side trait a provider carries: `Model`, `Source`, `Target`, `Plugins`, `StateStore`, `BlobStore`.
- **contract** — a typed agreement: WIT, CLI grammar, JSON envelope.
- **plugin** — the adapter noun in omnia's loader vocabulary. Not to be confused with the Cursor plugin under `plugins/emery/`, which the `emery` CLI never sees.

When authoritative inputs are incomplete, preserve the gap as `[unknown]` rather than guessing.

## Invariants

- Failures are `omnia_sdk::Error`, built with `bad_request!` and siblings. Explicit variants only for the recovery codes `specify-source-required`, `build-target-required`, `adapter-reference`, `unsupported-version`, `spec-not-generated`, `spec-outdated`, `repository-required`, `base-not-sealed`, `revision-not-found`, `slice-conflict`, `verify-failed`, `label-diverged`. `anyhow::Context` carries the unclassified tail to `server_error`. Production code never panics — a guest panic is a trap with no envelope. Exit codes are omnia's 1:1 map (`Error::exit_code`: `bad_request` 1, `not_found` 2, `server_error` 3, `bad_gateway` 4; clap usage errors exit 64 with no envelope).
- The model never authors a document. Synthesis is typed `Question`s put as briefs (`crates/engine/src/specify/{basis,spec,design,plan}.rs`) and verified against engine facts; the stored revision is the truth and Markdown is a `Display` projection. The specification is drafted per stem group: `SpecBrief::chunked` cuts the bases into chunks of at most `SPEC_CHUNK` (25) requirements — a stem past the cap split, smaller stems merged up to it — one `spec-draft` turn each beside the design and slicing turns, the first chunk alone carrying the preamble, and `SpecBrief::assemble` orders the one `Spec` by `ReqId`. The plan's floor is the stem — the first segment of a requirement subject's dotted id: requirements sharing one are one slice at the least, the model may merge stems and never splits one, each design type key is owned by exactly one slice, and a specification under one stem is one slice with no turn spent. Nothing parses Markdown back, and nothing of a stored revision reaches a run. A revision-shape change re-ids every revision and changes the JSON fixtures under `tests/specify/`; a projection change touches only the `.md` fixtures; a prompt change (`crates/engine/prose/`) touches none.
- The mount and the store follow W^X: what a run can write it never loads code from. The invocation directory is the one mount, `.`, writable — the tree `specify` lends its source adapters, the repository `build` starts from, `.emery/storage` and `.emery/vcs` beneath it — and the package store `~/.emery/adapters` is no mount at all: the host's loader reads it, no guest reaches it, and it lies apart from any project, so a component is never loaded from a tree a run can write; omnia refuses a store beneath a writable mount at assembly, so running `emery` from `$HOME` is refused at startup. Every repository and working copy a run names is a deployment-local path beneath that mount (`.`, `./.emery/vcs/repos/<key>`, `./.emery/vcs/sources/<name>`, `./.emery/vcs/integration`), which the `omnia:vcs` host resolves before git sees it: no guest holds a host path, a credential, or a git process. A build lends its integration working copy, never the checkout, and the mount beneath it is writable `.emery/` included: the revision store fails closed on a document rewritten beneath it rather than preventing the write. `SKIP_DIRS` names `.emery` and `.git`, so `beneath` refuses a claim or a write under either, and `workspace::list` skips a `.git` file as it does the directory, since a linked working copy's root holds one.
- An adapter is an exact package reference, `namespace:name@version` (`AdapterRef`), and nothing else: no default namespace, no latest, no path, no bare name — anything else is `bad_request` with code `adapter-reference` before any load. Every reference goes through the `omnia:plugins/loader` capability at its registry location (`Location::Registry { endpoint: None }`), under the guest name that location registers (`Location::name`: the reference without its version, so `emery:intent@1.0.0` is `emery:intent`), and the deployment's grant bounds every load: the loader reads the release from the package store first — the file `namespace_name@version.wasm` under `~/.emery/adapters`, read fresh on every run, whoever wrote it (the fetcher, an operator's `cp`, `wkg get -o`), final until removed — and, when the store lacks it, fetches it from the registry the deployment routes its namespace to (`emery` to `augentic.io`, compiled in; nothing else routed, and `~/.emery/wasm-pkg.toml` unread), hashes it to the registry's digest, writes it to the store, and loads it; a release the store lacks under a namespace nothing routes is the loader's `refused` before any fetch, naming the namespace and the file the store holds no copy of, hinted `wkg get <reference> -o ~/.emery/adapters/`; a registry that cannot supply it is `unavailable`. The engine names no registry on a load, so a project file, which a build can rewrite, chooses which package and, through `digest`, which bytes, and never where from. A `[[source]] digest` or `[target] digest` rides the load as its pin and the loader holds the bytes that answered — stored or fetched — to it. One reference pinned to two digests, and two versions of one package in one run (one guest), are refused before any load. The only pre-compiled artifact is the engine compiled into the binary; adapters are always raw wasm — the loader admits a package as raw wasm alone, so a `.cwasm` in the store or at the registry is refused typed however it hashes. A loaded handle is held to its axis before any dispatch (`Axis::require` over its exports): a source adapter under `build`, or a target under `specify`, is `bad_request` naming the interface it lacks.
- `build` lands as commits, never in the checkout. The revision is read, and `spec-not-generated` / `spec-outdated` raised, before the target loads; the base is settled after it: without a `[target] repository`, the project checkout's head, which must be a repository (`repository-required`) whose `pending(".")` minus paths under `SKIP_DIRS` is empty and which has a commit (`base-not-sealed`, the paths listed); with one, the `branch`'s commit in the clone under `.emery/vcs/repos/<key>`, cloned or fetched first (`revision-not-found` for a branch, revision, remote, or repository that does not exist; `bad_gateway` for a remote that refuses). The engine never `init`s a repository: a root commit sealed after it would carry `.emery/storage`, and the engine writes no ignore rule. A build resumes: the label `emery/<full revision id>` the repository already holds is read back as a local branch alone (`labelled`) — a tag, a remote's branch, or a commit of that spelling is never it, and a fetch writes no local branch, so whoever can write local branches in the repository a build reads is the operator, the party that already writes `.emery/storage` and the store — and only where it descends from the base (`descends`): a label the branches lack, or one off the base, is a fresh build from the base, and one over the base is resumed from wherever it stands. Its chain is read through `log` from the label to the base, first-parent, and every entry whose `Message` parses under this revision's `Revision:` trailer names a slice that is not built again (`resumed`); an entry without a `Slice:` trailer, or under another revision, is passed over, and a chain naming no slice is still resumed from, every slice built over the labelled head. From the labelled head, or the base, the engine cuts `./.emery/vcs/integration` on no branch, a stale one removed first, and runs the plan in waves: `Plan::ready(merged)` is every unmerged slice whose `depends_on` are merged, in id order (so a slice waiting on nothing is in the first wave whatever its id; none ready with slices left is a stored cycle, `server_error` naming them); every slice of a wave is built at once, up to `jobs` concurrently, each in `./.emery/vcs/worktrees/<id>` cut at the wave's head and handed the slice's plan entry, `Spec::cut` to its requirements, the whole design, the head as its `base`, and that copy; the model never sees the plan whole, and the cap bounds concurrency alone, so a cap of one yields the same history as a wide run. The model writes the copy through the SDK's `write_file` tool alone — the host's workspace tools are read-only — and the SDK's turn holds the report to the tree before it answers: a `written` path the tree does not hold, or a file written and left out, is a correction, so a build that wrote nothing cannot report files. A `Report` the gate refuses is the adapter's defect, `server_error` naming every finding; a requirement left out of `covered` is reported `uncovered`, never invented. Once the wave is built, each slice is integrated in id order, whatever order the builds finished in: its copy is first held to the head it was cut at (`head`), since the model's shell reaches the repository and a commit it sealed or moved there would leave `pending` empty and the slice merged as nothing, so a copy that moved is `server_error` naming both commits, nothing of it sealed; then what it changed is one commit in its copy — `<id> <name>` over `Slice:`, `Revision:`, `Requirements:`, `Covered:`, `Adapter:`, `Base:`, `Wave:` trailers — or none when it changed nothing, merged into the integration copy as a merge commit under the same message and the adapter's `merge_rules` (`union`, `ours`, `theirs` by path glob), and the copy removed. A merge that conflicts at a path no rule resolves is not made: the slice stays unmerged, its `conflicts` recorded, and it is ready again in the next wave over the merged head; its `ATTEMPTS`th (2) conflict is `bad_request` with code `slice-conflict`, the paths listed. A wave that integrated any slice, a commit merged or nothing to merge, is verified: one `Target::verify` over the integration copy answers a `Verdict`, gated by `Verdict::findings` (`server_error` as a bad report is), `passed: false` `bad_request` with code `verify-failed` listing the failures; `passed` seals what the checks left pending as `Wave <k> verified` and labels the head `emery/<full revision id>` in the repository the base came from, so the label always stands at a verified tree and the next wave is cut from it. Once every slice is merged, the label is pushed to the `[target] remote` when one is named, never forced, and the copy removed: a remote whose label holds commits this build does not is `bad_request` with code `label-diverged`, the label standing locally for the next run to resume from and push again once the operator settles the remote. The first failure ends the run as the adapter put it — class and code kept; a slice's failure names the slice, its wave, and the slices merged before it as staying committed in the integration copy; a wave's names the wave, the slices merged in it, and where the label stands; a push's names the remote and where the label stands — the integration copy, and a failed wave's slice copies, staying for inspection until the next build removes them; the engine writes no state of its own for a build: the labelled history is the output, what a run resumes from, and `BuildOutput` is the run's report alone. A repository source under `specify` is the same clone, keyed by its URL normalised (scheme and host case, a trailing `/` or `.git`, the `git@host:path` form), read in `./.emery/vcs/sources/<name>` at its `revision` and removed once the source answered, success or failure.
- Deleted verbs and flags are deleted from the grammar, not aliased. Pre-1.0, a major bump means regenerating with a fresh `emery specify`.
- Engine state is written only through the storage capabilities. Never hand-edit `.emery/storage`. `spec.md` / `design.md` / `plan.md` beside code are `emery show` output, never sources.
- When you remove a symbol: `rg <Symbol> -- AGENTS.md README.md docs/` and fix every hit in the same PR.

## Code style

clippy (`make lint`) and nightly rustfmt (`make fmt`) are the style gate; beyond them and the rules below, match the surrounding code.

- Suppress a lint with `#[expect(lint, reason = "…")]` at the smallest scope, never `#[allow]`.
- `<module>.rs` plus `<module>/<child>.rs`; `mod.rs` only under `tests/support/`.
- A fn over a type is that type's method, not a free fn taking it as its first argument, where the type's module declares the fn or the fn is a plain lookup or predicate on the type. A constructor is an associated fn. A policy `const` sits beside the type whose method reads it. Values several fns thread through every call become one struct whose methods they are. A fn stays free when it is pure over primitives and iterators, or when it is one module's rule applied to another module's type.

Comments follow the conventions `std`, `serde`, and `tokio` converge on: docs state the observable contract for the crate's user, never the body's mechanics.

- `///` goes on the public API only — the `pub` types, fns, fields, variants, and re-exports a user of the crate can reach — never on a private or `pub(crate)` item, an `impl` block, or a trait-impl method. A clap field's `///` is its `--help` text. A doc opens with one summary sentence (about fifteen words, full stop), then a blank line, then short sentences and bullet lists. `# Examples` holds compiled doctests, for non-obvious usage only; `# Errors` names each class the caller matches on, linked; `# Panics` the rest. Every item mentioned is an intra-doc link. No mechanics, history, or migration notes. A `//!` says what a module is for, in the same shape.
- A private item takes a `//` only for what a senior developer would not see from its name and signature: a constraint, a why, an invariant. Most carry nothing. No restatements, match-arm labels, or body paraphrases.
- Inside a body, a `//` is a section header: lowercase, no full stop, above a blank-line-separated block, naming what the block achieves, so the headers read together outline the fn. A fn readable at a glance carries none, and a header never narrates the line beneath it. The one in-body explanation is `// HACK: …`, for a trick a senior would not see through.
- A test fn takes `//`, never `///`, and only for rationale its scenario name and assertions do not expose.
- No commented-out code.
- Every sentence earns its place and reads once: short plain sentences, one idea each; three or more things are a bullet list, not a colon-and-dash clause; no chained em-dashes, nested parentheticals, or semicolon runs; each fact has one home across `//!`, `///`, and `//`. A comment is as long as its why takes and no longer — concise is not dense, and readable is not verbose.

## Testing

Tests drive the public boundary: a behaviour is asserted through what a user of the product or crate can reach, over scripted doubles rather than the operator's filesystem, a network, or a live model, never through private internals. A suite below the root survives only for an independent library contract; a unit test only for a branch no public boundary reaches. A test fn names the scenario (`gen_spec`, `no_sources`), never the outcome. Scripted doubles are strict: script exactly the exchanges a run consumes.

Root-led, on two rungs. Every CLI-reachable behaviour of the engine lives in `tests/` and drives `emery_cli::run` in-process over scripted capabilities (`tests/support/`), asserting the exit code, the envelope, scripted storage, and the version-control calls the scripted `Vcs` recorded — the locations, the order, the commit messages — never the operator's filesystem; the `Provider`'s `Plugins` is a constant, so nothing of a load is asserted there. The adapter boundary — the store, the fetch, the pin, the loader's refusals, and a real component extracting and building — and the repository boundary — what a build commits, labels, and pushes, what a dirty checkout refuses, what a repository source is lent — are asserted in `tests/runtime.rs` under the real runtime, in a deployment the suite owns (`omnia_test::host::Deployment` over the engine guest `build.rs` names, linking the hosts the engine imports, `WasiVcs` over `omnia_git::Client`), over scratch roots, a scratch wasm-pkg `local` registry, in-memory backends, repositories laid with a hermetic git that is also the oracle, and the mocks `build.rs` names, with a strict scripted model; no scripted double stands for a plugin or a version-control capability there, and the binary's `main.rs` is reached by no test. Crate suites survive only for independent library contracts (`sdk`, `prose`); unit tests only for CLI-unreachable branches.

## Commands

All from the repository root through `make` ([`Makefile`](Makefile) → mise). The tasks are the shared `mise/rust.toml` of [`augentic/toolkit`](https://github.com/augentic/toolkit), pinned in [`mise.toml`](mise.toml) to the tag every `uses:` under `.github/workflows/` names; bump both in one pull request when the pin moves.

```bash
make ci # exactly the CI jobs: fmt-check + lint + test + test-docs + docs + vet + deny — run before handing over
make check # local advisories: audit + fmt (rewrites) + lint + outdated + deps
make test # cargo nextest run --locked --workspace --all-features, under -Dwarnings
make lint # lint-host (cargo clippy --workspace --all-targets --all-features, then cargo hack --each-feature), then lint-wasm (the same over every lib, bin and example for wasm32-wasip2 — never tests)
make fmt # cargo +nightly fmt --all
make vet-regen # regenerate cargo-vet imports/exemptions/unpublished, then vet
make cov # cargo llvm-cov nextest --workspace --all-features --summary-only
make sweep # drop target/ artifacts untouched for a week
```

If `make ci` cannot run, say exactly why and which checks ran instead.

`mdbook build docs` builds the CLI reference and checks its links. The live journey (`cargo run -- specify --config examples/emery.toml`, then `cargo run -- build --config examples/emery.toml`, over the two mock components copied into the store `~/.emery/adapters` under references of their own) is in [examples/README.md](examples/README.md). The skill preview is `cursor-agent --plugin-dir plugins/emery` over a `cargo install --path . --locked` binary; reinstall when the CLI changes.

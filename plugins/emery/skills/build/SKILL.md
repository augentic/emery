# Build Skill

`emery build` is the one build verb: it reads the current revision, loads the one target adapter the run names — an exact package reference, `namespace:name@version`, read from the store `~/.emery/adapters` and fetched into it on the first run that names it — and builds the plan in waves. The build lands as commits in one repository, never in the checkout: a clone of the `[target] repository` kept under `.emery/vcs/repos/<name>` and built from its default branch; the project's own repository from its sealed head, when the key is `"."`; or, with no repository named, a repository the engine creates once at that path and keeps. From that base the engine builds every slice whose dependencies are merged at once, each in a working copy of its own, seals what each changed as one commit and merges it in id order into an integration working copy under the adapter's merge rules — a path the rules leave conflicted is resolved with the model from both sides, sealed in the slice's working copy over its commit, and the slice merged again with it taken whole — has the adapter verify the integrated tree, and labels the verified head `emery/<revision>` in that repository — wave after wave, until every slice is merged — then removes the copies. Nothing is pushed: the label stands for the operator to read or push. A label the repository already holds for the revision is resumed: the slices it records are not built again. The checkout the operator is working in is read for its head, when the build lands there, and never written. This skill installs or refreshes the CLI, elicits arguments, invokes the verb, and relays what it committed; it commits nothing itself.

## Invocation

1. **Install or refresh the CLI** — on a machine with no `emery` binary, invoking this skill is consent to install. When `emery` is already on `PATH`, confirm with the operator before reinstalling. Install the latest prebuilt release via Homebrew, or from source; an adapter whose declared minimum `emery-version` outruns the installed binary fails typed later (`unsupported-version`, exit 1) with the same reinstall command as its hint:

```bash
brew tap augentic/tap
brew install emery
# or: cargo install --git https://github.com/augentic/emery --locked
```

Then run `emery --version` and stop on failure. A build also needs `git` 2.5 or newer on `PATH`.

2. **Elicit the target adapter and pass it as a flag** — the CLI has no interactive prompt mode: no adapter at all — and no project-root `emery.toml` carrying a `[target]` table — fails typed (`build-target-required`, exit 1). Gather conversationally: the one target adapter to build through, an exact package reference with a version — `acme:rust@1.4.0`, never `acme:rust`, `rust`, or a path; one without a version or a namespace fails typed (`adapter-reference`, exit 1) before anything loads, so ask for the version when the operator names none. An operator who keeps a config file selects it instead with `--config [<path>]`; omit the value only for the project-relative `emery.toml`, and a run naming no adapter discovers that file on its own. Never combine the file carrier with a positional adapter (mixing fails typed, exit 1). Where the build lands is the config file's alone (`[target] repository`: a URL, built into a clone of it from its default branch; `"."`, the project's own repository; omitted, a repository the engine creates and keeps; `[target] name`, the directory under `.emery/vcs/repos/` a clone or a created repository is kept in, the adapter's name otherwise): a positional adapter names no repository, so it builds into the one the engine creates under the adapter's name. A build needs a committed revision: before any is committed the run fails typed (`spec-not-generated`, exit 2), so run `/emery:specify` first.
3. **Check the base** — under `[target] repository = "."` the base is the project checkout's head, and the run is refused (`base-not-sealed`, exit 1) when the checkout holds an uncommitted change outside `.emery/` and `.git/`, or has no commit yet. Run `git status --short` first; if it shows anything, tell the operator what is pending and let them commit or stash it — never commit or stash on their behalf. A directory that is no repository at all is refused too (`repository-required`, exit 1); the engine never initialises the project directory, so ask the operator to initialise and seal the project, name a repository URL, or drop the key before building. With no `[target] repository` — a positional adapter, or a table without the key — the build lands in a repository the engine creates at `.emery/vcs/repos/<name>` and keeps between runs, so the project directory needs nothing done to it; with a URL, it lands in a clone of that repository from its default branch, the adapter's `init` scaffolding only the files of its layout the tree lacks, so a held project's files stand.
4. **Invoke**, in JSON mode, so the relay can read what was committed:

```bash
emery --format json build <adapter>
# or: emery --format json build --config [<path>]
# or: emery --format json build --jobs 2 <adapter>   # at most two slices of a wave at once
```

Build dispatches one model turn per slice, the slices of a wave at once, and one verify turn per wave, and can take a while on a deep plan. `--jobs <N>` (`-j`, or `EMERY_JOBS`) caps how many slices of a wave build at once when the operator asks for it; unset builds the whole wave at once, and the cap changes the pace alone, never the history. Tracing follows the plugin rule's *Tracing and output* contract (a bare run is `info`; pass `-v` when the operator asks for debug).

## Relay

A successful run's envelope carries `revision`, `waves`, `base`, `repository` (where the build landed and the label stands: `.` for the project checkout, else `./.emery/vcs/repos/<name>`), `resumed` (when a label was resumed), `slices`, `verified`, `sealed` (what a wave's verification left in the tree, as `{ wave, commit, paths }`, when any did), `repaired` (the waves whose seal carries a path outside the adapter's `ours` rules, a repair rather than a regenerated lockfile), `head`, and `label`; each slice is `{ id, name, wave, covered, uncovered, written, resolved, commit }` in merge order, `written` the paths its commit changed, `resolved` the paths its merge conflicted at and the model resolved, omitted when none, and `commit` being the merge commit that brought it in, `null` for a slice that changed nothing. Relay it, and offer the ways to take it:

- Surface the CLI output verbatim — the revision built, the plan's waves, the base commit, the repository the build landed in, the slices resumed, each wave's slices with their covered and uncovered requirement ids, changed paths, resolved paths, and merge commit, the head each wave was verified at and whether its verification repaired the tree or sealed a regenerated file alone, and the label at its head — then the commands that read it, run in `repository` (`git -C .emery/vcs/repos/<name> …` when it is not the checkout): `git log --oneline --first-parent <base>..<label>` for the merges, one per slice and a `Wave <k> verified` commit where the verification repaired something or a check left something behind, `git diff --stat <base> <label>` for the files, `git switch <label>` or `git merge <label>` to take them.
- When the build landed in a clone of a `[target] repository`, offer to push the label to its origin, and push only when the operator asks, never forced:

```bash
git -C .emery/vcs/repos/<name> push origin emery/<revision>
```

- When the build landed in a repository the engine created, the label is that repository's history: offer `git -C .emery/vcs/repos/<name> remote add origin <url>` and a push when the operator has somewhere for it to go, and leave the directory alone otherwise, since deleting it discards the build.

- A requirement the adapter left out of `covered` is reported `uncovered`, never implemented by hand: relay it and let the operator decide whether to re-run, change a source and re-run `/emery:specify`, or take it up themselves.
- Never commit, amend, rebase, or rewrite anything through this skill: every commit of a build is the engine's, sealed with the revision, the requirements, the adapter, and the base in its message, and `spec.md`, `design.md`, `plan.md`, and `.emery/` stay out of it — the projections belong to `/emery:specify`, and the revision store is never tracked.
- On non-zero exit, surface the structured error and stop. The first failure ends the run, and the label stays at the last verified wave — unset when none verified — so the next `emery build` resumes from there rather than starting over; the message names the failed slice and its wave, or the failed wave, and says the slices merged before it, those built beside it in its wave included, stay committed in `./.emery/vcs/integration`, which the operator may inspect (`git -C .emery/vcs/integration log --first-parent`) and the next build resumes from: the slices merged there are verified in their wave, not built again, and the copy is cut again where they stand. A `verify-failed` failure lists the checks the adapter's verify turn failed over the integrated tree: relay them and the hint — inspect the integration copy, re-run to verify the wave's slices again with nothing built again, `git worktree remove --force` the copy to rebuild the wave from the last verified head, or `git bisect` over `emery/<revision>` to attribute a failure to a slice — and let the operator decide; never fix the tree by hand, and never remove the copy through this skill. A `bad_request` whose message says the model backend's time budget was exhausted means one turn timed out on both tries: relay the hint, since a re-run puts it again from where the label and the integration copy stand. A `merge-unresolved` failure names a slice whose merge conflicted at paths the adapter's merge rules leave, and why the model could not resolve them — one side removed a path or holds a link, a directory, or a file that is not text there, or its resolution was refused within the available rounds — so relay the paths and the hint (inspect them in `.emery/vcs/worktrees/<slice>` and `.emery/vcs/integration`; re-run to build the slice again over the merged head; a merge rule in the adapter for a list file or a generated one; or a re-run of `/emery:specify` for a plan that keeps the two in one slice) rather than resolving the conflict by hand. A `secret-detected` failure lists each path the build, the verification, or a merge's resolution wrote that carries a credential and what it carries: nothing of that change set was sealed, and the copy stays under `.emery/vcs/worktrees/<slice>` or `.emery/vcs/integration`; relay the paths and the hint (inspect them, remove the credential from where the build read it, re-run) and let the operator decide, never opening, quoting, or deleting the file's content through this skill. A `build-target-required` failure means no adapter was named and no `[target]` table was found: relay the hint and ask for the adapter. A `base-not-sealed` failure lists the pending paths: relay them and let the operator seal the checkout. A `repository-required` failure means the project is no repository: relay the hint. A `spec-not-generated` or `spec-outdated` failure means there is no revision this binary can build: relay the hint (`/emery:specify` first, or again) and let the operator decide. A `revision-not-found` failure means the `[target] repository` names no repository or has no default branch, or `.emery/vcs/repos/<name>` already holds a repository the engine created, which has no origin to fetch: relay the hint (check the URL; remove the directory or pick another `name`) and let the operator decide, never removing the directory through this skill. A `refused` failure means the loader rejected the request (an invalid or pre-compiled artifact, a `digest` the release does not resolve to, or a release under a namespace the binary routes nowhere, which the hint says to fetch with `wkg get <reference> -o ~/.emery/adapters/`); relay the hint and let the operator decide.

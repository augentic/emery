### Added

The SDK's suite holds the request shape, the reference tools, the gate's findings, and the spent-rounds refusal over a scripted model (`crates/sdk/tests/build.rs`).
- `emery build [<adapter>] [--config [<path>]]`: the build verb. It reads the current revision — `spec-not-generated` (exit `2`) before any is committed, `spec-outdated` (exit `1`) under an older grammar, both before the adapter loads — then loads the one target adapter the run names, by the same location, identity, digest, and `emery-version` rules a source adapter loads under (`adapter::load_target`, over the `load_axis` core `adapter::load` now shares), and builds every slice of the plan in `Plan::order` — a slice after the slices its `depends-on` names, ties by id, the one topological sort the slicing brief's cycle check shares (a cycle the engine never writes would come last, in id order) — one `Target::build` dispatch each, the design rendered once for every slice, handing the adapter `emery_adapter::target::Slice { id, name, requirements, spec: revision.spec.cut(&requirements), design, plan: slice.to_string() }` and the project root as the tree to build into. The adapter is named positionally, or by the `[target]` table of an operator-owned `emery.toml` (`adapter`, and `digest` as a `[[source]]` carries it) selected with `--config [<path>]`; a run naming neither discovers the project-root file, and one that finds no `[target]` there fails typed with `build-target-required` (exit `1`, the fifth recovery code, hinted `pass a target adapter to \`emery build\`, or add a \`[target]\` table to \`emery.toml\` at the project root`); `--config` beside a positional adapter is `bad_request`. `Spec::cut(&ids)` renders the preamble and the named requirements as `emery show spec` renders them, and `Plan::order()` is the build order over `&Slice`s. `tests/build.rs` holds the verb — the dispatch order and briefs, the config and discovery carriers, every refusal, the gate, and the first-failure stop — over the support's `TargetScript`, which the `Provider` double now carries beside its source script; the `spec-not-generated` hint reads `then re-run show or build`.

- The build plan, `plan.md`: a third revision document that slices the specification into buildable pieces. Each `emery specify` run puts a fourth brief, `slicing` (`SliceBrief` over the requirement bases and the type keys the design offers), beside the specification and design drafts: the stem — the first segment of a requirement subject's dotted id — is the floor, so requirements sharing one are one slice at the least, the model may merge stems into one slice and never splits one, names each slice in kebab-case, owns each design `type` key from exactly one slice, orders the slices by `depends-on` (acyclic, never a slice on itself), and briefs each; a specification under one stem is one slice named for it, owning every type, with no turn spent. The engine numbers the slices `SLICE-001` onward by each slice's lowest requirement and writes every list in id order, so re-runs over one specification number alike. The engine's `Plan` and `Slice` types carry it (`revision/plan.rs`), and `emery_engine::specify` re-exports `SliceId`, `PlanDiff`, and `SliceEntry` beside `ReqId`; `Revision { spec, design, plan }` commits it as `<id>/plan.json` under one content id over three length-prefixed bodies; `emery show plan` renders it as `## Slice: <name>` blocks with `ID:`, `Requirements:`, `Types:`, and `Depends on:` lines and the brief's paragraphs, `--format json` carrying the typed document; `PlanDiff` (`Diff.plan`) matches slices by id as `{ id, name }` entries with a `changed` entry naming the differing fields (`name`, `requirements`, `types`, `depends-on`, `brief`), and text mode's one-line summary gains `plan +a -r ~c`. `Requirements:`, `Types:`, and `Depends on:` join `RESERVED`, so no drafted paragraph opens with them. The SDK's `workspace::list` skips `plan.md` beside `spec.md` and `design.md`, and its `claims.md` names the first id segment as the surface the plan slices by. The grammar stamp is `emery: 3`; a stored revision under `2` is `spec-outdated` until the next `specify`.
- The `specify` re-mine diff flags a changed preamble: `SpecDiff` / `DesignDiff` carry `preamble: bool`, the JSON envelope carries it per document, and text mode prints `spec.md ~ preamble` / `design.md ~ preamble`.
- `emery_sdk::Seam { text, files, stems, anchors }`: the one seam shape, each field narrowing the turn and an empty one leaving it open, so `Seam::whole()` (the default) is the input as it stands, `Seam::files(paths)` the files beneath the input's root to mine, `Seam::note(text)` the whole input led by the adapter's text, `Seam::anchors(anchors)` the whole input with its `requirement`s held to those lines, and a struct literal any combination — a surface's text, its entry's import closure as `files`, its stem as `stems`, the lines its survey found a behaviour can start at as `anchors`. `anchors` are spans in the claim `path` grammar (`<path>#L<n>`, `<path>#L<start>-L<end>`, a bare `<path>` for the whole file), root-relative like `files`: when a seam names any, a `requirement` whose `path` shares no line with one of them — a whole-file `path` against listed lines among them — is a finding that names the seam's anchors in the claim's file — the sixteen nearest the claim's lines when it names more, in file order (`is at none of the lines this seam names for a `requirement`; in `src/orders.ts` it names L6-L9, L12; anchor it at the one where its behaviour starts, or leave it out`), or says the seam names none in that file — so the model re-anchors or drops it in the one correction round the backend allows, rather than guessing at a line the finding does not show; a `criterion` and every other kind are not held, the brief says so after the stem sentence (`A `requirement` anchors at one of the lines the text above lists`), and the check runs after the path is settled, so an anchor past the file or outside the seam is that finding alone. An anchor outside the grammar, or any anchor over an inline value, is the adapter's own defect, `server_error` before a turn is spent. `files` are named relative to the root and keep the adapter's order, deduped with `.` and empty segments dropped: the SDK lends the root — the read-only mount is the boundary — and lays the leading files into the turn whole, every line numbered, for as long as they fit within `INLINE_BYTES` together, then lists the rest (`The rest of this seam's files:`) to read from the lend, so an adapter that lays a surface's import closure puts the entry first and a closure past the budget still shows its head; a file that escapes the root or names none is `bad_request`, and files over an inline value are `server_error`. The turn reads text, then the lend, then the stem sentence, then the anchors sentence, then the anchor rule. `Seam::whole()`, `Seam::files(..)`, `Seam::note(..)`, and `Seam::anchors(..)` build the one-field shapes, the two over lists taking any `IntoIterator` of anything `Into<String>`. There is no `Seam` enum and no `Note` type. The SDK re-exports `serde_json` and `tracing`, so an adapter that joins claims of its own to the model's, or logs beside the SDK's events, still depends on `emery-sdk` alone — and, beside the contract types, `Anchor` and `BadAnchor` for the `path` grammar a survey spells anchors in — `Anchor` implements `Display`, re-spelling a parsed anchor in that grammar (`src/a.ts#L2` for one line, never a range of one), so nothing outside the contract crate formats one by hand — and `is_kebab` for the stems it derives. `emery_sdk::workspace::size` is gone: no adapter measured a listing with it — `typescript` sums the texts it parsed — and `workspace::list` is the module's one fn.
- `emery_sdk::extract(ctx, docs, seams)`: the extraction an adapter's `extract` calls — one gated turn per seam, put to the model `ctx` carries under `extract.md` among `docs` with the SDK's `claims.md` appended, so each turn holds the id grammar and the gate without a `read_doc` call for them, at most `emery_sdk::CONCURRENT` (four) pending, joined into one `Evidence` document in seam order; every seam of a workspace is lent the root, so every anchor is root-relative as answered and nothing is re-rooted. `emery_sdk::metadata(kind)`: the `metadata` answer, the adapter's kind beside the SDK's own version as the `emery-version` pin, a target-neutral `AdapterMetadata`. `emery_sdk::source_adapter!(metadata, extract)`: the one macro an adapter's guest invokes, in the shape of omnia's `command!(entry)` — it implements the world's `Guest` on a private type and invokes the bindings' `export!` for it over two plain fns the adapter writes: `fn metadata() -> AdapterMetadata` and `async fn extract<P: Model>(ctx: &Context<'_, P>) -> Result<Evidence, Error>`; the SDK lifts the WIT input and the host's model onto the `Context` before the call and lowers the outcome onto the world's `evidence` and `error` after, so no adapter names a binding or a backend. `emery_sdk::export` — the world's `Guest`, its records, and `export!` — stays public for a guest written by hand.
- `emery-sdk` re-exports what adapter-side code names from the leaves: the contract's `Source` capability (`emery_sdk::Source`, for a program that calls an adapter the way the engine does — an adapter implements the world's `Guest`, never `Source`), and the embedded prose — `emery_sdk::Doc`, `emery_sdk::prose![..]`, and the lookups `emery_sdk::body` and `emery_sdk::find`. An adapter's `[dependencies]` is `emery-sdk` alone, and it has no `[build-dependencies]`. The mock adapter and the SDK's suites name `emery_sdk::Doc`.
- `emery_sdk::RUNTIME`: the runtime references every adapter shares — `claims.md` (the claim `id` grammar, `path` anchors, the skip roots, and the fail-closed gate) and `reconciliation.md` (the `specify` pipeline and where extracted claims land) — embedded once from `crates/sdk/prose/` and shipped with the SDK, so the guidance that describes the gate moves with the pin of the code that enforces it. `read_doc` answers them after the adapter's own documents, and `list_docs` lists the adapter's references and `reconciliation.md`, never a system document — `extract.md`, `claims.md`, or `survey.md`, which a turn carries already or has nothing to learn from — so an adapter's prompt links `claims.md` as it links the adapter's own references and lists nothing; `emery_sdk::check` is the prose crate's `check` re-exported, and an adapter's suite passes `RUNTIME` as its imports (`check(docs, tree, prompts, RUNTIME)`), so such a link resolves, neither document is required in the tree, and a listed document at either path is a finding. The SDK's `tests/prose.rs` holds `RUNTIME` to its own tree.
- `emery_prose::check(docs, tree, prompts, imports)` takes the imports: documents another table embeds beside this one, which a link may name, which the tree need not hold and no prompt need reach, and which no listed document may shadow.
- `emery_sdk::workspace::list(root, keep)`, the physical workspace traversal an adapter may use: it lists the regular files beneath the root the engine lent, sorted and named relative to it as `/`-separated paths. `keep` is asked about every `workspace::Entry` — `Entry::Dir(path)` prunes a directory, `Entry::File(path)` selects a file — by its root-relative path, which the entry reads for the adapter: `path()`, `name()` (the last segment), `extension()` (after the last dot; a leading dot is not one), and `hidden()` (a dot name), so an adapter's policy is `|entry| !entry.hidden()` rather than its own unpicking of a `Path`. The walk never offers the engine's own files — `.omnia/` directories and `spec.md` / `design.md` / `plan.md` wherever they appear — and refuses a name that is not UTF-8 before it is offered. What the adapter does with the files is its own survey policy: `documentation` cuts them into seams, while `intent` uses them only to validate and read its one-file carrier.
- `emery_sdk::survey::surfaces(ctx, docs, facts, check)`: the one turn a survey may put to the model, for a source whose surfaces code cannot decide alone. The adapter's code renders what it read of a workspace as `survey::Facts` — `modules`, every production module root-relative; `text`, what it found (the manifest, the bootstrap, the registration sites); `files`, the files to lay into the turn whole, in order, as far as they fit within `INLINE_BYTES` together — and the SDK asks under the adapter's `survey.md`, its system prompt (a corpus without it is `server_error`, as is an inline value, which has no tree to survey), for a `survey::Inventory`: `surfaces`, each a `name`, an `anchor` in the claim `path` grammar, and a `stem`, and the `unreached` modules no surface reaches. The answer is held to the tree before it is returned — an anchor names one of the listed modules and cites lines its file holds, a stem is lowercase kebab-case, a name is non-empty and unique, an `unreached` module is listed and no surface's entry — and to the adapter's `check`, whose findings are returned to the model together with the SDK's for a correction round, until the host's round limit is spent (`bad_request`); every anchor and `unreached` path is spelled root-relative, as the module list spells them (`./src/a.ts#L2-L2` reads `src/a.ts#L2`), before the gate and the adapter's `check` read it on each round and in what is returned, so an adapter looks a path up as the tree spells it and never unpicks the model's spelling, and a round and the accepted answer see one inventory; an anchor outside the grammar or escaping the root is left as answered for the finding that names it. `Inventory` and `Surface` derive `Serialize` beside `Deserialize`, so a suite scripts the answer from the typed value. The turn lends the tree, offers the reference tools, and is steered by the `survey-<source>` schema; it logs `surveying by model` (the module count) and `surveyed by model` (the surfaces and `unreached` counts) at INFO and the named surfaces at DEBUG. An adapter whose source alone decides the cut (`intent`, `documentation`) puts no survey turn: its survey is a plain fn over the `SourceInput`. Either way, what a survey derives beyond the model's naming — the closure each anchor reaches, the stems code can read there, the ids, the `type` claims `typescript` copies from declarations — is code's, joined to the model's answer in the adapter's own `extract`, after `emery_sdk::extract` returns, built from the re-exported `serde_json`.
- One tracing level governs a run — omnia's host console, the engine, and every adapter — and the global `-v` / `--verbose` and `-q` / `--quiet` flags select it. The flags are omnia's (0.37) `omnia_sdk::api::command::Verbosity`, flattened into `App` so the grammar accepts them, lists them in `--help` and completions, and refuses `-v` beside `-q` as a usage error (exit `64`); omnia's direct entry reads their counts from argv before the engine runs and selects the run's level, forwarding argv verbatim, and the run itself never reads them. A bare `emery` run is command mode's `info`: the engine's progress at its slow steps, an adapter's `source_adapter_extract` boundary span, and the SDK's progress (`mining` per seam; a turn retried or failed at WARN) reach stderr together. Each `-v` raises the level one step and each `-q` lowers it, clamped — `-q` warn, `-qq` error, `-qqq` off; `-v` debug (what each turn yielded, each reference-tool call, each rejected candidate), `-vv` trace. A flag overrides a process `RUST_LOG`; a bare run keeps one that is set, so `RUST_LOG=emery_sdk=debug emery specify …` admits the SDK's detail alone and `RUST_LOG=off` silences every guest. The `runtime!` invocation in `src/main.rs` declares no `env:` — omnia dropped the block — and the engine's own `emery.tracing` key is gone. The SDK's boundary reloads nothing; an adapter built on an earlier SDK opens at `info` as before.
- `[[source]] digest` (`SourceConfig.digest: Option<Digest>`): the `sha256:` pin the adapter's component must resolve to. The engine passes it on the load (`Plugins::load(from, digest)`), and the deployment's loader holds the resolved bytes to it before wasmtime sees them, so a component or package that resolves to other bytes is `refused` (exit `1`); the handle the loader returns carries the digest the bytes hashed to (`Plugin::digest`). A declared guest is attested, not fetched, so a digest on a bare name is `bad_request` before any load. An earlier 0.38 draft dropped the pin with the mirror it hashed; the loader's check restores it without one.
- The SDK's `mining`, `mined`, and `failed` events carry the seam's `label` — the first non-blank line of its `text`, else its first file and how many more, else `tree` or `value` for a whole input — so a run's log names each seam by what it covers rather than its index alone; `Seam` documents that its text's first line is that label. The engine's `extracted` event carries `kinds` (the count per claim kind) and `stems` (the first id segment of each requirement and how many share it), so what a source yielded is read off the log without the document. At TRACE (`-vv`), `mined` is followed by `accepted`, carrying the seam's accepted document as JSON, so what the gate let through is read off the log too, seam by seam.
- The SDK labels each question by what it asks about: a mining turn is `evidence-<source>-<seam>` — the schema name a backend records as the completion's `label` (the Cursor backend's `completion` line) — where every turn of a run had been `evidence`, so a run's completions are matched to their seams without the timestamps.
- `emery_adapter::source::{Evidence, Claim, ClaimKind, Backing}` derive `Serialize`, an absent `id`, `path`, `synopsis`, or `backing` omitted, so an accepted document serialises as the JSON its claims carry — equivalent to the model's answer, not byte-for-byte.
- `AdapterRef` derives `PartialEq` / `Eq`. `emery_engine::ENGINE` is the name of the guest the engine itself runs as; a reference whose location would register under it (`Location::name`) is refused before any load.

### Changed

- The shipped runtime's mounts follow W^X — what a run can write it never loads code from. The invocation directory is mounted as `.` writable, where it was read-only: the tree `specify` lends its source adapters and `build` lends its target, `.omnia/storage` beneath it. The adapters root, `~/.emery/adapters`, is mounted read-only as `adapters` (`emery_engine::ADAPTERS`), apart from any project, and is the one root a local component loads through: an `AdapterRef::File` is a relative path beneath that root, wherever it is written (argv, a `[[source]]` or `[target]` entry — a config file's `adapter` is no longer resolved beside the file), loaded as `adapters/<path>` through the mount and refused `bad_request` when it escapes the root or `not_found` when nothing is there; the engine's `anchored_to` is gone with the file-relative rule. `src/main.rs` carries the one hand-written fn beside the `runtime!` invocation, `adapters_root()`, which creates the directory on first use so the mount opens, and stops the runtime before any guest runs when there is no home directory or the directory cannot be created — a root that fell back into the invocation directory would sit inside the writable mount; omnia refuses a writable mount over a read-only one, so running `emery` from `$HOME` itself is refused at startup. A build lends the whole project tree, `.omnia/` included — the store fails closed on a document rewritten beneath it rather than preventing the write — and an extraction turn's lend is unchanged in path and brief, now over a writable mount. The root suites stage a scenario's component under the repository's gitignored `adapters/`, their stand-in for the mount, and `tests/specify/emery.toml` spells its component paths beneath the root; the first-party adapters' `examples/emery.toml` and eval configs in `emery-adapters` have the same move ahead of them.
- `crates/cli/src/sources.rs` is `config.rs`: the one module carrying every `emery.toml` table — `[[source]]` for `specify`, `[target]` for `build`, `[registries]` for both — and the argv carriers of each verb. Each verb's carriers decode in one flat match (`SourceCarriers` into `SpecifyInput`, `TargetCarriers` into `BuildInput`), and `ConfigFile` is one plain struct read whole: every table must parse for any verb to read the file, as Cargo reads its manifest, so an unknown key under `[[source]]` refuses a `build` and one under `[target]` refuses a `specify`, where each verb decoded its own tables and skipped the rest. A `[[source]]` entry that parses is still located only by the run whose source it is, so an escaping `path` or an absolute component `adapter` among them never refuses a run that named its own sources.
- `emery_engine::adapter::load` returns `Loaded<AdapterMetadata>` per reference — the loaded identity and the adapter's declared metadata — where it returned the kind alone, so one shape serves both axes; `specify` reads the kind off it.
- `emery_engine::Provider` requires `Target` beside `Source`, and the engine guest implements it over the WIT import, so the engine imports both `emery:adapter/source` and `emery:adapter/target` and omnia relays each to the guest exporting it.
- A requirement's citations carry where the claim anchors: `Cited { source, claim, path }`, `path` the claim's own `path` in the claim grammar (`src/orders.ts#L12-L34`) or `null` for a claim without one, stored in `spec.json` and carried by `emery show --format json`; the Markdown projection is unchanged. The re-mine diff matches requirements where they anchor before it matches them by id: an outgoing and an incoming requirement under one stem whose citations share an anchor — the same source and file, line ranges that meet (two whole-file anchors meet too) — are one requirement, paired one to one with the pair sharing the most anchors first and ties in position order, so the pairing is the same whenever the revisions are; what no anchor matches is matched by id as before. A requirement matched under another id is a `changed` entry whose `fields` lead with `id` and which carries `was`, the id it held in the outgoing revision, instead of a removal and an addition — the ids are positional, numbered in source order, and the anchors are the code's. `Requirement::shared_anchors(other)` is the count of anchors two requirements cite in common that scores the pairing, `Cited::overlaps(other)` whether two citations anchor at one place, and `Requirement::stem()` the first segment of the subject. The grammar stamp is `emery: 4`; a stored revision under `3` is `spec-outdated` until the next `specify`.
- The design brief offers a `type` claim under its declared name — its `name` extra, the identifier the declaration spells, before its id and then its path with any line anchor stripped — so several types one requirement id covers are each their own design key rather than one key and a path-suffixed twin. A claim without `name` keys as before.
- `emery_sdk::extract` states that a request the backend's time budget ended is not put once more: the backend reports it as a budget exhausted, a `bad_request`, since the same request put again takes as long; only an upstream failure is retried.
- `Revision::read(id, spec, design, plan)` takes the third body and `Diff::between` carries `plan`; `Changed<E = Entry>` is the one changed-record shape, its identity field `entry` (was `requirement`), so `Changed<SliceEntry>` reports a slice as `Changed` reports a requirement. `ReqId` lives beside `SliceId` in `revision/id.rs`, unchanged in shape and rendering, and orders (`Ord`) by number. The design brief's private section plan is `Outline`, so `Plan` names the document.
- Extraction is `emery_sdk::extract(ctx, docs, seams)`, called from an adapter's own `extract` with the seams its survey chose. It puts each seam to the model as one turn, at most four pending, then joins the partials into one document: claims concatenated in seam order, every anchor as the model answered it, since every seam is lent the root. Every seam is waited for; the failures are then reported together, each as `- seam <index>: <description>` in seam order, under the first failure's class. No seam is `bad_request` before any is mined. One seam is a single turn and its outcome, unchanged. The turn itself — the embedded `extract.md` with the shared `claims.md` as the system prompt, the SDK's brief, the lend, and the claim gate as the check — is the SDK's alone: there is no per-seam hook to call or override, so the seams an adapter hands over are its one way to shape what the model is asked. A survey is a plain fn over the `SourceInput`, so what it decides is asserted with no model at all.
- The SDK is types and functions, the shape of omnia's own guest SDK, and an adapter is a guest of the `source-adapter` world, exported with one macro the way every omnia command guest is with `command!`: its `wasm32`-only guest module invokes `emery_sdk::source_adapter!(metadata, extract)` and writes the two fns it names: `fn metadata() -> AdapterMetadata`, answered with `emery_sdk::metadata(SourceKind::..)`, and `async fn extract<P: Model>(ctx: &Context<'_, P>) -> Result<Evidence, Error>`, which is the adapter's survey — `let seams = survey::survey(ctx.input)?;`, a plain fn over the input — then `emery_sdk::extract(ctx, PROSE, &seams)`, and after it only what the adapter joins to the answer from its own reading of the source, so the flow from cut to turns reads in the adapter's own code and no closure adapts the survey's shape to the SDK's. The `Context` carries the model: the macro's lift binds the host's model, `emery_sdk::Provider` — the unit struct with the empty `impl Model` every omnia guest would otherwise declare, kept in the SDK because an adapter binds the model and nothing else — into every call, so no adapter names a backend, and tests build the `Context` with `Scripted` in the field the lift fills. The guest module is `cfg(target_arch = "wasm32")`, so the crate builds natively and its survey is tested there.

- The `Authority` enum is `SourceKind`, the kind of source an adapter reads (`intent`, `documentation`, `behaviour`); "authority" names the precedence those kinds rank by, not a type. An adapter names it in its `metadata` answer through `emery_sdk::metadata`, and a committed requirement's loser notes record it as `kind` — a revision-shape change, so every revision re-ids. The kebab values and the rendered `Note:` lines are unchanged.
- The kind of source is the adapter's metadata, not the document's. The WIT `adapter-metadata` record gains `kind: source-kind` and the `evidence` record is `claims` alone; `emery_adapter::source::AdapterMetadata` gains `kind: SourceKind` and `Evidence` is `{ claims }`, deriving its answer schema with `deny_unknown_fields`, so a document-level `kind` in a model answer is a schema miss the backend corrects. `emery_sdk::metadata(kind)` reports the adapter's kind beside the `emery-version` pin, and the SDK's per-seam turn asks `Question::<Evidence>` directly. `adapter::load` returns each distinct adapter's declared kind keyed by id (`BTreeMap<String, SourceKind>`) from the one `metadata` read that also gates its version, and `specify` ranks every source by it before the fan-out — so an adapter's rank is fixed at load, never read from what the model returned. Committed revisions are unchanged: the loser `kind` a requirement records is the same value, sourced from the adapter.
- `emery-prose` is named for what it does: the `registry` module is gone and `Doc`, `find`, `body`, and `check` sit at the crate root; the `registry!` macro is `prose!`, after `include_str!` — a declarative macro that takes the list of documents to embed, each named from the invoking file the way `include_str!` names one, and expands to the `&'static [Doc]` itself, each body the `include_str!` of its listed file and each table path what follows the file's `prose/` segment, so an adapter reads `pub static PROSE: &[Doc] = emery_sdk::prose!["../prose/extract.md", ..];` at its crate root and looks the document up as `extract.md`; a listed file outside a `prose/` directory fails the build at the list, as a missing one does. Every tree is flat at its root: an adapter's prompt, `extract.md`, sits at `prose/` beside its `references/`, the SDK's shared references at `crates/sdk/prose/`, and the engine's synthesis corpus at `crates/engine/prose/` — no `prompts/`, `emery/`, or `synthesis/` wrapper holds a whole tree. There is no procedural macro, no `emit` feature, no build-script walker, no generated `docs()` accessor, and no `build.rs`: an edit to a listed file rebuilds the crate through `include_str!`, a listed file the tree lacks fails the build at the list, and `emery_prose::check(docs, tree, prompts, imports)` — the native test a crate's suite runs over the tree beside it, naming the documents its code puts to the model by path — reports a document the list leaves out, a path listed twice, a relative link no listed document answers, a prompt the table lacks, and a listed document no prompt reaches through those links, so nothing is embedded that the model is never told to read; the engine's own corpus is held to the four briefs' `PROSE`. `emery_prose::find` is a scan, so a table is in the order it is listed. `emery_prose::body` returns `Option<&'static str>` instead of panicking on a path the build did not embed — the SDK reads the extraction prompt from the table for each seam's turn and reports a miss as `server_error`.
- The contract and SDK crates are renamed for what they hold. The contract crate is `emery-adapter`, after the `emery:adapter` WIT package it binds, with one public module per axis: `emery_adapter::source::{Source, SourceInput, SourceContent, SourceKind, AdapterMetadata, Evidence, Claim, ClaimKind, Backing, CLAIM_ID_REGEX}` (and, on `wasm32`, `export` — the world an adapter's guest implements, which the SDK re-exports), with the shared kebab predicate at the root (`emery_adapter::is_kebab`). The SDK crate is `emery-sdk`: adapters `use emery_sdk::{Context, Seam, mine, …}` and `emery_sdk::export`; its root stays flat. There is no `emery-source` crate. A second axis lands as a second module in each crate, not a crate.
- The contract crate exposes every public item of an axis from its axis module; the `types` and `claims` modules are gone. `SourceInput::workspace(name, root)` and `SourceInput::value(name, text)` stay as the constructors a host program or a suite builds an input with; the engine builds the struct itself.
- `emery_sdk::Context<'_, P>` is `{ adapter_id, input, model }` — the adapter addressed, the input, and the model every turn of the call is put to; `EvidenceTurn`, `content_note`, and the `types` module are deleted; the crate re-exports the contract's types at its root in place of fourteen individual model types; omnia's `model` module is not among them, since no adapter names a model type — `Error`, `Model`, and the error macros are the SDK's whole re-export of omnia.
- `emery-sdk` ships its own `README.md` as the crates.io page, and its docs.rs build targets `wasm32-wasip2` first, so `export`, `Provider`, and the `source_adapter!` expansion are present in the published documentation. `make lint` runs a second clippy pass over the guest side — `emery-sdk`, the engine guest, and the `adapter` example for `wasm32-wasip2` — so a defect in `cfg(target_arch = "wasm32")` code fails `make ci` rather than the live journey.
- The SDK's user turn always offers the `list_docs` / `read_doc` reference tools (every adapter embeds at least its prompt) and describes a bound workspace in the model's own terms — "`$SOURCE_DIR` is the bound source tree, lent read-only: the root of every file you can read, and the root every `path` is relative to" — naming no path: the root the guest knows the tree by (`./src`, a `/lend/…` mount) is not the one the model's file tools open at, and a turn that quoted it had the model reconciling the two before it read a line. The lend carries the root; the brief and a seam's file list say only what `$SOURCE_DIR` is and how to walk it. The turn names the source by its name and adapter id alone; what kind of source it is, the adapter's own `extract.md` says, so the SDK carries no source noun.
- `specify` checks its source list whole — non-empty, kebab-case names, no name twice, roots beneath the project — before a single adapter loads, so a refused list never fetches a package or reads a component.
- A source's citation handle is its **name** everywhere, as `emery.toml` has always spelled it (`[[source]] name = "api"`): the WIT `input.key` is `input.name`, `SourceInput.key` is `SourceInput.name`, `SourceConfig.key` is `SourceConfig.name`, and the SDK's briefs, events, and prose say "source name" where they said "source key". The stored revision already cited a source as `source`, so no revision re-ids. The WIT record's field changes shape: an adapter built against `emery:adapter` with `input.key` does not instantiate under this engine, and the first-party adapters co-move.
- `specify` ends the run as soon as a source fails, and the failure is the run's as the adapter put it — code and description: a refusal of its input is `bad_request` (exit `1`), an upstream failure `bad_gateway` (exit `4`) — where before every source was waited for and every failure, a refusal included, was flattened into one `server_error` (exit `3`). Evidence the claim gate rejects is still the engine's `server_error`.
- `emery_sdk::extract` reuses a slot as soon as any turn answers rather than once the earliest pending one does, so a slow seam no longer holds finished slots idle behind it; the document still reads in seam order. Seams are dispatched largest first — a seam naming files by their count, one over the whole input, whose size is not known, before them in seam order — so the small seams fill the slots the large ones leave. A seam whose turn fails upstream (`bad_gateway`: the model or a tool transport) is put once more before the source fails, and the retry's outcome stands in for the first; a refusal — the host's, or the gate's once the rounds are spent — is never retried.
- `emery_sdk::CONCURRENT` is documented as a cap on the turns in flight, not on how finely a survey cuts: a finer cut packs the slots better even though no more than four are answered at once.
- The SDK's instrumented source-adapter boundary initializes and flushes guest telemetry around extraction; the guest's filter is the guest environment's `RUST_LOG`, which the runtime sets from the run's tracing level — `info` on a bare run, so an adapter's progress reaches stderr. The SDK's events take the engine's shape — INFO as a slow step opens, DEBUG for what it yielded — and every one names the source key and, within a seam, its index, since the guest console prints no span fields: `mining` (per seam, with the file count where the seam names files) at INFO; `mined` (with the claim count), every reference-tool call (`answered`: the tool, its arguments as the model sent them, and the refusal if any), and every `candidate rejected` (with its findings) at DEBUG; a turn put once more (with the upstream error, which nothing else reports) or `failed` (with its class alone) at WARN. The engine brackets each source with `extracting` at INFO and `extracted` at DEBUG, the latter carrying the claim count, and each brief's `Review::verdict` logs a rejected candidate's findings at DEBUG under the brief's `judge` span (`candidate rejected`), so `-v` names what a refused `spec-draft`, `design-draft`, or `slicing` was refused for where the envelope carries only the last round's. No description is printed twice: the failure body on stderr is its one print, so neither the engine's spans nor the SDK's record an error as an event.
- An adapter's identity is the guest its reference names, and every reference goes through the loader by that name. `AdapterRef::name`, `AdapterRef::id`, and `adapter::Loader` are gone: `adapter::load(provider, adapters, registries)` takes the `(reference, digest)` pairs a run's sources name and the run's `Registries`, loads every distinct adapter once — all together, so a run waits only for its slowest acquisition — and reads each one's `metadata` once, however many sources share it, under the identity the loader's handle returns. Each reference loads at the location it names — omnia's `omnia:plugins/loader.load(from: location, digest: option<string>)`, `omnia_sdk::plugins::Location` on the SDK side — and the deployment's grant bounds every arm: a bare `intent` loads as the declared guest `intent` (`Location::Declared`), which the loader attests when the deployment declares it and refuses typed (`refused`, exit `1`) when it does not — an undeclared name is an envelope rather than a dispatch trap; a local component loads by its project-relative path (`Location::Path`), which the loader reads through the deployment's read-only `.` mount and registers under the file's stem (`./adapters/custom.wasm` dispatches as `custom`), so two references that name one guest — two components sharing a stem — are refused by name (`bad_request`, exit `1`) before either loads; a package loads by its exact reference (`Location::Registry`), fetched from the registry the project's `[registries]` table routes its namespace to, which the engine names on the load, and registers under the reference without its version (`emery:intent@1.0.0` dispatches as `emery:intent`, its location's `Location::name`), so a run holds one version of a package and two versions of one are refused by name as two components sharing a stem are. The engine still refuses a package whose namespace nothing routes, and a component that is not a file beneath the project, before any load. It also refuses a reference that would load as its own guest — `emery_engine::ENGINE`, the `emery` the runtime embeds the engine as: the bare name, or a component with that stem (`bad_request`, exit `1`) — since the loader attests an active guest by name and would hand back the engine itself in the adapter's place, with `metadata` and `extract` then dispatched to it. `adapter::load` returns what each reference `Loaded` as — that identity and the kind of source — keyed by the reference's `Display`, and the `emery-version` gate is put to the same identity. The `source:<name>` routed id is gone with them. The key a source takes when the operator names none is the CLI's rule, beside the argv decoder in `crates/cli/src/sources.rs`, and now serves a `[[source]]` entry that omits `name` too: the bare name, a package's name (`emery:intent@1.0.0` → `intent`), or a component file's stem kebab-cased (`my_adapter.wasm` → `my-adapter`) — no `emery_` or `emery-` prefix is stripped, so the key is the name the guest loads by.
- The shipped runtime (`src/main.rs`) is one `omnia::runtime!` invocation and nothing else: `guests: [{ path: env!("EMERY_GUEST") }]` embeds the engine, named `emery` by the file's stem, in place of `guests: { static: [{ id, source }], .. }`; the read-only `.` mount; the cursor-bound hosts. There is no hand-written `main`, no per-run deployment planning, and no compiled-in registry routing: what varies per run — which adapters load, from where, under which pin — the engine names on each `omnia:plugins/loader` load, and the deployment's grant bounds it. The read-only `.` mount is the one root a local component loads through — the loader reads the file through the mount at the project-relative path the reference names (the engine checks the path against its preopen before the load), fresh on every run — and a package is fetched from the registry the load names, fresh on every run. Nothing declares the source interface `emery:adapter/source@0.1.0` — omnia relays every import outside its own namespaces to the guest exporting it. The root `build.rs` still names the raw `emery.wasm` for a debug build and precompiles a release `emery.cwasm` — for the binary's own `TARGET` under `omnia::CompileOptions::default()`, passed to `omnia::compile::compile` explicitly, so neither the build machine nor the build shell's environment steers the artifact; omnia loads either format, so a release binary starts from the precompiled engine. The loader admits every path and package a guest names as raw wasm alone: the only pre-compiled artifact is the engine compiled into the binary, and an adapter is always raw wasm — a pre-compiled artifact under an adapter's path is refused typed (`refused`, exit `1`) however it hashes, since the path, its pin, and its registry routing come from the same project the run is asked to trust, and a pin proves nothing about who built the bytes. The loader holds a pinned adapter to its digest itself; the engine passes the pin on the load and checks nothing after. The root crate's omnia features are `link` and `loader`. The `runtime` example is gone with `src/wasm-pkg.toml` and `cfg-if`: the live journey runs the shipped binary, `cargo run -- specify --config examples/emery.toml`.

- `SpecBrief::verify` refuses boilerplate scenarios: a `when` or a `then` that restates the requirement's statement (compared case- and punctuation-insensitively; a `then` that echoes the statement records no outcome), or an `[unknown]` `then` for a covered requirement. A `then` shared across requirements is accepted and logged at DEBUG (`one \`then\` repeats across requirements`, with the outcome and the count): two behaviours can observe one outcome, and refusing the draft for it had cost whole regenerations of a large specification for a refrain the check could not tell from a shared result. An uncovered requirement may commit `then: [unknown]` instead of inventing an outcome, and the brief line for one says so. `requirement-block.md` asks the `then` of an uncovered requirement for the outcome the statements themselves name — the value written, the response returned, the state entered — before `[unknown]`, and `claim-landing.md` says the same of a criterion's landing.
- The three document drafts run together. `DesignBrief::new(&extracts, &bases)` and `SliceBrief::new(&bases, types)` take the requirement bases the grouping produced, where each had taken the drafted `Spec` (and the slicing the drafted `Design`), and `specify` joins `spec-draft`, `design-draft`, and `slicing` with `future::try_join3` after the one grouping turn, so a run's wall clock is its slowest draft rather than the sum of three. The specification is drafted in chunks: `SpecBrief::chunked(&extracts, &bases)` partitions the bases by stem into groups of at most `emery_engine::specify::SPEC_CHUNK` (25) requirements — a stem past the cap split, smaller stems merged up to it, in requirement order — and one `spec-draft` turn per chunk runs under `future::try_join_all` beside the design and the slicing, so a run past twenty-five requirements spends its draft across turns of a bounded size and a refused candidate costs one chunk's regeneration rather than the whole draft's. Only the first chunk's turn asks for the preamble; every other chunk's schema pins `preamble` to `maxItems: 0`, its brief says the preamble is drafted with the first chunk, and a preamble answered there is a finding. `SpecBrief::assemble` builds the one `Spec` — the first chunk's preamble, every requirement in `ReqId` order — whichever chunk answers first; a run of twenty-five or fewer is one turn as before, so the JSON fixtures under `tests/specify/` are unchanged, and `tests/specify.rs` gains `chunked_draft` over a run of twenty-eight. Each turn closes on the same requirement outline (`BasesSection`: id, subject, status, sources, coverage, every contributor's statement and role) in place of a rendered document — the design's `## Requirements (the specification's, drafted beside this design)`, the slicing's `## Requirements` — and `synthesise.md`, `design-format.md`, and `slicing.md` say so. The slicing's type keys are the outline's (`DesignBrief::types()`, every key an accepted design references exactly once) in key order, so a plan's `types` list and the schema's enum are sorted by key rather than by the design's block order; `Design::types()` is gone with its one caller.
- `GroupingBrief::verify` refuses a group that merges two ids one source minted under one stem: the extract that named `orders.create` and `orders.cancel` apart under `orders` told them apart, so an answer folding them into one requirement is a finding (`group N: \`<source>\` minted \`a\`, \`b\` as distinct requirements under the stem \`<stem>\`, so they are never one group`) and the backend asks again. Two sources' ids still merge freely, as do one source's ids under different stems; `grouping.md` carries the rule.
- The claim gate checks a `path` anchor's grammar: `emery_adapter::source::Anchor::parse` reads `<path>[#L<n>[-L<m>]]` — a path `emery_adapter::beneath` accepts, and a line range with no leading zero whose end is not before its start — and `Evidence::findings` names each malformed anchor (`BadAnchor`) beside the id and extras findings, so a claim anchored at `../secret`, `.omnia/storage/x`, or `src/a.ts#L9-L3` is refused before any requirement is built from it. `beneath(path)` is the one root-relative path rule, at the contract crate's root beside `is_kebab` with `SKIP_DIRS` and `SKIP_FILES` (moved up from `emery_adapter::source`): it answers the path normalised — `/`-separated, empty and `.` segments dropped — or the `BadPath` it breaks (`Escapes` for an empty, absolute, or `..` path; `NoFile` for one naming the root itself; `SkipDir` under `.omnia/`; `SkipFile` for a `spec.md` / `design.md` / `plan.md`), rendered as `escapes the root`, `names no file`, `is under the engine's own `.omnia/``, `names the engine's own `spec.md``. `BadAnchor::Path(BadPath)` carries it, where `BadAnchor` spelled `Escapes`, `SkipDir`, and `SkipFile` of its own with `escapes the source root` and `is under the skip root`; the report gate holds every `written` path to the same rule, where it had its own with `escapes the workspace root` and no skip-file check, and lists a file twice however the two spellings differ; the SDK's seam files and survey anchors go through it too, where the SDK kept a third copy. `Claim::anchor()` reads a claim's parsed anchor for a caller that checks it against a tree, as the SDK's extract does.
- `emery_sdk::extract` verifies every anchor and id against the seam that minted it, and its `check` hands the model the findings as corrections: a `path` on an inline value's claim (no tree was lent), a `path` outside the files the seam names, a `path` at no regular file under the lent tree, or a `#L` line past the file's last; a `requirement` or `criterion` id whose first segment is not one of the seam's `stems`. A seam's files are laid in the turn whole when they fit — `emery_sdk::INLINE_BYTES` (64 KiB) across the seam — every line led by its number so `#L<n>` is cited from what is shown rather than re-read (`### \`file\` (N lines)` and a fence per file), and listed by path otherwise; `Seam::stems` carries the stems the seam's ids must lead with, so an adapter's survey binds each seam to its surface. `claims.md` states the path and stem rules the gate enforces.
- `GroupingBrief::derive` asks the model to group whenever one source's requirement ids span two or more stems, not only when two or more sources are bound: one source's seams may describe one behaviour under different nouns, and the baseline's id-equality never merges those. A single-source, single-stem run still spends no grouping turn.
- A design `type` block is keyed by the claim's declared name — its id, its `name` extra, or its path with any `#L…` anchor stripped — where a path-keyed claim carried its anchor, so re-anchored runs churned the revision id. A name an earlier claim took gains the later claim's anchored path in parentheses, so two declarations of one name are placed apart.

### Removed

- `emery_cli::Verbosity` is gone: the `-v` / `--verbose` and `-q` / `--quiet` flags are omnia's, declared through `omnia_sdk::api::command::Verbosity` and read by the runtime, never by the engine. The subscriber `execute_wasi` installs is the engine's filter, over the `RUST_LOG` the runtime sets.
- `emery-prose-macros` and `emery_prose::include_prose!` are gone. A corpus is listed with `prose!` and held to its tree by `check`, so no crate carries a `build.rs` for its prose.
- `emery_sdk::SourceAdapter` and the `source!` macro are gone, and with the trait its `extract`, `evidence`, `prompt`, `metadata`, and `stamp`. An adapter's `extract` is its own plain fn — its survey then `emery_sdk::extract` — named to `emery_sdk::source_adapter!` beside its `metadata`, which is `emery_sdk::metadata(SourceKind::..)`; the `doc(hidden)` on `export`, which the trait's macro expanded against, is lifted. `emery_sdk::Answer` is gone too: the model answers the contract's `Evidence` directly, and there is no kind to stamp onto it — the engine takes it from the adapter's metadata.
- The per-source `registry` override (`SourceConfig.registry`, `[[source]] registry`) is gone; a `registry` key on a `[[source]]` is an unknown field. Which registry serves a package is the project's `[registries]` table (`emery.toml`, `<namespace> = "<registry>"`, decoded into `SpecifyInput.registries: Registries`), over the one route the engine knows — `emery` is `augentic.io` unless a line re-routes it — and a namespace nothing routes refuses the package typed (`bad_request`, naming the namespace) before any fetch. A run naming its sources on the command line reads the project-root `emery.toml` for the table alone, its `[[source]]` entries parsed but not merged in. The shipped runtime compiles in no routing and no allow-list — which registry a package is fetched from is the project file's decision, the same operator-owned file that can name a local component outright, and the engine names that registry on the load — where an earlier draft compiled the routing into the binary: `src/wasm-pkg.toml` is gone.
- The reserved `git` and `url` content keys are gone; each is an unknown field, refused with its name and line like any other. The `[[source]] name` key is optional: an entry naming none is keyed by its adapter, as an argv source is.

- `emery build` runs the plan in waves, each slice in a working copy of its own, and resumes from its label. After the base, the engine reads what `emery/<revision>` already holds over it — `Repo::merged_under`: the new `omnia:vcs` `transport.labelled` of the label, the label namespace alone, so a tag, a remote's branch, or a commit of that spelling is never it, `NotFound` a fresh build; the new `store.descends` of the base and the labelled head, `false` a fresh build from the base, since a label off the base is not this base's history; then the new `store.log` (the first-parent chain from the label back to, excluding, the base, newest first), each entry read back through `vcs::Message::parse` and kept when its `Slice:` and `Revision:` trailers name this revision — so the slices it names are not built again (`BuildOutput::resumed`, `  resumed: SLICE-001`) and the run starts from the labelled head, every slice built over it when the chain names none. Whoever can write local branches in the repository a build reads is the operator: a fetch writes no local branch, and a clone creates one, the remote's default. Verifying a resumed head before building on it is not done: under that boundary it is robustness against a moved label or changed checks rather than security, and it costs a turn when nothing is left to build. The slices left go in waves — `Plan::ready(merged)`: every unmerged slice whose `depends-on` are merged, in id order; none ready with slices left is a stored cycle, `server_error` naming them — each wave built at once, up to `--jobs <N>` (`-j`, `EMERY_JOBS`; a `NonZeroUsize`, `0` clap's usage error; unset the wave's width) concurrently through `futures::stream::buffer_unordered`, each slice in `./.emery/vcs/worktrees/<id>` cut at the wave's head and handed, beside its documents, the commit its tree sits on (`slice.base`, which the SDK's brief names); the cap bounds concurrency alone, so a cap of one yields the same history as a wide run. Once the wave is built, each slice is integrated in id order: its commit sealed in its copy under `vcs::Message` (`<id> <name>` over `Slice:`, `Revision:`, `Requirements:`, `Covered:`, `Adapter:`, `Base:`, `Wave:` trailers, `Display` to write and `parse` to read back) and merged into the integration copy as a merge commit under the same message and the adapter's merge rules (`WorkingCopy::merge` over `omnia_sdk::vcs::Rule`, mapped by `vcs::rules` from the metadata's `MergeRule`s), the copy removed either way; a merge that conflicts at a path no rule resolves is not made, the slice left for the next wave with its `conflicts` recorded (`BuiltSlice::conflicts`, `conflicted (<paths>)`), and its `ATTEMPTS`th (2) conflict is `slice-conflict` (exit `1`, hinted a merge rule or a plan that keeps the slices together). A wave that integrated any slice, a commit merged or nothing to merge, is then verified — one `Target::verify` over `./.emery/vcs/integration`, gated by `Verdict::findings` (`server_error` as a bad report is), a failed verdict `verify-failed` (exit `1`) listing the failures, hinted the inspection and `git bisect` over the label — its by-products sealed as `Wave <k> verified`, and the head labelled `emery/<revision>`, so the label always stands at a verified tree, `BuildOutput::verified` lists each wave's head, and text mode prints `  wave <k>: <n> slices verified at <head8>` over the slices' lines (`…, merged <commit>`, `…, nothing to merge`). `push` and the copy's removal come once every slice is merged; the push is never forced, and a remote whose `emery/<revision>` holds commits this build does not is `label-diverged` (exit `1`, hinted the remote branch's reading and its `--delete` way out), the label standing locally for the next run to resume from and push again. A slice's failure names the slice, its wave, and the slices merged before it; a wave's names the wave, the slices merged in it, and where the label stands; a push's (`at_push`) names the remote and where the label stands (`` `emery/<revision>` is not set `` or `` stays at `<head>` ``); the integration copy and a failed wave's slice copies stay for inspection, and the next run removes them and resumes from the last verified wave. `BuiltSlice` gains `wave`; `BuildInput` gains `jobs`; `slice-conflict`, `verify-failed`, and `label-diverged` are the three new recovery codes.

- `emery-sdk` re-exports what adapter-side code names from the leaves: the contract's `Source` capability (`emery_sdk::Source`, for a program that calls an adapter the way the engine does — an adapter implements the world's `Guest`, never `Source`), and the embedded prose — `emery_sdk::Doc`, `emery_sdk::prose![..]`, and the lookups `emery_sdk::body` and `emery_sdk::find`. - `emery_sdk::workspace::list(root, keep)`, the physical workspace traversal an adapter may use: it lists the regular files beneath the root the engine lent, sorted and named relative to it as `/`-separated paths. `keep` is asked about every `workspace::Entry` — `Entry::Dir(path)` prunes a directory, `Entry::File(path)` selects a file — by its root-relative path, which the entry reads for the adapter: `path()`, `name()` (the last segment), `extension()` (after the last dot; a leading dot is not one), and `hidden()` (a dot name), so an adapter's policy is `|entry| !entry.hidden()` rather than its own unpicking of a `Path`. What the adapter does with the files is its own survey policy: `documentation` cuts them into seams, while `intent` uses them only to validate and read its one-file carrier.
- `emery_sdk::survey::surfaces(ctx, docs, facts, check)`: the one turn a survey may put to the model, for a source whose surfaces code cannot decide alone. The adapter's code renders what it read of a workspace as `survey::Facts` — `modules`, every production module root-relative; `text`, what it found (the manifest, the bootstrap, the registration sites); `files`, the files to lay into the turn whole, in order, as far as they fit within `INLINE_BYTES` together — and the SDK asks under the adapter's `survey.md`, its system prompt (a corpus without it is `server_error`, as is an inline value, which has no tree to survey), for a `survey::Inventory`: `surfaces`, each a `name`, an `anchor` in the claim `path` grammar, and a `stem`, and the `unreached` modules no surface reaches. The answer is held to the tree before it is returned — an anchor names one of the listed modules and cites lines its file holds, a stem is lowercase kebab-case, a name is non-empty and unique, an `unreached` module is listed and no surface's entry — and to the adapter's `check`, whose findings are returned to the model together with the SDK's for a correction round, until the host's round limit is spent (`bad_request`); every anchor and `unreached` path is spelled root-relative, as the module list spells them (`./src/a.ts#L2-L2` reads `src/a.ts#L2`), before the gate and the adapter's `check` read it on each round and in what is returned, so an adapter looks a path up as the tree spells it and never unpicks the model's spelling, and a round and the accepted answer see one inventory; an anchor outside the grammar or escaping the root is left as answered for the finding that names it. `Inventory` and `Surface` derive `Serialize` beside `Deserialize`, so a suite scripts the answer from the typed value. The turn lends the tree, offers the reference tools, and is steered by the `survey-<source>` schema; it logs `surveying by model` (the module count) and `surveyed by model` (the surfaces and `unreached` counts) at INFO and the named surfaces at DEBUG. An adapter whose source alone decides the cut (`intent`, `documentation`) puts no survey turn: its survey is a plain fn over the `SourceInput`. Either way, what a survey derives beyond the model's naming — the closure each anchor reaches, the stems code can read there, the ids, the `type` claims `typescript` copies from declarations — is code's, joined to the model's answer in the adapter's own `extract`, after `emery_sdk::extract` returns, built from the re-exported `serde_json`.
- One tracing level governs a run — omnia's host console, the engine, and every adapter — and the global `-v` / `--verbose` and `-q` / `--quiet` flags select it. The flags are omnia's (0.37) `omnia_sdk::api::command::Verbosity`, flattened into `App` so the grammar accepts them, lists them in `--help` and completions, and refuses `-v` beside `-q` as a usage error (exit `64`); omnia's direct entry reads their counts from argv before the engine runs and selects the run's level, forwarding argv verbatim, and the run itself never reads them. A bare `emery` run is command mode's `info`: the engine's progress at its slow steps, an adapter's `source_adapter_extract` boundary span, and the SDK's progress (`mining` per seam; a turn retried or failed at WARN) reach stderr together. Each `-v` raises the level one step and each `-q` lowers it, clamped — `-q` warn, `-qq` error, `-qqq` off; `-v` debug (what each turn yielded, each reference-tool call, each rejected candidate), `-vv` trace. A flag overrides a process `RUST_LOG`; a bare run keeps one that is set, so `RUST_LOG=emery_sdk=debug emery specify …` admits the SDK's detail alone and `RUST_LOG=off` silences every guest. The `runtime!` invocation in `src/main.rs` declares no `env:` — omnia dropped the block — and the engine's own `emery.tracing` key is gone. The SDK's boundary reloads nothing; an adapter built on an earlier SDK opens at `info` as before.
- `[[source]] digest` and `[target] digest` (`SourceConfig.digest`, `BuildInput.digest`: `Option<Digest>`): the `sha256:` pin the adapter's release must resolve to. The engine passes it on the load (`Plugins::load(from, digest)`), and the deployment's loader holds the bytes that answered — the stored file or the fetched release — to it before wasmtime sees them, so a release that resolves to other bytes is `refused` (exit `1`); the handle the loader returns carries the digest the bytes hashed to (`Plugin::digest`). One reference pinned to two digests in one run is `bad_request` before any load.
- The SDK's `mining`, `mined`, and `failed` events carry the seam's `label` — the first non-blank line of its `text`, else its first file and how many more, else `tree` or `value` for a whole input — so a run's log names each seam by what it covers rather than its index alone; `Seam` documents that its text's first line is that label. The engine's `extracted` event carries `kinds` (the count per claim kind) and `stems` (the first id segment of each requirement and how many share it), so what a source yielded is read off the log without the document. At TRACE (`-vv`), `mined` is followed by `accepted`, carrying the seam's accepted document as JSON, so what the gate let through is read off the log too, seam by seam.
- The SDK labels each question by what it asks about: a mining turn is `evidence-<source>-<seam>` — the schema name a backend records as the completion's `label` (the Cursor backend's `completion` line) — where every turn of a run had been `evidence`, so a run's completions are matched to their seams without the timestamps.
- `emery_adapter::source::{Evidence, Claim, ClaimKind, Backing}` derive `Serialize`, an absent `id`, `path`, `synopsis`, or `backing` omitted, so an accepted document serialises as the JSON its claims carry — equivalent to the model's answer, not byte-for-byte.
- `emery_engine::AdapterRef` is one struct, `{ namespace, name, version }`, parsed from the exact package form `namespace:name@version` and nothing else — no default namespace, no latest, no path, no bare name — so a reference without a version or a namespace is `bad_request` with the new recovery code `adapter-reference` (exit `1`), hinted `an adapter is an exact package reference, \`namespace:name@version\``, before anything loads. `Display` is the reference as spelled, which config serialises and a run dedupes loads by; `name()` is the package name, the source name a run binds when the operator gives none (`emery:intent@1.0.0` → `intent`); `guest()` is the reference without its version, the name the adapter loads and dispatches as; `location()` is `Location::Registry { package, endpoint: None }`. It derives `PartialEq` / `Eq` / `Ord` and serde `try_from` / `into` `String`, so `emery.toml` parses an `adapter` straight into it. `emery_engine::Axis { Source, Target }` names the two kinds of adapter by the interface each exports (`Axis::INTERFACES`, `emery:adapter/source@0.1.0` and `emery:adapter/target@0.1.0`), and `Axis::require(reference, exports)` holds a loaded handle to its axis before any dispatch: a source adapter named to `build`, or a target to `specify`, is `bad_request` naming the interface it lacks rather than a trap at the first call.
- `tests/runtime.rs`: the adapter boundary asserted under the real runtime. The suite owns its deployment — `omnia_test::host::Deployment::new().guest("emery", env!("EMERY_GUEST")).mount(project).store(store).registries(local)` over the engine guest `build.rs` names, `Captured::run` linking the four hosts the engine imports (`WasiModel`, `WasiKeyValue`, `WasiBlobstore`, `WasiOtel`) over `Backends::defaults()` and a strict `ScriptedModel`, the loader assembly's — so nothing of the shipped binary is reached from a test and `src/main.rs` carries the production grants alone; it runs over scratch roots: the project, the store, and a wasm-pkg `local` registry the `acme` namespace is routed to, staged with the mock components `build.rs` now names (`EMERY_MOCK_SOURCE`, `EMERY_MOCK_TARGET`). It holds a release read from the store, one fetched into it and read back on the next run, a build writing the project through `write_file`, the pin held and missed, a pre-compiled artifact refused stored or fetched, an unrouted namespace refused with the `wkg get` hint, a file off the reference spelling never read, two versions of one package refused before any load, a source adapter refused under `build`, and a store beneath the writable mount refused at assembly — with no network and nothing of the operator's `$HOME` touched. The native suites keep no double of the plugin capability: the `Provider`'s `Plugins` answers every load with one constant handle exporting both axes, and the gitignored `adapters/` scratch, `ScriptedLoader`, and `tests/specify/emery.toml` are gone.

### Changed

- Every adapter is a package, read from a store. An adapter — a positional `<adapter>`, a `--description <adapter>=<text>`, a `[[source]] adapter`, the `[target] adapter` — is an exact package reference, `namespace:name@version`, and every reference loads through the `omnia:plugins/loader` capability at its registry location, which omnia resolves store-first: the shipped runtime's `plugins: { store: "~/.emery/adapters", registries: include_str!("wasm-pkg.toml") }` names the package store, where a release is one file filed flat by its reference as `namespace_name@version.wasm` — the name `wkg get <reference> -o <dir>/` writes, so `ls ~/.emery/adapters` lists references — read fresh on every run and with no network, whoever wrote it, the fetcher, an operator's `cp`, or `wkg get`, and final until removed; a release the store lacks is fetched from the registry the binary routes its namespace to, hashed to the registry's digest, written to the store once, and loaded, so the first run on a fresh machine that names a release is one fetch and every run after reads the file. The routing is compiled in and nothing on the machine redirects it: `src/wasm-pkg.toml` is `[namespace_registries] emery = "augentic.io"` alone, and a release the store lacks under any other namespace is the loader's `refused` (exit `1`) before any fetch, naming the namespace and the file the store holds no copy of, with the one static hint `wkg get <reference> -o ~/.emery/adapters/` — the command that fills the store under wkg's own routing and the mirror recipe for a machine that must not fetch — where the engine names no registry on a load (`Location::Registry { endpoint: None }`), so a project file, which a build can rewrite, chooses which package and, through `digest`, which bytes, and never where from. A registry that cannot supply a release is `unavailable` (exit `4`), and a copy in the store stands in for it. A copy at a published version stands in for that release on this machine, for every project naming it — the operator's trust the store is, as `~/.cargo/bin` is — and a developer's build is kept beside the release under a version of its own, by convention a `-dev` pre-release (`emery_typescript@0.14.0-dev.wasm`, named `emery:typescript@0.14.0-dev`). The store holds raw wasm alone: a `.cwasm` copied in, or served by a registry, is refused however it hashes. There is no default namespace, no latest, and no machine-wide active release; `emery adapter …` is a clap usage error (exit `64`), since the store is a directory and the shell is its tool. The first-party train publishes to `ghcr.io/augentic/emery/<name>:<version>`, which is where `augentic.io` resolves `emery:<name>@<version>` to.
- The mount and the store follow W^X — what a run can write it never loads code from. The invocation directory is the one mount, `.`, writable where it was read-only: the tree `specify` lends its source adapters and `build` lends its target, `.emery/storage` beneath it. The package store `~/.emery/adapters` is no mount at all — the host's loader reads it and no guest reaches it — and lies apart from any project, so a component is never loaded from a tree a run can write; omnia refuses a store beneath a writable mount when the deployment assembles, so running `emery` from `$HOME` itself is refused at startup. A build lends the whole project tree, `.emery/` included — the revision store fails closed on a document rewritten beneath it rather than preventing the write — and an extraction turn's lend is unchanged in path and brief, now over a writable mount.
- The engine's root under a project is `.emery/`, where it was `.omnia/`: revision state lives at `.emery/storage`, and `emery_adapter::SKIP_DIRS` names `.emery` beside `.git`, so a claim anchored or a file written under either is refused — `is under the reserved `.emery/`` — and `emery_sdk::workspace::list` offers neither. A `.omnia/` left by an earlier build is orphaned: nothing reads it, and a `specify` must be re-run to commit a revision under the new root.
- `crates/cli/src/sources.rs` is `config.rs`: the one module carrying every `emery.toml` table — `[[source]]` for `specify`, `[target]` for `build` — and the argv carriers of each verb, every `adapter` parsed as an `AdapterRef` at the field. Each verb's carriers decode in one flat match (`SourceCarriers` into `SpecifyInput`, `TargetCarriers` into `BuildInput`), and `ConfigFile` is one plain struct read whole: every table must parse for any verb to read the file, as Cargo reads its manifest, so an unknown key or a malformed `adapter` under `[[source]]` refuses a `build` and one under `[target]` refuses a `specify`, where each verb decoded its own tables and skipped the rest. A `[[source]]` entry that parses is still located only by the run whose source it is, so an escaping `path` among them never refuses a run that named its own sources. A `[[source]]` entry without `name` is keyed by its package's name, as an argv source is.
- `emery_engine::adapter::load` returns `Loaded<AdapterMetadata>` per reference — the loaded identity and the adapter's declared metadata — where it returned the kind alone, so one shape serves both axes; `specify` reads the kind off it.
- `emery_engine::Provider` requires `Target` beside `Source`, and the engine guest implements it over the WIT import, so the engine imports both `emery:adapter/source` and `emery:adapter/target` and omnia relays each to the guest exporting it.
- A requirement's citations carry where the claim anchors: `Cited { source, claim, path }`, `path` the claim's own `path` in the claim grammar (`src/orders.ts#L12-L34`) or `null` for a claim without one, stored in `spec.json` and carried by `emery show --format json`; the Markdown projection is unchanged. The re-mine diff matches requirements where they anchor before it matches them by id: an outgoing and an incoming requirement under one stem whose citations share an anchor — the same source and file, line ranges that meet (two whole-file anchors meet too) — are one requirement, paired one to one with the pair sharing the most anchors first and ties in position order, so the pairing is the same whenever the revisions are; what no anchor matches is matched by id as before. A requirement matched under another id is a `changed` entry whose `fields` lead with `id` and which carries `was`, the id it held in the outgoing revision, instead of a removal and an addition — the ids are positional, numbered in source order, and the anchors are the code's. `Requirement::shared_anchors(other)` is the count of anchors two requirements cite in common that scores the pairing, `Cited::overlaps(other)` whether two citations anchor at one place, and `Requirement::stem()` the first segment of the subject. The grammar stamp is `emery: 4`; a stored revision under `3` is `spec-outdated` until the next `specify`.
- The design brief offers a `type` claim under its declared name — its `name` extra, the identifier the declaration spells, before its id and then its path with any line anchor stripped — so several types one requirement id covers are each their own design key rather than one key and a path-suffixed twin. A claim without `name` keys as before.
- `emery_sdk::extract` states that a request the backend's time budget ended is not put once more: the backend reports it as a budget exhausted, a `bad_request`, since the same request put again takes as long; only an upstream failure is retried.
- `Revision::read(id, spec, design, plan)` takes the third body and `Diff::between` carries `plan`; `Changed<E = Entry>` is the one changed-record shape, its identity field `entry` (was `requirement`), so `Changed<SliceEntry>` reports a slice as `Changed` reports a requirement. `ReqId` lives beside `SliceId` in `revision/id.rs`, unchanged in shape and rendering, and orders (`Ord`) by number. The design brief's private section plan is `Outline`, so `Plan` names the document.
- Extraction is `emery_sdk::extract(ctx, docs, seams)`, called from an adapter's own `extract` with the seams its survey chose. It puts each seam to the model as one turn, at most four pending, then joins the partials into one document: claims concatenated in seam order, every anchor as the model answered it, since every seam is lent the root. Every seam is waited for; the failures are then reported together, each as `- seam <index>: <description>` in seam order, under the first failure's class. No seam is `bad_request` before any is mined. One seam is a single turn and its outcome, unchanged. The turn itself — the embedded `extract.md` with the shared `claims.md` as the system prompt, the SDK's brief, the lend, and the claim gate as the check — is the SDK's alone: there is no per-seam hook to call or override, so the seams an adapter hands over are its one way to shape what the model is asked. A survey is a plain fn over the `SourceInput`, so what it decides is asserted with no model at all.
- The SDK is types and functions, the shape of omnia's own guest SDK, and an adapter is a guest of the `source-adapter` world, exported with one macro over one type the way every omnia guest is with `export!(T)`: its `wasm32`-only guest module declares a unit struct, implements `emery_sdk::SourceAdapter` on it, and invokes `emery_sdk::source_adapter!(Adapter)` over it. The trait is two items: `const KIND: SourceKind`, the kind of source the adapter reads, which the macro answers the `metadata` export with through `emery_sdk::metadata`, and `async fn extract<P: Model>(ctx: &Context<'_, P>) -> Result<Evidence, Error>`, which is the adapter's survey — `let seams = survey::survey(ctx.input)?;`, a plain fn over the input — then `emery_sdk::extract(ctx, PROSE, &seams)`, and after it only what the adapter joins to the answer from its own reading of the source, so the flow from cut to turns reads in the adapter's own code and no closure adapts the survey's shape to the SDK's. The `Context` carries the model: the macro's lift binds the host's model, `emery_sdk::Provider` — the unit struct with the empty `impl Model` every omnia guest would otherwise declare, kept in the SDK because an adapter binds the model and nothing else — into every call, so no adapter names a backend, and tests build the `Context` with `Scripted` in the field the lift fills. The guest module is `cfg(target_arch = "wasm32")`, so the crate builds natively and its survey is tested there.

- The `Authority` enum is `SourceKind`, the kind of source an adapter reads (`intent`, `documentation`, `behaviour`); "authority" names the precedence those kinds rank by, not a type. An adapter names it in its `metadata` answer through `emery_sdk::metadata`, and a committed requirement's loser notes record it as `kind` — a revision-shape change, so every revision re-ids. The kebab values and the rendered `Note:` lines are unchanged.
- The kind of source is the adapter's metadata, not the document's. The WIT `adapter-metadata` record gains `kind: source-kind` and the `evidence` record is `claims` alone; `emery_adapter::source::AdapterMetadata` gains `kind: SourceKind` and `Evidence` is `{ claims }`, deriving its answer schema with `deny_unknown_fields`, so a document-level `kind` in a model answer is a schema miss the backend corrects. `emery_sdk::metadata(kind)` reports the adapter's kind beside the `emery-version` pin, and the SDK's per-seam turn asks `Question::<Evidence>` directly. `adapter::load` returns each distinct adapter's declared kind keyed by id (`BTreeMap<String, SourceKind>`) from the one `metadata` read that also gates its version, and `specify` ranks every source by it before the fan-out — so an adapter's rank is fixed at load, never read from what the model returned. Committed revisions are unchanged: the loser `kind` a requirement records is the same value, sourced from the adapter.
- `emery-prose` is named for what it does: the `registry` module is gone and `Doc`, `find`, `body`, and `check` sit at the crate root; the `registry!` macro is `prose!`, after `include_str!` — a declarative macro that takes the list of documents to embed, each named from the invoking file the way `include_str!` names one, and expands to the `&'static [Doc]` itself, each body the `include_str!` of its listed file and each table path what follows the file's `prose/` segment, so an adapter reads `pub static PROSE: &[Doc] = emery_sdk::prose!["../prose/extract.md", ..];` at its crate root and looks the document up as `extract.md`; a listed file outside a `prose/` directory fails the build at the list, as a missing one does. Every tree is flat at its root: an adapter's prompt, `extract.md`, sits at `prose/` beside its `references/`, the SDK's shared references at `crates/sdk/prose/`, and the engine's synthesis corpus at `crates/engine/prose/` — no `prompts/`, `emery/`, or `synthesis/` wrapper holds a whole tree. There is no procedural macro, no `emit` feature, no build-script walker, no generated `docs()` accessor, and no `build.rs`: an edit to a listed file rebuilds the crate through `include_str!`, a listed file the tree lacks fails the build at the list, and `emery_prose::check(docs, tree, prompts, imports)` — the native test a crate's suite runs over the tree beside it, naming the documents its code puts to the model by path — reports a document the list leaves out, a path listed twice, a relative link no listed document answers, a prompt the table lacks, and a listed document no prompt reaches through those links, so nothing is embedded that the model is never told to read; the engine's own corpus is held to the four briefs' `PROSE`. `emery_prose::find` is a scan, so a table is in the order it is listed. `emery_prose::body` returns `Option<&'static str>` instead of panicking on a path the build did not embed — the SDK reads the extraction prompt from the table for each seam's turn and reports a miss as `server_error`.
- The contract and SDK crates are renamed for what they hold. The contract crate is `emery-adapter`, after the `emery:adapter` WIT package it binds, with one public module per axis: `emery_adapter::source::{Source, SourceInput, SourceContent, SourceKind, AdapterMetadata, Evidence, Claim, ClaimKind, Backing, CLAIM_ID_REGEX}` (and, on `wasm32`, `export` — the world an adapter's guest implements, which the SDK re-exports), with the shared kebab predicate at the root (`emery_adapter::is_kebab`). The SDK crate is `emery-sdk`: adapters `use emery_sdk::{Context, Seam, mine, …}` and `emery_sdk::export`; its root stays flat. There is no `emery-source` crate. A second axis lands as a second module in each crate, not a crate.
- The contract crate exposes every public item of an axis from its axis module; the `types` and `claims` modules are gone. `SourceInput::workspace(name, root)` and `SourceInput::value(name, text)` stay as the constructors a host program or a suite builds an input with; the engine builds the struct itself.
- `emery_sdk::Context<'_, P>` is `{ adapter_id, input, model }` — the adapter addressed, the input, and the model every turn of the call is put to; `EvidenceTurn`, `content_note`, and the `types` module are deleted; the crate re-exports the contract's types at its root in place of fourteen individual model types; omnia's `model` module is not among them, since no adapter names a model type — `Error`, `Model`, and the error macros are the SDK's whole re-export of omnia.
- `emery-sdk` ships its own `README.md` as the crates.io page, and its docs.rs build targets `wasm32-wasip2` first, so `export`, `Provider`, and the `source_adapter!` expansion are present in the published documentation. `make lint` runs a second clippy pass over the guest side — `emery-sdk`, the engine guest, and the `adapter` example for `wasm32-wasip2` — so a defect in `cfg(target_arch = "wasm32")` code fails `make ci` rather than the live journey.
- The SDK's user turn always offers the `list_docs` / `read_doc` reference tools (every adapter embeds at least its prompt) and describes a bound workspace in the model's own terms — "`$SOURCE_DIR` is the bound source tree, lent read-only: the root of every file you can read, and the root every `path` is relative to" — naming no path: the root the guest knows the tree by (`./src`, a `/lend/…` mount) is not the one the model's file tools open at, and a turn that quoted it had the model reconciling the two before it read a line. The lend carries the root; the brief and a seam's file list say only what `$SOURCE_DIR` is and how to walk it. The turn names the source by its name and adapter id alone; what kind of source it is, the adapter's own `extract.md` says, so the SDK carries no source noun.
- `specify` checks its source list whole — non-empty, kebab-case names, no name twice, roots beneath the project — before a single adapter loads, so a refused list never fetches a package or reads a component.
- A source's citation handle is its **name** everywhere, as `emery.toml` has always spelled it (`[[source]] name = "api"`): the WIT `input.key` is `input.name`, `SourceInput.key` is `SourceInput.name`, `SourceConfig.key` is `SourceConfig.name`, and the SDK's briefs, events, and prose say "source name" where they said "source key". The stored revision already cited a source as `source`, so no revision re-ids. The WIT record's field changes shape: an adapter built against `emery:adapter` with `input.key` does not instantiate under this engine, and the first-party adapters co-move.
- `specify` ends the run as soon as a source fails, and the failure is the run's as the adapter put it — code and description: a refusal of its input is `bad_request` (exit `1`), an upstream failure `bad_gateway` (exit `4`) — where before every source was waited for and every failure, a refusal included, was flattened into one `server_error` (exit `3`). Evidence the claim gate rejects is still the engine's `server_error`.
- `emery_sdk::extract` reuses a slot as soon as any turn answers rather than once the earliest pending one does, so a slow seam no longer holds finished slots idle behind it; the document still reads in seam order. Seams are dispatched largest first — a seam naming files by their count, one over the whole input, whose size is not known, before them in seam order — so the small seams fill the slots the large ones leave. A seam whose turn fails upstream (`bad_gateway`: the model or a tool transport) is put once more before the source fails, and the retry's outcome stands in for the first; a refusal — the host's, or the gate's once the rounds are spent — is never retried.
- `emery_sdk::CONCURRENT` is documented as a cap on the turns in flight, not on how finely a survey cuts: a finer cut packs the slots better even though no more than four are answered at once.
- The SDK's instrumented source-adapter boundary initializes and flushes guest telemetry around extraction; the guest's filter is the guest environment's `RUST_LOG`, which the runtime sets from the run's tracing level — `info` on a bare run, so an adapter's progress reaches stderr. The SDK's events take the engine's shape — INFO as a slow step opens, DEBUG for what it yielded — and every one names the source key and, within a seam, its index, since the guest console prints no span fields: `mining` (per seam, with the file count where the seam names files) at INFO; `mined` (with the claim count), every reference-tool call (`answered`: the tool, its arguments as the model sent them, and the refusal if any), and every `candidate rejected` (with its findings) at DEBUG; a turn put once more (with the upstream error, which nothing else reports) or `failed` (with its class alone) at WARN. The engine brackets each source with `extracting` at INFO and `extracted` at DEBUG, the latter carrying the claim count, and each brief's `Review::verdict` logs a rejected candidate's findings at DEBUG under the brief's `judge` span (`candidate rejected`), so `-v` names what a refused `spec-draft`, `design-draft`, or `slicing` was refused for where the envelope carries only the last round's. No description is printed twice: the failure body on stderr is its one print, so neither the engine's spans nor the SDK's record an error as an event.
- An adapter's identity is the guest its reference names, and every reference goes through the loader by that name. `AdapterRef::id` and `adapter::Loader` are gone: `adapter::load(provider, adapters)` takes the `(reference, digest)` pairs a run's sources name, loads every distinct reference once — all together, so a run waits only for its slowest acquisition — and reads each one's `metadata` once, however many sources share it, under the identity the loader's handle returns; `adapter::load_target` loads a build's one target the same way, both over the shared `load_axis`, which returns `Loaded<M>` — the loaded identity and the adapter's declared metadata — so one shape serves both axes and `specify` reads the kind of source off it. Each reference loads at its registry location — omnia's `omnia:plugins/loader.load(from: location, digest: option<string>)`, `omnia_sdk::plugins::Location` on the SDK side — and registers under the reference without its version (`emery:intent@1.0.0` dispatches as `emery:intent`, its location's `Location::name`), so a run holds one version of a package and two versions of one are refused by name (`bad_request`, exit `1`) before either loads. The engine's `bad_request` refusals are the grammar's alone, before any load; a release the store lacks under an unrouted namespace, a pre-compiled artifact, and a pin the bytes miss are the loader's `refused`, and a registry that cannot supply a release its `unavailable`, each named by the engine with the adapter that failed (`adapter \`acme:nope@1.0.0\`: …`). The `source:<name>` routed id is gone with them.
- The shipped runtime is one `omnia::runtime!` invocation and nothing else, in `src/main.rs` under the host arm of `cfg_select!`, the wasm32 arm an empty `main` as before, while `src/lib.rs` stays the wasm32 engine guest whole and the native `rlib` is empty: `guests: [{ path: env!("EMERY_GUEST") }]` embeds the engine, named `emery` by the file's stem; `plugins: { store, registries }` the package store and the one compiled-in route; the one writable `.` mount; the cursor-bound hosts. There is no hand-written `main`, no `adapters_root()`, no `wasm_pkg()`, no written template, no per-run deployment planning, and no `adapters` mount: what varies per run — which releases load, under which pin — the engine names on each `omnia:plugins/loader` load, and the deployment's store and routing bound it. Nothing declares the adapter interfaces — omnia relays every import outside its own namespaces to the guest exporting it. The lib's crate type is `rlib` alone, so no native build links a `libemery.dylib` nobody loads; the root `build.rs` builds the wasm32 guest with `cargo rustc --lib --crate-type cdylib` — the raw `emery.wasm` for a debug build, a release `emery.cwasm` precompiled for the binary's own `TARGET` under `omnia::CompileOptions::default()`, passed to `omnia::compile::compile` explicitly, so neither the build machine nor the build shell's environment steers the artifact; omnia loads either format — and builds the two mock adapters under `examples/` beside it, naming them `EMERY_MOCK_SOURCE` and `EMERY_MOCK_TARGET` for the runtime suite. Nothing of an adapter is fetched or embedded: the build is offline and the binary carries the engine alone. The loader admits a package as raw wasm alone: the only pre-compiled artifact is the engine compiled into the binary, and a `.cwasm` in the store or at a registry is refused typed (`refused`, exit `1`) however it hashes, since a pin says nothing about who built the bytes. The root crate's omnia features are `jit`, `link`, and `loader`; `omnia-test` is a dev-dependency with `guest` and `host`. The `runtime` example and `cfg-if` are gone: the live journey runs the shipped binary, `cargo run -- specify --config examples/emery.toml`, over the two mock components copied into the store under references of their own (`example:source@0.1.0`, `example:target@0.1.0`).

- `SpecBrief::verify` refuses boilerplate scenarios: a `when` or a `then` that restates the requirement's statement (compared case- and punctuation-insensitively; a `then` that echoes the statement records no outcome), or an `[unknown]` `then` for a covered requirement. A `then` shared across requirements is accepted and logged at DEBUG (`one \`then\` repeats across requirements`, with the outcome and the count): two behaviours can observe one outcome, and refusing the draft for it had cost whole regenerations of a large specification for a refrain the check could not tell from a shared result. An uncovered requirement may commit `then: [unknown]` instead of inventing an outcome, and the brief line for one says so. `requirement-block.md` asks the `then` of an uncovered requirement for the outcome the statements themselves name — the value written, the response returned, the state entered — before `[unknown]`, and `claim-landing.md` says the same of a criterion's landing.
- The three document drafts run together. `DesignBrief::new(&extracts, &bases)` and `SliceBrief::new(&bases, types)` take the requirement bases the grouping produced, where each had taken the drafted `Spec` (and the slicing the drafted `Design`), and `specify` joins `spec-draft`, `design-draft`, and `slicing` with `future::try_join3` after the one grouping turn, so a run's wall clock is its slowest draft rather than the sum of three. The specification is drafted in chunks: `SpecBrief::chunked(&extracts, &bases)` partitions the bases by stem into groups of at most `emery_engine::specify::SPEC_CHUNK` (25) requirements — a stem past the cap split, smaller stems merged up to it, in requirement order — and one `spec-draft` turn per chunk runs under `future::try_join_all` beside the design and the slicing, so a run past twenty-five requirements spends its draft across turns of a bounded size and a refused candidate costs one chunk's regeneration rather than the whole draft's. Only the first chunk's turn asks for the preamble; every other chunk's schema pins `preamble` to `maxItems: 0`, its brief says the preamble is drafted with the first chunk, and a preamble answered there is a finding. `SpecBrief::assemble` builds the one `Spec` — the first chunk's preamble, every requirement in `ReqId` order — whichever chunk answers first; a run of twenty-five or fewer is one turn as before, so the JSON fixtures under `tests/specify/` are unchanged, and `tests/specify.rs` gains `chunked_draft` over a run of twenty-eight. Each turn closes on the same requirement outline (`BasesSection`: id, subject, status, sources, coverage, every contributor's statement and role) in place of a rendered document — the design's `## Requirements (the specification's, drafted beside this design)`, the slicing's `## Requirements` — and `synthesise.md`, `design-format.md`, and `slicing.md` say so. The slicing's type keys are the outline's (`DesignBrief::types()`, every key an accepted design references exactly once) in key order, so a plan's `types` list and the schema's enum are sorted by key rather than by the design's block order; `Design::types()` is gone with its one caller.
- `GroupingBrief::verify` refuses a group that merges two ids one source minted under one stem: the extract that named `orders.create` and `orders.cancel` apart under `orders` told them apart, so an answer folding them into one requirement is a finding (`group N: \`<source>\` minted \`a\`, \`b\` as distinct requirements under the stem \`<stem>\`, so they are never one group`) and the backend asks again. Two sources' ids still merge freely, as do one source's ids under different stems; `grouping.md` carries the rule.
- The claim gate checks a `path` anchor's grammar: `emery_adapter::source::Anchor::parse` reads `<path>[#L<n>[-L<m>]]` — a path `emery_adapter::beneath` accepts, and a line range with no leading zero whose end is not before its start — and `Evidence::findings` names each malformed anchor (`BadAnchor`) beside the id and extras findings, so a claim anchored at `../secret`, `.emery/storage/x`, or `src/a.ts#L9-L3` is refused before any requirement is built from it. `beneath(path)` is the one root-relative path rule, at the contract crate's root beside `is_kebab` with `SKIP_DIRS` and `SKIP_FILES` (moved up from `emery_adapter::source`): it answers the path normalised — `/`-separated, empty and `.` segments dropped — or the `BadPath` it breaks (`Escapes` for an empty, absolute, or `..` path; `NoFile` for one naming the root itself; `SkipDir` under `.emery/` or `.git/`; `SkipFile` for a `spec.md` / `design.md` / `plan.md`), rendered as `escapes the root`, `names no file`, `is under the reserved `.emery/``, `names the engine's own `spec.md``. `BadAnchor::Path(BadPath)` carries it, where `BadAnchor` spelled `Escapes`, `SkipDir`, and `SkipFile` of its own with `escapes the source root` and `is under the skip root`; the report gate holds every `written` path to the same rule, where it had its own with `escapes the workspace root` and no skip-file check, and lists a file twice however the two spellings differ; the SDK's seam files and survey anchors go through it too, where the SDK kept a third copy. `Claim::anchor()` reads a claim's parsed anchor for a caller that checks it against a tree, as the SDK's extract does.
- `emery_sdk::extract` verifies every anchor and id against the seam that minted it, and its `check` hands the model the findings as corrections: a `path` on an inline value's claim (no tree was lent), a `path` outside the files the seam names, a `path` at no regular file under the lent tree, or a `#L` line past the file's last; a `requirement` or `criterion` id whose first segment is not one of the seam's `stems`. A seam's files are laid in the turn whole when they fit — `emery_sdk::INLINE_BYTES` (64 KiB) across the seam — every line led by its number so `#L<n>` is cited from what is shown rather than re-read (`### \`file\` (N lines)` and a fence per file), and listed by path otherwise; `Seam::stems` carries the stems the seam's ids must lead with, so an adapter's survey binds each seam to its surface. `claims.md` states the path and stem rules the gate enforces.
- `GroupingBrief::derive` asks the model to group whenever one source's requirement ids span two or more stems, not only when two or more sources are bound: one source's seams may describe one behaviour under different nouns, and the baseline's id-equality never merges those. A single-source, single-stem run still spends no grouping turn.
- A design `type` block is keyed by the claim's declared name — its id, its `name` extra, or its path with any `#L…` anchor stripped — where a path-keyed claim carried its anchor, so re-anchored runs churned the revision id. A name an earlier claim took gains the later claim's anchored path in parentheses, so two declarations of one name are placed apart.

### Removed

- `emery_cli::Verbosity` is gone: the `-v` / `--verbose` and `-q` / `--quiet` flags are omnia's, declared through `omnia_sdk::api::command::Verbosity` and read by the runtime, never by the engine. The subscriber `execute_wasi` installs is the engine's filter, over the `RUST_LOG` the runtime sets.
- `emery-prose-macros` and `emery_prose::include_prose!` are gone. A corpus is listed with `prose!` and held to its tree by `check`, so no crate carries a `build.rs` for its prose.
- The `source!` macro is gone, and `emery_sdk::SourceAdapter` keeps `extract` alone of its methods: `evidence`, `prompt`, `metadata`, and `stamp` are gone, the kind `metadata` answered is the trait's `const KIND`, and the type implementing it is exported with `emery_sdk::source_adapter!(Adapter)`. An adapter's `extract` is its survey then `emery_sdk::extract`; the `doc(hidden)` on `export`, which the trait's macro expanded against, is lifted. `emery_sdk::Answer` is gone too: the model answers the contract's `Evidence` directly, and there is no kind to stamp onto it — the engine takes it from the adapter's metadata.
- The per-source `registry` override (`SourceConfig.registry`, `[[source]] registry`), the `[registries]` table, and `emery_engine::Registries` are gone; a `registry` key on a `[[source]]` and a `[registries]` table are unknown fields, refused with their name and line. Where a release is fetched from is the binary's compiled-in route (`emery` to `augentic.io`) and otherwise the operator's `wkg get <reference> -o ~/.emery/adapters/`; `~/.emery/wasm-pkg.toml` is not read — a file there from an earlier 0.38 build is inert and may be deleted.
- Bare names and component paths are gone from every adapter position: `AdapterRef::File` / `AdapterRef::Static`, `Location::Path` / `Location::Declared` loads, the `.wasm` and kebab heuristics, the stem rule (`my_adapter.wasm` → `my-adapter`), `file://`, the `NAMESPACE` shorthand (`intent@1.0.0` for `emery:intent@1.0.0`), `emery_engine::ADAPTERS`, `emery_engine::ENGINE`, and the engine's refusal of a reference naming its own guest (a package id always carries a colon and the engine's is bare, so the collision is structural). The shipped binary declared no adapter, so a bare name always refused; now it is `bad_request` with code `adapter-reference` before any load, as a path is. A component an earlier 0.38 build read from `~/.emery/adapters/<name>.wasm` is never read again: `mv ~/.emery/adapters/name.wasm ~/.emery/adapters/<namespace>_<name>@<version>.wasm` keeps one still wanted, under the reference a project names it by (a developer's build under a `-dev` version of its own), and `rm` drops one the next run may fetch.
- The reserved `git` and `url` content keys are gone; each is an unknown field, refused with its name and line like any other. The `[[source]] name` key is optional: an entry naming none is keyed by its adapter, as an argv source is.
